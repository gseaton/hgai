# Mutation Summary

## Intent
The 3D Visualization renders every hypernode and hyperedge in the selected hypergraph(s) at once, which becomes overwhelming for any graph of real size. The user wanted a way to "zoom in" on one entity of interest — a hyperedge or hypernode identifier — and see only the elements within a chosen number of connectivity hops from it, with that focus element re-centered at the origin and the camera automatically framed to the resulting subgraph.

## Context
This is the eighth in a sequential run of 3D-visualization enhancements this session (hyperedges-as-members support, members-label decluttering, z-order correctness, shift+drag panning, a collapsible details panel, and an orphan-node-hiding toggle), all implemented and live-verified the same way. `renderViz()` already had an established shape — fetch raw nodes/edges per selected graph, build viz nodes/links, call `.graphData()`, then `zoomToFit` — that the orphan-hiding toggle from the immediately preceding turn had already extended once by filtering the raw node list before the node-building loop runs. The focus filter reuses that same insertion point rather than introducing a new filtering mechanism.

## What Changed and Why
- **"Degree" is defined per the user's own worked example** ("1 only go out 1, 2 go out 1 then those 1 degree nodes link to their 1 degree nodes") as full BFS hops through the hypergraph, not a literal edge-count — because a raw edge-count definition breaks down at a hyperedge, which has no single "other side." `vizOneHopNeighbors()` instead defines one hop as one semantic step: expanding a **hypernode** pulls in every hyperedge it belongs to *and* every other member of those hyperedges in the same step (so a hyperedge never appears with only one of its participants visible — it would otherwise misrepresent the relationship); expanding a **hyperedge** pulls in just its direct members. `vizComputeNeighborhood()` runs this BFS for exactly `degree` iterations from the focus id.
- **Filtering happens before the existing node/link-building logic**, exactly where the prior turn's orphan-hiding filter already hooks in — `rawNodes`/`edges` are trimmed down to the neighborhood's id sets per selected graph, and the unmodified downstream logic (hnode/henode/members/link construction) simply builds a smaller scene from smaller input, with no separate code path needed for "focused" vs "unfocused" rendering.
- **The origin-pin uses d3-force's `fx`/`fy`/`fz` fixed-position fields, not just `x`/`y`/`z`.** Setting only `x/y/z` places a node at the origin for one frame, but the force simulation immediately moves it again as it settles; `fx/fy/fz` tells d3-force to treat the node as anchored, so the rest of the neighborhood settles relative to a focus point that actually stays at the origin — this is what "move the filter hyperedge/hypernode to the origin" required literally, not just visually for a moment.
- **`zoomToFit` was already invoked unconditionally after every render** (established since the very first viz turns this session) — no new camera-fitting logic was needed; filtering the node set before that existing call already produces a "fit to the filtered result" effect for free, satisfying the "and 'fit' the resultant filtered visualization to the view" half of the request.
- **A focus id can resolve to either an hnode or a henode** (hypernode vs hyperedge identity node use different viz-id prefixing schemes, per the existing `hello-world::<id>` / `hello-world::he::<id>` convention). `renderViz()` checks the computed neighborhood's `nodeIds`/`edgeIds` sets to determine which prefix applies before locating the actual viz node object to pin.
- **A focus id absent from a particular selected graph contributes nothing from that graph**, rather than falling back to that graph's full unfiltered content — relevant when multiple graphs are selected at once, since a filtered neighborhood view silently reverting to "everything" for graphs that don't contain the focus id would be a confusing inconsistency. A single toast fires (not one per graph) if the id isn't found in *any* selected graph, and the empty-state message becomes focus-aware ("No elements found within N degree(s) of ...") when nothing at all resolves.
- **Both the Focus button and Enter-in-the-input-field trigger a render**, and changing the degree select while a focus is already active also re-renders automatically (guarded so it's a no-op with an empty focus field) — matching the reactive-toggle precedent set by the orphan-hiding switch in the prior turn, where a control that changes what's actually in the scene re-renders on its own rather than requiring a separate manual step.

## Key Decisions
- Considered defining "degree" as a literal single-edge-hop count (matching a conventional graph-theory reading of "degree"), but the user's own parenthetical example describes a two-step expansion at degree 1 (hypernode → its hyperedges → their other members) — a literal single-hop reading would either strand every hyperedge with zero visible members at degree 1, or require the user to spend one extra "degree" just to see a hyperedge's participants at all. The semantic-hop definition matches the example given exactly.
- Reused the neighborhood-filtering insertion point from the immediately preceding orphan-hiding turn rather than adding a second, parallel filtering pass — the two filters (orphan-hiding, focus) compose naturally this way (both narrow `rawNodes`/`edges` before the same downstream build logic runs) without needing to reconcile two different filtering mechanisms.

## Verification
Live end-to-end verification via a hand-rolled CDP script against a freshly-started `hgai.main` dev server (it had stopped between sessions) and a freshly-created headless Chrome profile (established practice this session, to avoid stale-cache false results). Logged in as `admin`, rendered the `hello-world` demo graph (baseline: 50 nodes / 69 links), and independently fetched the raw hyperedge data via the app's own `fetchGraphElements()` to hand-compute the expected neighborhood before testing against it, rather than trusting the feature's own output to validate itself:
- **Focus `person:moe`, degree 1**: resulting scene had exactly the 8 hypernodes and 6 hyperedges independently computed from the raw membership data (the Three Stooges cluster), with zero leakage from unrelated clusters (Rat Pack, Beatles, Entertainment groups). `moe`'s viz node had `fx=fy=fz=0` and `x=y=z=0`.
- **Focus `person:moe`, degree 2**: grew to 11 hypernodes / 8 hyperedges, correctly picking up `group:beatles`, `group:entertainment`, `group:rat-pack` (reachable because `group:three-stooges`, a degree-1 node, itself belongs to two more hyperedges linking sibling groups together) while still correctly excluding the *individual members* of those other groups (`person:frank`, `person:lennon`, etc.) — those are a further hop away, confirming the BFS frontier logic expands exactly one additional semantic step, not an unbounded flood.
- **Focus a hyperedge id directly (`edge:classic-stooges`), degree 1**: resulting scene had precisely that edge's 4 direct members and nothing else (6 total viz nodes including the henode and its virtual members node), with the henode pinned at the origin.
- **Nonexistent id (`person:does-not-exist`)**: correct warning toast fired, and the empty-state panel showed the focus-aware message.
- **Clear button**: fully restored the original unfiltered 50-node/69-link scene and reset the input field to empty.
- **Enter-key path** (typing an id and pressing Enter, bypassing the Focus button): produced the identical 8-hypernode result as the button-click path.
- **Degree-select `change` listener** (changing the degree dropdown without clicking Focus, while a focus is already active): correctly re-triggered a render and grew the result from 8 to 11 hypernodes, matching the button-driven degree-2 test.
- **Camera re-fit**: captured `cameraPosition()` before and after switching focus from an 11-hypernode neighborhood to a 4-hypernode one — camera distance shrank from z≈345.9 to z≈182.8, confirming `zoomToFit` actually re-frames the camera to the new, smaller scene rather than leaving it at a stale distance.

No bugs were found during this verification pass — a first for this session's run of 3D-viz turns, each of which had previously surfaced at least one genuine issue (stale browser cache, synthetic-event/native-input mismatches, simulation-settling timing artifacts, and a real CSS flexbox bug) only through live testing.
