# Mutation Summary

## Intent
Continue the phased inferencing plan with Step 5: surface the reasoning engine built in Steps 2–4 (`expand_edge`/`expand_edge_closure`, `check_transitive`) across every remaining query/access surface — SHQL, MCP, REST, and UI discoverability — in the dependency order the plan specified (SHQL first, since it's more expressive/agent-relevant than HQL for chained reasoning; then MCP and REST, both thin wrappers over the same engine functions; then UI, lowest priority).

## Context
HQL's `infer: true` (Step 3) and its transitive-reachability wiring (Step 4) were already built and live-verified. SHQL's pattern-matching engine (`_eval_edge_pattern`) has a materially different shape — it evaluates patterns against a growing list of variable bindings, with member-pattern matching that can bind new `?vars` from an edge's member list — so wiring inference in required understanding that architecture first: an inferred edge needed to enter the *same* candidate-edge list a literal `.search()` call produces, before `_match_members_expand` runs, for it to be genuinely "first-class and chainable" as the plan's build-plan.md source material specifically calls out (an inferred edge can bind `?var` and anchor a later hop, no different from a stored one).

## What Changed and Why
SHQL gained the identical two capabilities HQL has — axiom-driven expansion and transitive-path reachability — behind a top-level `infer: true` flag threaded through the full pattern-evaluation recursion (including `optional`/`union` branches, so inference isn't silently dropped inside those constructs). The transitive-reachability trigger reuses SHQL's own `bound_node_ids` computation (already needed for query narrowing) to detect when a 2-member pattern has both endpoints concrete, rather than introducing new pattern syntax.

MCP and REST were comparatively mechanical once the engine functions existed: two MCP tools (`hgai_infer_expand_edge`, `hgai_infer_check_transitive`) and a new `/graphs/{graph_id}/infer/{transitive,expand}` REST router, both calling the exact same `hgai.core.inference` functions HQL/SHQL use — no duplicated reasoning logic anywhere, consistent with this whole plan's "one engine, many surfaces" throughline.

For UI, the query editors (HQL/SHQL) are already free-form YAML/text inputs — `infer: true` needs no new widget, only discoverability. Two new example queries were added to each editor's existing example-browser panel (already a proven, low-risk way this app teaches its own query syntax) rather than building new UI chrome. Visualize's rendering of inferred edges was explicitly left out of scope for this step — flagged clearly rather than silently skipped, since it's a distinct, larger feature (new data-fetching path into an already-complex 3D rendering pipeline) that doesn't fit naturally alongside the query-surface work that makes up the rest of Step 5.

Every piece was verified live: SHQL's `expand_edge_closure` integration confirmed against the same `rel:parent`/`rel:father` superproperty-projection scenario used in Step 3 (correct `_inferred`/`_source_edge`/`_axiom` bound to `?e` and selectable via dot-path); SHQL's `check_transitive` integration confirmed against the same `warehouse`/`section-a`/`pallet-1` chain from Step 4 (correct 2-hop path, and confirmed absent without `infer: true`); both MCP tools invoked directly (not just confirmed registered) and their output cross-checked against the equivalent REST calls; both REST routes exercised via curl including the `mode="bool"` validation-error path; and the new HQL example was clicked through in an actual browser session, confirming it populates the editor and executes cleanly end-to-end.

## Key Decisions
- **SHQL's inference block reuses `bound_node_ids`** (already computed for query narrowing) to detect a fully-resolved 2-member pattern, rather than adding new pattern syntax or a second traversal of `member_patterns` — smaller diff, one less thing to keep in sync with the existing narrowing logic.
- **No new reasoning logic in MCP or REST** — both are pure delegation to Steps 2–4's already-tested functions, which is why they needed no new unit tests of their own; verification here means confirming the wiring (registration, request/response shape, error handling), not re-verifying the algorithms.
- **UI scope deliberately limited to discoverability** (example queries) **not Visualize rendering** — an explicit, stated trade-off rather than a silent omission, matching the plan's own "lowest priority, do last" framing for this piece specifically.
- Full test suite: 72 passed (unchanged — no new unit tests this step, all verification was live/integration-style given the DB- and network-dependent nature of what shipped), same 3 pre-existing unrelated `test_mesh.py` failures.
