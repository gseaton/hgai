# Mutation Summary

## Intent
Direct follow-on to the prior turn's SHQL fix: having agreed that §6.2 needed explicit result-shape and attribute-access semantics plus a worked example, the user asked for the same treatment on §6.1 (HQL) — the sibling query language in the same §6 Query Layer section of `build-plan.md`.

## Context
- HQL and SHQL are deliberately different tools in this system: HQL is fast, single-collection, filter-style retrieval; SHQL is SPARQL-style multi-hop pattern matching with joins. The fix therefore isn't a copy-paste of the SHQL addition — it's the *analogous* clarification for a language with different semantics. Where SHQL needed "any bound `?var`, any hop, is attribute-addressable," HQL's honest analogue is the opposite: attribute access is scoped to the single matched document only, and the plan needed to say so explicitly so an implementing agent doesn't either (a) silently under-scope HQL by leaving this ambiguous, or (b) over-scope it by adding cross-document joins that duplicate what SHQL already owns (Phase 5 and Phase 6 are separate agent sessions with no shared memory — an explicit non-goal here prevents accidental scope duplication between them).
- This session's own prior research (an Explore-agent audit of the reference `hgai` codebase) had already identified two concrete, relevant facts reused here: (1) HQL genuinely cannot join edge members to their node documents and never could in the reference implementation — a deliberate, not accidental, boundary; and (2) a real bug where `where: {id: {$in: [...]}}` against hypernodes silently matched nothing (unrecognized `where` keys fell through to an `attributes.<key>` filter instead of raising). Both were folded into the §6.1 rewrite: the first as a stated design boundary to preserve, the second as a capability to explicitly build correctly (multi-id lookup via the Filter IR's `In`) plus a testing note flagging why it needs a dedicated test (it failed silently before, not loudly).

## What Changed and Why
Rewrote §6.1 in place, immediately after the existing field-list paragraph, adding: a result-shape paragraph (flat list of same-kind documents, contrasted explicitly with SHQL's binding-table shape from §6.2); an attribute-access-boundary paragraph (same-document-only, with an explicit instruction not to add cross-document joins to HQL since that's SHQL's job); a multi-id lookup paragraph documenting the `In`-compiled bulk-fetch capability and why it needs a dedicated regression test; and three worked YAML examples (filtered projection, bulk-id hydration explicitly framed as "the HQL-side half" of a common HQL+SHQL combined pattern, and PIT+aggregate) — the same "small number of pinned canonical examples" density used for §6.2, per the document's own token-efficiency goal.

## Key Decisions
- Did not make HQL support joins/member-hydration to close the gap with SHQL — kept the two languages' capability boundary exactly as it was in the reference implementation, and stated it as deliberate rather than leaving an implementing agent to guess whether the missing join support in HQL was an oversight to fix or a boundary to respect.
- Framed the bulk-id example explicitly as pairing with SHQL/a prior query ("the HQL-side half of...") rather than as a standalone feature, to reinforce the two-language division of labor established in the boundary paragraph immediately above it.
