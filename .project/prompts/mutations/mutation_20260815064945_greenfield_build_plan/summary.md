# Mutation Summary

## Intent
The user wants to rebuild `hgai` (HypergraphAI) as a "better and more polished" system, from an empty greenfield project folder, using the same or similar technologies with recommended improvements. The deliverable is not code — it's a planning document written specifically so an AI coding agent (Claude Code, or another agent like Cursor/Codex) can execute the rebuild autonomously, in ordered steps, with no other context available (the target project folder is empty and won't have access back to this repo).

## Context
- The current `hgai` project is a mature, mostly-functional Python/FastAPI/MongoDB semantic hypergraph platform: hyperedges as first-class N-ary relationships, two query languages (HQL, SHQL), MCP server, mesh federation, RBAC/multi-tenancy via Spaces, a working vanilla-JS SPA and a prompt_toolkit shell.
- Existing project memory already documented that the inferencing engine (`hgai/core/inference.py`) is dead code with zero call sites, and that HQL/SHQL had several fixed and unfixed quirks (YAML `?var` quoting, member-anchor resolution, `$or` pass-through inconsistency between node/edge queries).
- To write an accurate, non-speculative plan, a live audit was performed this session: read `pyproject.toml`/`requirements.txt`, all `docs/design/` and `docs/dev_notes/` files (including a design-tenets doc, an unwired SKOS/OWL inferencing spec, and a GPT-authored "AI-native knowledge store" essay used as inspiration for new capabilities), and dispatched an Explore subagent to survey the entire codebase module-by-module (core package, storage abstraction, HQL/SHQL engines, mesh, MCP, UI, shell, tests, deployment config).
- That audit surfaced concrete defects not previously in memory: MongoDB query syntax leaking through the "backend-agnostic" storage abstraction into the query engines; a `Dockerfile` that never copies most of the local sub-packages into the image (broken deploy path); a `pyproject.toml` package-include list missing two modules; duplicated CRUD route trees for space-scoped vs. unowned graphs; hardcoded default admin credentials; zero test coverage on REST/auth/MCP; SHQL tools missing entirely from the MCP server; and a documented `HgaiModule` base class that doesn't exist in code. These became the basis for a dedicated "lessons from the reference implementation" table in the plan, so the rebuild doesn't reproduce them.
- Two project rule files (`capture_all_mutating_prompts.md`) mandate this three-file capture (`prompt.md`/`mutation.md`/`summary.md`) after any file-mutating session, hence this capture.

## What Changed and Why
One new file was created: `docs/design/epcis-to-build-production-hgai/build-plan.md`. No other files were modified — this was a pure documentation-generation task with no code changes to the existing `hgai` project itself.

The document was structured to serve an LLM-agent audience end-to-end:
- **Meta-instructions first** (§0) so a consuming agent knows the document's execution order and how binding each section is (schemas are binding, prose is context).
- **A defect/lessons table** (§2) instead of narrative prose — it's the single highest-value section for review purposes and is written as an explicit "don't repeat this" checklist tied to the audit findings.
- **A technology decision table** (§3) with exactly one recommendation per row (no menus of options) — greenfield agents need unambiguous choices, not a survey of alternatives, so each row states the v1 tech, the v2 tech, and the one-line reason, with no hedging.
- **Compact schemas/interfaces instead of full code** throughout, to hold to the "reduce token count without sacrificing clarity" requirement — tables and short dataclass/Protocol sketches carry the same information as prose at a fraction of the tokens.
- **An ordered, phase-by-phase build plan** (§14, Phase 0–12) as the actual "multiple steps" the user asked for, each phase scoped to one vertical concern with explicit exit criteria so an agent can self-verify before proceeding, rather than attempting the whole system in one pass.
- **An explicit deferred/non-goals section** (§15) to keep the greenfield v1 scope bounded — several ideas from the "AI-native knowledge store" inspiration essay (policy-bound access, provenance signing, learned retrieval ranking, a message-bus event system) were deliberately excluded from v1 with a one-line reason each, rather than either silently dropping them or bloating the initial build.

## Key Decisions
- **Kept MongoDB as the primary store** rather than proposing a graph database or Postgres — the flexible-attribute document model already fits hypernodes/hyperedges well, and the product requirement was "same or similar technologies," not a storage-paradigm change.
- **Added exactly one new backend service (Qdrant)** for vector/semantic search rather than a full polyglot stack (separate lexical engine, separate graph engine) as the inspiration essay sketched — chose to ship MongoDB text indexes for lexical search first and defer a dedicated lexical engine, to avoid over-building speculative infrastructure ahead of proven need.
- **Introduced a Filter IR** as the concrete fix for the most structurally important defect found (query engines leaking MongoDB syntax past the storage abstraction) — this was called out as defect #1 and threaded through §6.3, §7, and the Phase 1/5/6 exit criteria, since it's also what would make a second storage backend possible later without touching HQL/SHQL.
- **Resurrected rather than redesigned** the inferencing engine and the mesh federation engine — both had solid prior designs (the SKOS/OWL axiom vocabulary in `docs/dev_notes/skhg-inferencing-notes.md`, and a mesh engine confirmed fully implemented and correct except for its test doubles) that just needed to be wired up correctly and tested properly, not reinvented.
- **Named a 3-tier Organization → Space → Hypergraph tenancy model** as new in v2, pulling directly from an unexecuted prior design prompt (`docs/design/prompt-gen-plan-orgs.md`) found during the audit rather than inventing a new tenancy scheme.
- Chose TypeScript + Vite + Preact + Tailwind for the UI rebuild instead of a heavier framework (React+Redux, Angular) or staying with a no-build vanilla JS approach — this keeps the "SPA talking to REST/MCP" shape of the original UI (rated functionally solid in the audit) while adding type safety, judged as the right weight for a project of this size.
