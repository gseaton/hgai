# Mutation Summary

## Intent
The previous mutation had folded only two of `sparql-vs-shql-gaps.md`'s three Tier 1 "build now" items (`VALUES` and `SUM`/`AVG`/`MIN`/`MAX`) into the conversion plan, per that turn's explicit, narrower request. The user then asked for a full review of the plan against the gaps document's findings — an audit request, not a narrow addition — which surfaced that the plan was inconsistent with itself and with the gaps document in several concrete ways, not just incomplete.

## Context
Both documents live in `docs/architecture/` and are meant to be read together: the plan is the "what to build," the gaps document is the "why, and in what order" behind several of the plan's scope decisions. Reviewing one against the other required reading both in full and checking every specific claim in the plan (what's in scope, what's approximated, what's rejected, and why) against the gaps document's five-tier prioritization, rather than skimming for an overall impression.

## What Changed and Why
Six concrete inconsistencies were found and fixed, all following the same pattern: the plan's §2 comparison table had, in the prior mutation, already been edited to *describe* something as supported (the `BIND` row explicitly says "Supported when...") without the corresponding §5 phase actually being built to match — an artifact of that prior edit being scoped only to `VALUES`/aggregates while accidentally touching the `BIND` row's wording too. This review completed that alignment rather than reverting it, since gaps.md's Tier 1 independently and explicitly recommends output-only `BIND` at the same priority as `VALUES` and the aggregates — finishing the job was more correct than undoing half of it.

The same completeness gap existed for Tier 2 (`ASK`, `^p`, fixed-length path chains — recommended "build" and "build if time allows" respectively, but absent from every phase) and Tier 3 (`FILTER EXISTS`/`NOT EXISTS` and `MINUS` — recommended as documented approximations, but the plan's Phase 3 and Phase 5 both described them as flatly rejected, with Phase 5 even using "quietly drops a `MINUS` clause" as its example of what *not* to do, directly contradicting Phase 3 once `MINUS` became approximated). Each of these was closed by adding the specific phase content gaps.md's own "What this means for the phased plan" section had already prescribed — Phase 2.5 for the property-path special cases, Phase 4 for `ASK` and output-only `BIND` (grouped with the aggregates since they share the same "plain SHQL `SELECT`, computed over client-side" strategy and the same 2,000-candidate-per-pattern cap caveat), and Phase 3 for the `EXISTS`/`MINUS` approximations.

Phase 5's rejection layer was also generic where gaps.md had explicitly asked for it not to be: "written into the transpiler's rejection layer from day one with the specific reasoning above (not a generic 'unsupported')." The fix threads that reasoning directly into Phase 5's own text — pointing a user who hits `SERVICE` at mesh dot-notation, a user who hits `CONSTRUCT`/`DESCRIBE` at the equivalent native HGAI mechanism, and so on — rather than leaving it as a cross-reference the reader has to go chase down separately.

Finally, §6's recommendation paragraph conflated "requires an SHQL engine change" (Tier 4's actual reasoning) with "carries real translation-fidelity limits even when approximated" (Tier 3's actual reasoning) into one imprecise sentence grouping `MINUS` alongside genuinely-out-of-scope items. This was split back into the tier structure gaps.md actually uses, since the distinction is the entire point of gaps.md having three different verdicts (approximate, defer, refuse) rather than one binary in/out line.

## Key Decisions
- Treated this as a full rewrite of the affected sections rather than a series of small patches, since the inconsistencies were interconnected (fixing Phase 3's `MINUS` handling required also fixing Phase 5's example, which required also fixing §6's summary of what Phase 5 rejects) — patching them independently risked leaving a different, smaller inconsistency behind.
- Kept the §2 table's Tier 4/5 rows themselves largely unchanged (their existing "no direct equivalent" framing was already accurate) rather than duplicating each row's full non-goal reasoning inline — that reasoning now lives once, in Phase 5, with the table rows pointing there via "(§5, Phase 5)" references, avoiding the table becoming unreadably long.
- Updated `sparql-vs-shql-gaps.md`'s own cross-reference note rather than leaving it describing only the Tier 1 fold-in, since a reader following that note after this review would otherwise be told a smaller, now-stale version of what actually changed.
