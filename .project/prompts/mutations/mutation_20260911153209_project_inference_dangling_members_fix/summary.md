# Mutation Summary

## Intent
The user reported that visualizing a hypergraph populated via "Project Inference" showed only bare spheres (henodes) with no link lines connecting them — the graph looked broken/disconnected, unlike a normal hyperedge's rendering (henode → "hyperedge" link → members-node → per-member "relation" links).

## Context
`project_inference` (built earlier this session) materializes inference results by creating new hyperedge documents in a target hypergraph, copying each candidate's `members` list (a list of `{node_id, seq}` pairs) verbatim from the source computation. When the target graph is the *same* graph as the source(s) — the common case exercised by prior verification — this works fine, because the referenced hypernodes already exist there. But when projecting into a genuinely new/different target graph (e.g. via "New hypergraph" in the Project Inference UI, or `create_target: true` against a fresh graph id), only the *edge* gets written — the hypernodes it references as members were never copied into that target graph, so they don't exist there at all.

The Visualize screen's `renderViz()` (`ui/js/app.js`) already has a defensive guard for exactly this situation: a hyperedge's members-node and relation-links are only built if at least one member resolves to a real node in the graph being rendered (`if (!validMembers.length) return;` in Pass B) — but the henode itself is always created unconditionally in Pass A specifically so a first-class hyperedge is never silently hidden. The combination — henode always drawn, but every member dangling — produces exactly the reported symptom: a lone sphere with no lines. This wasn't a Visualize bug; Visualize was correctly reflecting genuinely inconsistent stored data. Nothing in `create_hyperedge` (or the REST API generally) validates that a hyperedge's member ids correspond to real hypernodes — that's an existing, intentional looseness at the storage layer (a hand-authored edge with a typo'd member id behaves the same way) — but `project_inference`'s own docstring commits to a stronger guarantee: a materialized edge should be "indistinguishable at the storage/query level from anything hand-asserted." A hand-asserted edge's members are, in ordinary use, real nodes that exist; a materialized edge whose members exist nowhere in the target graph breaks that promise.

## What Changed and Why
Added `_ensure_member_exists()` inside `project_inference`, called for every member of a candidate right before it's written. For each member id: if it already exists as a hypernode (or hyperedge) in the target graph, nothing happens. Otherwise, the function searches the source graph(s) for a hypernode with that id and, if found, copies it (id, label, type, description, valid_from/valid_to) into the target graph via the ordinary `create_hypernode` path — so the copy gets its own proper audit trail, hyperkey-equivalent identity, and mutation history, exactly like any other hypernode creation. Results are cached per node id within a single `project_inference` call, since many candidates typically share members (e.g. every fact about the same person).

This only runs on the real-write path — `dry_run` still returns a preview without creating or copying anything, per its existing documented contract.

## Key Decisions
- **Copy hypernodes lazily, only for the members actually about to be written** — not upfront for every candidate — so a `dry_run` preview or a `skip`ped (duplicate) candidate never triggers a node copy, keeping the "dry_run writes nothing" and "skip means nothing happens" guarantees intact.
- **Only hypernode-shaped members are copied; a member that's itself a hyperedge and not found in the target is left dangling.** Recursively materializing an entire referenced hyperedge (with its own members, possibly nested further) is a much larger feature than this fix's scope — the henode-as-member case is rare, and Visualize's existing dangling-reference guard already handles it gracefully (it just omits the relation-link for that one member, rather than breaking the whole edge).
- **This is a fix in `hgai/core/inference.py`, not `ui/js/app.js`** — the root cause was the target graph having genuinely incomplete data (missing hypernodes), not a rendering defect. Fixing the data producer ensures every other consumer (HQL member-lookups, exports, future features) is correct too, not just Visualize.

## Live Verification Performed
Started an isolated test server (`HGAI_MONGO_DB=hgai_viz_projfix HGAI_PORT=8399`). Seeded a source graph `projsrc` with the same `rel:parent`/`rel:father`/`skos:narrowerTransitive` axiom + 3-member `rel:father` fact fixture used in prior inferencing verifications. Called `POST /graphs/projtarget/infer/project` with `source_graph_ids: ["projsrc"]`, `mode: "expand"`, `create_target: true` — creating a brand-new `projtarget` graph that had never seen any of `projsrc`'s hypernodes.

Confirmed via REST: `projtarget` ended up with exactly the 3 referenced hypernodes (`person:adam`, `person:cain`, `person:abel`) copied in, plus the 1 materialized `rel:parent` edge. Re-running the same projection request correctly reported it as `skip` (idempotent), with no duplicate node copies. In the browser, selecting only `projtarget` in Visualize and rendering showed the full expected structure — henode → "flavor:hub" link → members-node → three `rel:parent` relation-links (first member in blue, others in orange) — matching a normal, non-projected hyperedge's rendering exactly, with no dangling/lineless spheres.

Test server killed and `hgai_viz_projfix` database dropped afterward.
