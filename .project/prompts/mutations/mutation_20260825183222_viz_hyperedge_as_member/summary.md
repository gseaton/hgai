# Mutation Summary

## Intent
The previous turn's investigation (a read-only ask, no code changed) established that while the design docs explicitly state "hyperedges are treated as hypernodes" and nothing at the storage/API layer blocks storing a hyperedge's id as a member of another hyperedge, the 3D visualization actively broke that promise: it built its set of "resolvable member ids" from hypernodes only, silently dropping any member whose `node_id` pointed at a hyperedge instead — and if *all* of a hyperedge's members were other hyperedges, the hyperedge itself never even appeared in the graph. This turn fixes that specific, concretely-identified gap.

## Context
`renderViz()` (`ui/js/app.js`) builds two disjoint id spaces for the visualization's node objects: hypernodes become `kind: 'hnode'` nodes with viz-graph id `${gid}::${rawId}`, and each hyperedge becomes its own `kind: 'henode'` identity node with viz-graph id `${gid}::he::${rawId}` (plus a synthetic "members" node fanning out to each actual member). The bug wasn't just "hyperedge members get filtered out" — even if that filter were simply removed, the link-target construction (`target: \`${gid}::${m.node_id}\`\`) unconditionally assumed the hnode id scheme, so a member link pointing at a hyperedge would have pointed at a viz-graph id that was never created as any node — data 3d-force-graph would either reject or silently drop. Both halves (validity-checking, id-scheme construction) needed fixing together.

## What Changed and Why
- **Two id sets instead of one**, built in a first pass over the graph's hypernodes and hyperedges before any member-resolution happens, specifically so a hyperedge that's defined *after* the hyperedge that references it (arbitrary API ordering, no guaranteed sort) is still known to be a valid target — resolution never depends on processing order.
- **`vizMemberTargetId()` centralizes "what viz-graph id does this member's raw id actually correspond to"** — a member is now valid if it matches *either* set, and the function returns the correctly-scoped id (`${gid}::${id}` vs `${gid}::he::${id}`) rather than the caller having to remember which scheme applies. This is the piece that makes a hyperedge-typed member link somewhere real, not just "not filtered out."
- **A hyperedge's own `henode` is now unconditionally created**, moved out from behind the `if (!validMembers.length) return` early-exit that used to skip the entire hyperedge (identity node included) when it had no resolvable hypernode members. This was necessary, not optional politeness: without it, a hyperedge whose only members are other hyperedges would still never appear, and any *other* hyperedge referencing it as a member would produce a dangling link to a node that was never added to the graph. The "members" virtual node, its flavor-link, and the per-member relation-links are still skipped when there are genuinely zero resolvable members — there's nothing to hang off an empty members branch — but the hyperedge's own presence in the graph, and its correct participation as someone else's member, no longer depends on that.
- **`hyperedgeCount` now increments for every hyperedge, not just ones with resolvable hypernode members** — since every hyperedge now gets a node in the graph, the "N hypernodes · M hyperedges" stat line stays an accurate count of what's actually rendered.

## Key Decisions
- Considered leaving the early-return in place and only fixing member *resolution* (so a hyperedge referencing another hyperedge would work, but a hyperedge with zero valid members of any kind would still be invisible) — rejected, because that leaves exactly the dangling-link failure mode described above for the specific new case this fix exists to support: a hyperedge whose members are *entirely* other hyperedges.
- Did not add any backend/API-level validation restricting or type-checking `EdgeMember.node_id` — the investigation in the previous turn already established the storage layer doesn't block this, and the design docs treat that as intentional (hyperedges as first-class, hypernode-like elements). This turn's fix is scoped to making the *consumer* (the 3D visualization) correctly honor data that was already legal to store, not to adding new constraints.

## Verification
Live end-to-end verification via a hand-rolled CDP script against a restarted dev server (picked up the code change — the dev server had stopped between turns and was restarted) and a fresh headless Chrome instance (no browser extension connected in this environment), using real hypergraph data already present (`edge:classic-stooges`, `edge:rat-pack-core`, `person:moe`). Created a test hyperedge with a *mixed* member list — one hyperedge (`edge:classic-stooges`) and one hypernode (`person:moe`) — and confirmed via `State.viz3d.graphData()`: the new hyperedge's own node exists with `arity: 2` (both members correctly resolved, where the old code would have reported `arity: 1` and silently dropped the hyperedge member); a link exists from its members-node to `edge:classic-stooges`'s henode; a link exists from its members-node to `person:moe`'s hnode (regression check — normal hypernode members still resolve correctly). Created a second test hyperedge whose *only* member is another hyperedge (`edge:rat-pack-core`, zero hypernode members) and confirmed it still appears in the graph with `arity: 1` and a correctly-resolved link to that hyperedge — under the old code this hyperedge would never have been added to the graph at all. Confirmed the `viz-stats` display counted all real hyperedges correctly. Cleaned up both test hyperedges afterward. Full `pytest` suite: 45 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes. Left the dev server running afterward and killed only the headless Chrome test instance. `git status --short` shows only `ui/js/app.js` as this turn's change.
