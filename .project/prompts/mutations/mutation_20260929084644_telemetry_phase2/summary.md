# Mutation Summary

## Intent
Implement Phase 2 ("SHQL + errors") of docs/architect/telemetry-20260929061557.md: instrument `execute_shql` (the single chokepoint every SHQL caller already goes through) and add REST-layer error fingerprinting via FastAPI exception handlers.

## Context
Phase 1 shipped the telemetry foundation (queue, exporter, REST usage-event middleware). This phase adds the plan's §7 error-reporting design and the SHQL row of its §4 instrumentation table.

## What Changed and Why
`execute_shql` is wrapped, not modified internally: its existing body was renamed `_execute_shql_impl` and a thin new `execute_shql` times the call and emits one `usage` or one `error` event before returning/re-raising the real result/exception unchanged — verified directly by tests that patch a broken `emit()` and assert the real return value/exception still comes through. The usage event's attributes lean on `SHQLResult.meta` fields already built by this session's earlier aggregation/paging work (`aggregate_pushdown`, `paging_pushdown`, `truncated`, `cached`, federation), plus a second, disposable parse of the query text purely to extract pattern kinds and whether an aggregate was requested (kept isolated from the real execution path). REST error reporting is two new `app.exception_handler` registrations that call `rest_errors.report` and then return exactly what FastAPI/Starlette would have returned anyway (delegating to the real default handlers rather than reimplementing them), so response bodies and status codes are provably unchanged — asserted in tests, not just claimed. Fingerprinting groups by exception type, the innermost repo-only stack frame, and a message *template* with quoted segments redacted, so the same underlying bug against different customers' data (the plan's own worked example: a "Hypergraph not found: '...'" error) fingerprints identically instead of flooding one "unique" error per graph name.

## Key Decisions
- **401 is excluded from error reporting** (documented in `rest_errors.py`), the one deliberate departure from the plan's literal wording ("`app.exception_handler(Exception)` and one for `HTTPException`" with no stated carve-out): an expired or missing token is routine, extremely high-volume traffic, not a bug to triage, and fingerprinting every one would bury genuine errors in noise — exactly the outcome the plan's own §8 says error reporting exists to avoid. 403 and everything else are still reported, matching the plan's own 404 fingerprinting example.
- **SHQL errors that reach REST produce two error events** (one `surface: "shql"` from `execute_shql`'s own boundary, one `surface: "rest"` from the exception handler, once the SHQL router converts the exception to an `HTTPException`) — accepted as intentional, documented duplication rather than engineered away, since the plan explicitly wants the SHQL-layer report to be "distinct from a generic REST 500" and de-duplicating across layers would need passing an already-reported flag through call boundaries that don't otherwise need to know about each other.
- **Message templating is a generic regex** (strip quoted segments) rather than every raise site passing an explicit template — the plan names this as the pragmatic alternative to a wider sweep of call sites, and it covers the `{value!r}` shape the plan's own example uses.
- **Fingerprinting frame is the innermost repo frame**, not the plan's literally-read "first" frame — interpreted this way because the outermost frame is always the same chokepoint (`execute_shql`) for every SHQL bug, which would make fingerprinting useless for telling different bugs apart; documented as an explicit interpretation in `errors.py`, not a silent choice.
- **`duration_ms` on REST error events comes from a timestamp the middleware stashes on `scope["state"]`** at request start, so exception handlers (which run deeper in the stack, with no timer of their own) report a real elapsed time rather than a placeholder 0.
