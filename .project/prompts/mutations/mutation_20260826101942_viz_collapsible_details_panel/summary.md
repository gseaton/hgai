# Mutation Summary

## Intent
The Visualize screen's "Element Details" panel occupied a fixed 25% of the row's width (`col-md-3`) at all times, whether or not it had anything useful showing (its default state is just a "click something to inspect it" placeholder) — permanently costing the 3D canvas a quarter of its horizontal space. The user wanted to collapse it away when not needed, giving that space back to the visualization.

## Context
The layout is a two-column Bootstrap row: the 3D canvas (previously `col-md-9`, a fixed 75%) and the details panel (`col-md-3`, a fixed 25%). Making the panel collapsible meant the canvas column could no longer be a fixed fraction either — it needed to be flexible, growing to absorb whatever width the details panel gives up when collapsed.

## What Changed and Why
- **The canvas column became a flexible `.col` instead of a fixed `col-md-9`.** Bootstrap's `.col` (flex-grow: 1, flex-basis: 0%) fills whatever space its siblings don't claim — exactly the behavior needed for the canvas to expand when the details panel shrinks, without JavaScript having to compute or set explicit widths itself.
- **The details panel collapses to a narrow 48px strip, not `d-none`.** A fully-hidden panel would need a separate floating "reopen" affordance drawn somewhere over the canvas to bring it back; leaving a slim, always-visible strip with just the toggle button (chevron flipped to point the other way) keeps the reopen control in a predictable, permanent location and reads as a standard collapsible-sidebar pattern.
- **A `setTimeout(vizResizeCanvas, 160)` follows every toggle**, timed to run after the CSS width transition finishes. `vizResizeCanvas()` reads the wrapper's current pixel size and calls `.width()/.height()` on the 3d-force-graph instance — without this, the underlying `<canvas>` element (which has explicit pixel dimensions, not CSS-relative ones) would keep rendering at its old size inside the newly-resized wrapper, leaving letterboxing until the next unrelated window resize happened to trigger a redraw.
- **Real bug found and fixed along the way, not part of the original ask but necessary for it to work at all:** switching the canvas column from a fixed `col-md-9` to a flexible `.col` exposed a genuine pre-existing flexbox pitfall. A flex item's "automatic minimum size" (the floor the browser won't shrink it below, even with `flex-basis: 0%`) defaults to its *content's* min-content size unless told otherwise — and the 3D canvas element inside this column gets an explicit large pixel width set directly by 3d-force-graph's renderer (not CSS), which is exactly the kind of strong intrinsic size that inflates a flex item's automatic minimum. That pushed the canvas column's effective minimum size past what was actually available once the details column claimed its own width, causing the row to wrap onto two lines instead of laying out side by side — with the row's own fixed inline height then making that wrap render as the two columns overlapping at the same position instead of visibly stacking. Adding `min-width: 0` to the canvas column is the standard, well-established fix for this exact class of flexbox bug (reset the automatic minimum so the item's actual size is governed by the flex distribution, not its content).

## Key Decisions
- Did not persist the collapsed/expanded state (e.g. via `localStorage`) — this is a lightweight session-level UI preference, consistent with how the Visualize screen's other toggles (`vizLabelsEnabled`, `vizMediaEnabled`) already work as plain in-memory state that resets on page reload, and persistence wasn't requested.
- Fixed the flexbox min-width bug in place rather than reverting to a fixed-width canvas column and trying some other approach to "grow" it — `min-width: 0` is a one-line, well-understood, standard fix for exactly this situation, and reverting to fixed widths would have brought back needing to compute exact pixel widths in JavaScript for both the expanded and collapsed states, which the flexible `.col` approach avoids entirely once its minimum-size floor is reset correctly.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the already-running dev server (frontend-only change, no restart needed) and a freshly-created headless Chrome profile (established practice this session). The min-width bug was caught *during* this same verification pass — an initial check showed the canvas column's measured width staying frozen at 1213px both before and after collapsing the details panel, which further investigation (edge-position measurements, then a live `element.style.minWidth = '0'` test) traced to the wrap/overlap behavior described above and confirmed the fix before committing it to the actual files. With the fix applied: measured the canvas wrapper's width before collapsing (892px), after collapsing (1147px — a 255px gain, matching the details column's own shrink from 303px to 48px almost exactly, net of the row's gutter), and after re-expanding (892px again, an exact return to the original). Confirmed the details column's collapsed-state CSS class, header/body visibility, and toggle icon all flip correctly in both directions, and that `State.viz3d.width()` tracked the wrapper's actual pixel width after each toggle (proving `vizResizeCanvas()` fired and the renderer actually redrew at the new size, not just the CSS layout changing). Full `pytest` suite: 45 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes. Left the dev server running afterward and killed only the headless Chrome test instance. `git status --short` shows `ui/index.html`, `ui/js/app.js`, and `ui/css/hgai.css` as this turn's changes.
