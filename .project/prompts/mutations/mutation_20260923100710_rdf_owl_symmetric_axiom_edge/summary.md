# Mutation Summary

## Intent
This is a follow-up revision to an earlier request (see `mutation_20260923095434_rdf_owl_symmetric`) that added `owl:SymmetricProperty` support to RDF import. That earlier version only emitted a `symmetric`-flavored data edge per triple using the symmetric predicate, with no axiom edge recording the predicate itself as symmetric. The user revised the request to ask for a second hyperedge — a `hub`-flavored axiom edge with `relation="owl:symmetric"` and the predicate as its single member — bringing `owl:SymmetricProperty` to parity with how `owl:TransitiveProperty` and `owl:inverseOf` were already handled (each of those already produces a `hub`-flavored axiom edge that the inference engine's `infer: true` recognizes).

## Context
HypergraphAI's inference engine (`hgai/core/inference.py`) recognizes axioms as ordinary hyperedges asserting a fixed control-vocabulary `relation` string against relation-hypernodes — never hardcoded per-domain-relation. Without an `owl:symmetric` axiom edge, a symmetric predicate's *own* symmetric nature was only implicit in how its data edges were flavored; it could not be looked up, queried, or fed into `infer: true`'s axiom-driven expansion the same way `owl:transitive` and `owl:inverse-of` axioms can. The project convention (established across the prior two segments of this session) requires: prefix-expanded full IRIs for all ids/relations except literal-attribute keys, unit tests, mutation-testing to confirm new tests actually catch a disabled feature, a full test suite run, live disposable-instance verification, doc updates, and a mutation record — all followed here.

## What Changed and Why
`hgai/core/rdf_import.py`'s entity-processing loop already tracked which predicates carry `owl:SymmetricProperty` (via a `symmetric_properties` set) to decide data-edge flavor. This revision reused that same detection to also emit one additional axiom edge per symmetric predicate: `{relation: "owl:symmetric", flavor: "hub", members: [{node_id: <predicate IRI>, seq: 0}]}`. This required widening the internal `edge_tuples` tuple shape to carry a per-edge `flavor` (previously all data edges were `hub` by default, with only the transitive/inverse-of axiom edges as separate `hub` cases) so the symmetric data edges (which need `flavor="symmetric"`) and the new axiom edge (which needs `flavor="hub"`) could share one emission/sort/build path.

Tests were updated to match: two tests whose old names and assertions described the deliberately-removed old behavior ("no separate axiom edge") were renamed and rewritten to assert the new behavior; a count-based test was updated for the extra edge; a composite coexistence test gained an explicit assertion on the new `owl:symmetric` axiom edge. This is an intentional behavior change per the user's revised request, not a regression.

Docs (`docs/help/notes/web-ui/export-import.md`, `docs/api-reference.md`) were updated because the RDF-to-hypergraph mapping tables in both had explicitly documented the old, now-superseded "no axiom edge" behavior, including a stale note that `owl:SymmetricProperty` was "not specially recognized" for inference — both were corrected to describe the new two-edge behavior and its `infer: true` support.

## Key Decisions
- Reused the existing `symmetric_properties` detection set rather than adding a second OWL-types pass, since the information needed (which predicate IRIs are `owl:SymmetricProperty`) was already being computed for data-edge flavoring.
- Widened `edge_tuples` to `(relation, flavor, member_ids, sort_key)` instead of adding a parallel special-case branch, since the codebase already had precedent for extra `hub`-flavored single/double-member axiom edges (`owl:transitive`, `owl:inverse-of`) and this kept all axiom-edge emission on one code path.
- Live-verified via `infer/expand` on a hand-asserted `hub`-flavored edge on the same relation (not just checking the axiom edge's shape) to confirm the new axiom edge is actually load-bearing for the inference engine, not just present in storage.
