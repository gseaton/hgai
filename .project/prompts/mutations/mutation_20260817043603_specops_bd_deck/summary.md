# Mutation Summary

## Intent
Directly following the earlier `demo-bus-dev-20260817` deck (a defense-industry BD briefing built around a contract-staffing example), the user asked for a near-identical deck package — same five required content threads, same audience type (BD/product managers at large U.S. defense professional-services/consulting firms) — but with the worked example reoriented around "supporting special operations and other forces in combat operations," in a new folder (`docs/decks/demo-spec-ops-20260817`).

## Context
- The five required content threads were unchanged from the prior request: core hypergraph concepts, hgai as a general (non-AI-specific) knowledge platform, hgai as AI context memory within and across sessions, MCP enabling agents to persist and query distilled knowledge (not just retrieve it), and one complete, simple, step-by-step example proving hgai's advantage over SQL and traditional semantic knowledge graphs — this time explicitly scoped to a special-operations/combat-support domain rather than contract staffing.
- Before drafting the concrete scenario, this session weighed how to responsibly interpret "combat operations" as a demo-content domain. The system's operating guidance draws a clear line between legitimate defense-sector business/technical content (which this clearly is — a data-platform capability briefing for professional-services firms, analogous in kind to the prior staffing-scenario deck and to how real defense-tech companies publicly market ISR fusion, logistics, and mission-support platforms) and content that provides operational guidance for lethal action (weapons targeting, fire-control coordination, strike planning), which this was not asked for and was deliberately kept out of scope. The concrete scenario was therefore built around casualty evacuation (MEDEVAC) coordination and multi-source ISR fusion for situational awareness — an unambiguously protective/life-saving mission-support function — rather than any fires/targeting theme, and this reasoning is stated explicitly in the presenter notes' opening section so the choice isn't left implicit or discoverable only by inference.
- Three concrete safeguards were built into the scenario itself, all stated plainly in the deck and/or presenter notes rather than left implicit: (1) the entire example is labeled a fictional training exercise ("Exercise Steel Compass"), with no real unit, operation, location, person, or aircraft represented; (2) the only military-doctrine structure referenced (the 9-line MEDEVAC request format) is unclassified and taught to every U.S. service member, so citing its field structure discloses nothing sensitive; (3) the AI-generated hyperedge in the example is explicitly and repeatedly framed as a recommendation for a human controller to weigh, never as an automated or autonomous action — this framing appears in the data file's own comment, the deck's narrative, and the presenter notes.
- Reused the prior deck's file structure and conventions (main deck + presenter-notes companion + `data/` + `queries/`, matching `docs/decks/demo-alpha`'s established layout) and its "live vs. roadmap" honesty convention (explicitly not repeating the existing investor deck's SKOS-inferencing overclaim, consistent with the reasoning already established and recorded in the prior deck's mutation summary).
- A real correctness issue was caught and fixed while authoring the SHQL query: this session's own established knowledge (from `hgai_shql_hql_engine_quirks` memory, reconfirmed against `demo-alpha`'s actual proven query files) is that SHQL member sub-patterns do NOT enforce a `type:` constraint at match time — only top-level `node:` patterns do. The MEDEVAC-request hyperedge has 5 members of mixed types (element, location, asset, 2 patients), so a naive query trying to wildcard-extract "the patients" by binding an unconstrained `{bind: "?patient", type: Person}` member sub-pattern directly would have been genuinely ambiguous against the other unfilled member slots. The query was instead written the way `demo-alpha`'s own proven q10 does it: bind each unknown independently via a top-level, type-checked `node:` pattern first, then use the hyperedge patterns purely as join constraints (every member slot either a literal `id:` or an already-bound `?var` anchor, zero wildcard slots) — this was caught and corrected before being shipped as a customer-facing demo artifact.

## What Changed and Why
Created a new, self-contained deck package at `docs/decks/demo-spec-ops-20260817/`, structurally parallel to the prior `demo-bus-dev-20260817` package but substantively rewritten (not copy-pasted) throughout:

- **The main deck** reframes every section's language and use-case examples around mission support (ISR/multi-INT fusion, logistics/sustainment, personnel recovery, mission planning, after-action review) in place of the prior deck's capture-management/staffing framing, and adds a dedicated "why edge deployment matters" angle (self-hosted, lightweight Docker footprint, disconnected/intermittent/limited-environment architecture fit) relevant specifically to a special-operations/tactical-edge audience that wasn't in the prior deck.
- **The worked example** was rebuilt from scratch around a 5-participant MEDEVAC-request hyperedge (element, location, asset, and — deliberately — two patients, to also demonstrate variable-arity N-ary membership, a step beyond the prior deck's fixed 3-member example), a precedence-upgrade point-in-time comparison, a multi-source ISR-confirmation hyperedge that itself references the MEDEVAC-request hyperedge as a member (reinforcing the "hyperedges are first-class, referenceable like hypernodes" tenet a second, more sophisticated time), and an AI-generated recommendation hyperedge carrying the same provenance/confidence/basis-edge-ids pattern as the prior deck's risk-assessment example.
- **The SQL and RDF comparison files** were deliberately designed to expose an even sharper pain point than the prior deck's: because a MEDEVAC request can have a variable number of patients, the SQL schema needs a second bridge table (and the ISR confirmation needs a third, for its variable number of corroborating sources) purely to hold what is a single hyperedge member list in hgai, and the RDF version needs multiple `demo:requestPatient` triples per reified resource plus a `GROUP_CONCAT` in every query that reads it back — both comparison query files were written to make this concretely visible rather than only asserted in prose.
- **Presenter notes** were expanded relative to the prior deck's with defense-mission-specific anticipated questions (classification/authorization status, DIL/edge-deployment claims, comparison to Palantir Gotham/Foundry and Anduril Lattice specifically, AI-write risk framed as "creating a false picture" rather than generic data quality) and, uniquely to this deck, an explicit opening section justifying the scenario choice itself — judged necessary because a presenter fielding "why isn't this about targeting/fires" needs a prepared, confident, non-defensive answer rather than having to improvise one live.

## Key Decisions
- **Chose MEDEVAC/ISR-fusion over any fires, targeting, or strike-coordination scenario** for the "combat operations" example — judged to be both the more responsible choice (protective/life-saving function, unclassified doctrinal grounding, unambiguous human-in-the-loop framing for the AI's output) and, independently, the stronger technical showcase (a genuinely 5-participant, variable-arity N-ary fact), so the safety-motivated choice and the best-demo choice were the same choice rather than a tradeoff between them.
- **Framed the entire scenario as a fictional training exercise** rather than as a live/notional real-world operation — a stronger disambiguation than the prior deck's "fictional example customer" framing, chosen because this domain's content (casualty status, ISR reporting, aircraft tasking) reads as more operationally sensitive in character than a staffing scenario even when fictional, so the extra explicitness was judged warranted.
- **Kept the AI-generated hyperedge strictly as decision support for a human controller**, stated redundantly across the data file, the deck, and the presenter notes rather than once — this repetition was deliberate: it's the single most important framing choice in the whole deck, and the presenter-notes Q&A entry on AI-write risk treats it as the answer to "can this system take autonomous action," which needed to be unambiguously "no" everywhere it could be read.
- **Fixed a genuine SHQL correctness risk** (member-pattern type-checking ambiguity on a 5-member hyperedge) by following `demo-alpha`'s own proven safe pattern (independent top-level bindings + pure join-constraint edge patterns) rather than shipping the more naive wildcard-extraction form that would have looked plausible but was not guaranteed correct against the real engine's documented behavior — consistent with this session's established practice of verifying demo artifacts against the actual, current system rather than the separate greenfield-rebuild spec's hypothetical syntax.
