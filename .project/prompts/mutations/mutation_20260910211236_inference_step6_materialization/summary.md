# Mutation Summary

## Intent
Continue the phased inferencing plan with Step 6, the last of the originally-numbered phases: "Project Inference" — an explicit, user-triggered operation that crosses the transient/persisted boundary this whole plan deliberately maintained everywhere else (Steps 2–5 compute inference results live, at read time, and never write anything). This was the feature the user asked for directly, mid-conversation, after confirming the rest of the plan was fully transient: a way to select source hypergraph(s), run inference, and persist the results into an existing or new target hypergraph.

## Context
The plan (developed in the original design conversation) specified this precisely: `project_inference` introduces zero new reasoning logic — it's a persistence wrapper around Steps 3–4's `expand_edge_closure`/`walk_closure`, writing through the ordinary `create_hyperedge` path so hyperkey dedup (built in this session's very first piece of work) and the `mutations` audit trail (built shortly after) apply automatically, with no special-casing needed. Two properties were called out as required, not optional: safe to re-run (idempotent against an unchanged source), and explicit that this is a snapshot, not a live sync (a materialized edge does not track its source after creation).

## What Changed and Why
`project_inference` implements both materialization modes the plan described. "Expand" mode reuses `HyperedgeSearchFilters` (the same multi-graph raw-dict search already used by HQL/SHQL) to gather source fact edges, then `expand_edge_closure` exactly as HQL/SHQL/MCP/REST already do for live queries. "Transitive" mode is new plumbing: rather than requiring a caller to name every start/end pair (as `check_transitive`'s query-facing modes do), it discovers every subject node across the relevant fact edges itself and walks the full closure from each — the natural shape for "materialize everything this transitive relation implies," as opposed to answering one reachability question at a time. Both modes funnel into one write loop: a `find_duplicate_hyperedge` pre-check (skip if already materialized) before every `create_hyperedge` call, with `attributes.provenance` recording exactly what produced the edge.

The REST route (`POST /graphs/{graph_id}/infer/project`) is deliberately the only *write* in the entire `/infer/*` surface — everything else added in Step 5 only reads. It adds one access-control nuance the read-only routes didn't need: since this operation pulls data *from* other graphs the caller specifies at request time (not fixed in the URL), each source graph's read access is checked explicitly with `can_access_graph`, in addition to the existing `require_graph_access("write")` dependency guarding the target — otherwise a user with write access to one graph could use this endpoint to exfiltrate facts from a graph they can't actually read.

Live verification exercised every property the plan required, not just the happy path: created a fresh target graph via `create_target: true` in the same call; ran `expand` mode (superproperty projection, matching Step 3's exact scenario) and `transitive` mode (the `warehouse`/`section-a`/`pallet-1` chain from Step 4) against the same target; confirmed each materialized edge carries correct `attributes.provenance` *and* automatically picked up a real `mutations: [{mutation: "create", ...}]` entry with no special-casing needed, exactly as the plan predicted, since materialization goes through the same `create_hyperedge` every hand-asserted fact does; re-ran both calls unchanged and confirmed `created: 0, skipped: 1` for each (idempotency); added a genuinely new fact to the source and re-ran, confirming exactly one new edge was created while the previously-materialized one was correctly skipped (the "delta only" property); and exercised both `400` validation paths (`mode="transitive"` without `relation`; an invalid `mode` value).

## Key Decisions
- **"Transitive" mode discovers its own start nodes** rather than requiring the caller to enumerate them — a deliberate divergence from `check_transitive`'s query-facing shape (which always takes an explicit `start_id`), because "materialize this relation's whole closure" is a fundamentally different request than "answer one reachability question," and forcing the caller to already know every subject node would defeat the point of a bulk materialization operation.
- **Source-graph read-access is checked explicitly in the router**, not left to `project_inference` itself — the engine function has no concept of an "account," by design (matching every other function in this module); access control belongs at the API boundary, and checking it there means the same engine function could later be called from a non-HTTP context (a script, a scheduled job) without dragging an auth dependency into it.
- **The UI screen was explicitly not attempted this step** — the engine and REST route are complete, tested, and independently usable (verified via curl above); the dedicated "Project Inference" screen is a distinct enough scope (new page, multi-select, preview-before-write flow) that attempting it in the same pass risked rushing it, so it's called out clearly as remaining work rather than silently dropped.
- Full test suite: 72 passed (unchanged — `project_inference` is DB-dependent and was verified live, matching this session's pattern for every DB-touching piece of the inference plan), same 3 pre-existing unrelated `test_mesh.py` failures.
