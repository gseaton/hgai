# Mutation Summary

## Intent
The earlier "SPARQL to SHQL Conversion Plan" (published as a Claude Docs artifact in this session) produced a full feature-by-feature comparison table listing roughly a dozen SPARQL capabilities SHQL has no equivalent for, but deliberately didn't rank them — it was scoped as an overview and phased implementation plan, not a prioritization. The user's follow-up asked the natural next question directly: given that list, which gaps actually matter, and should any of them be prioritized at all? Unlike the prior response (an ask-prompt, captured under `.project/prompts/asks/`), this request explicitly asked for the answer to be written to a specific file in the codebase (`docs/architecture/sparql-vs-shql-gaps.md`), making it a mutating prompt.

## Context
`docs/architecture/` already holds a couple of lightweight, frontmatter-free architecture notes (`hypergraph-3d-viz.md`, `hypergraph_ai_design_notes.md`) — unlike `docs/help/notes/`, which requires YAML frontmatter for the Help topic system, this folder is plain reference markdown, so the new file follows that lighter convention (a `#` title, no frontmatter). No code was read or touched beyond what the prior session's research had already established about `hgai_module_shql/engine.py` and `hgai/core/rdf_import.py`; one new fact was checked directly in the engine source for this document specifically — the internal `search(..., limit=2000)` cap behind `node:`/`edge:` pattern matching — since it materially affects the safety of the document's central strategic recommendation (client-side, transpiler-only aggregation).

## What Changed and Why
Created `docs/architecture/sparql-vs-shql-gaps.md`, structured around three explicit scoring axes (usage frequency, engineering cost *and where it lands*, and whether an adequate workaround already exists) rather than a single subjective "priority" label, so the reasoning behind each ranking is auditable rather than asserted. The document's key original contribution beyond the prior plan is the "push computation into the transpiler, not the engine" section: several gaps initially scoped in the prior plan as requiring `hgai_module_shql` engine changes (`SUM`/`AVG`/`MIN`/`MAX`, simple `BIND` cases, `ASK`, an approximate `MINUS`) can instead be implemented entirely inside the new transpiler module by fetching a broad result set from an ordinary SHQL `SELECT` and computing SPARQL semantics client-side — reclassifying them from expensive/risky (touches the shared query engine) to cheap/self-contained (isolated to new code). This reclassification is explicitly caveated: it depends on true match counts staying under SHQL's internal 2,000-candidate-per-pattern search cap, past which client-side aggregation would be silently incomplete rather than merely slow — a real limitation, not a footnote to omit.

The five resulting tiers (build now / build if cheap / approximate only / explicitly out of scope / import-time-not-query-time) each carry per-item reasoning rather than a bare list, including for the Tier 4 "won't build" items — the reasoning matters as much as the verdict there, since several of them (`CONSTRUCT`/`DESCRIBE`, `SERVICE`, SPARQL Update) aren't being deferred for cost reasons but rejected because HGAI already has a better-fitted native mechanism for the same underlying need (targeted node/edge queries, mesh dot-notation, the REST/CRUD/MCP write API), and building SPARQL-shaped access to those same needs would mean maintaining a worse, redundant path to something that already exists.

## Key Decisions
- Scored gaps on three independent axes instead of a single priority number, specifically so a cheap-but-rare gap (e.g. `ASK`) and an expensive-but-common gap (e.g. general property-path algebra) don't collapse into the same rank for different, opposite reasons.
- Treated "requires an SHQL engine change" and "requires an RDF-import change" as two genuinely different kinds of cost, not variations on the same axis, since they have different blast radii (the shared query engine every SHQL consumer depends on, versus the RDF import pipeline's own, separate data-preservation tradeoffs) and different natural owners for the decision.
- Explicitly separated "approximate and document the caveat" (Tier 3: `FILTER EXISTS`/`NOT EXISTS`, `MINUS`) from "build properly" and from "don't build at all" — a deliberate middle category, since silently shipping a subtly-wrong approximation without saying so would repeat the exact mistake the original plan's Phase 5 (rejection/diagnostics layer) was designed to prevent for outright-unsupported constructs.
- Justified each Tier 4 "explicitly out of scope" item with *why it's a non-goal*, not just *why it's expensive* — several of them are cheap in absolute terms but wrong to build regardless, because HGAI already solves the same underlying problem a different, better way (this is the document's most opinionated section, and deliberately so, since the user's question was "if at all," inviting exactly this kind of pushback on some items rather than a uniform roadmap).
