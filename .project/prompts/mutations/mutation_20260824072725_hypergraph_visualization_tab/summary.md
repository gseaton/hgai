# Mutation Summary

## Intent
The user wanted a way to visually explore hypergraph(s) from the existing HypergraphAI web UI, rather than only browsing hypernodes/hyperedges as flat tables. They suggested Cytoscape.js or a similar graph-visualization library, and wanted support for visualizing one or more selected hypergraphs at once.

## Context
The UI (`ui/index.html`, `ui/js/app.js`, `ui/js/api.js`, `ui/css/hgai.css`) is a vanilla-JS, Bootstrap 5 single-page app with no build step — screens are plain `<div class="screen">` blocks toggled via `showScreen()`, and each screen has a loader function registered in a `loaders` map. There's an existing pattern for graph-scoped screens (Hypernodes, Hyperedges) that populate a `<select>` of hypergraphs from `_fetchAndCacheGraphs()` and resolve space-scoped vs. global API calls via `graphSpaceId()`. The domain model (`hgai/models/hyperedge.py`) is a true n-ary hypergraph: a `Hyperedge` has a `flavor` (hub/symmetric/direct/transitive/inverse-transitive) and an ordered list of `EdgeMember` (node_id + seq), so an edge can connect any number of hypernodes, not just two.

## What Changed and Why
- **Library choice**: Added Cytoscape.js via CDN (`cytoscape@3.30.2`), consistent with how the app already pulls Bootstrap/CodeMirror from CDN rather than bundling. No build step was introduced.
- **New "Visualize" screen**: Added to the sidebar under the existing "Knowledge" section, alongside Hypergraphs/Hypernodes/Hyperedges, since it's another way of viewing the same graph data rather than an admin function.
- **Multi-graph support**: The hypergraph picker is a native `<select multiple>` (not a custom multi-select widget) to keep the change minimal and consistent with the plain-HTML-forms style used elsewhere in the app. Elements from each selected graph are namespaced by graph ID (`${graphId}::${nodeId}`) so multiple graphs can be rendered together without ID collisions.
- **Hyperedge rendering strategy**: Cytoscape only supports binary edges natively, but this app's hyperedges are n-ary. Rather than always expanding every hyperedge into a hub node (which makes ordinary binary relations look cluttered), the code special-cases arity:
  - Exactly 2 members → a normal Cytoscape edge between the two hypernodes, directed (arrowhead) only for `direct`/`transitive`/`inverse-transitive` flavors, undirected for `hub`/`symmetric`.
  - 1 or 3+ members → a diamond "hyperedge node" (star/hub topology) connected via plain spoke edges to each member, colored by flavor.
  This keeps the common case (binary relations) visually clean while still faithfully representing true hyperedges.
- **Node coloring**: Hypernode colors are derived deterministically from a hash of the node's `type` string against a fixed palette, so the same type always gets the same color across renders without needing a stored color-per-type table.
- **Interactivity**: Clicking any hypernode or hyperedge-node populates a right-hand "Element Details" panel with the raw JSON (reusing the same `attributes`/`tags`/etc. shape already shown elsewhere via `showDetail()`, but inline rather than in a modal so the graph stays visible). The legend is generated per-render from the types/flavors actually present, and each legend chip is clickable to dim/un-dim that node type. A live search box dims all non-matching nodes/edges without re-fetching data.
- **Fetch limits**: Each graph's nodes/edges are fetched with a page size of 500 (`VIZ_FETCH_LIMIT`); if the true total exceeds that, a warning toast tells the user the view is partial rather than silently truncating.

## Key Decisions
- **Binary-vs-hub rendering split** (see above) was chosen over always using hub nodes because most real hyperedges in this domain (e.g. `sibling`, `has-member` with exactly two members) read far better as plain lines; forcing every relation through a hub node would make simple graphs unnecessarily busy. The split is purely presentational — the underlying data model is untouched.
- **No new multi-select UI component**: considered a custom checkbox-dropdown for the hypergraph picker (nicer UX for many graphs) but chose the native `<select multiple>` to match the project's existing "plain HTML forms, no component library beyond Bootstrap" convention and avoid adding UI-kit complexity for a first version.
- **Verification**: Since no browser (Claude-in-Chrome) extension was available in this environment, the feature was verified end-to-end by standing up a local MongoDB + the hgai server and driving a headless Chrome instance directly via the Chrome DevTools Protocol (over the existing `websockets` Python package already vendored in `.venv`) — logging in, opening the Visualize tab, selecting the seeded `hello-world` graph, rendering, switching through all five layouts, exercising the legend toggle/search/label-toggle controls via the live Cytoscape API, and clicking both a hypernode and a hub node to confirm the details panel populates. No console errors were observed in any of these steps. This test infrastructure (mongod, the hgai server process, and headless Chrome) was torn down afterward and left no trace outside the session's scratchpad directory.
