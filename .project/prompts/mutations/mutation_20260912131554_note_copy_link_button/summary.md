# Mutation Summary

## Intent
The immediately preceding turn answered a question about note-link syntax (`ask_202609121311_note_link_syntax_by_label`) and surfaced a real usability gap in the process: hgai's internal note links resolve strictly by note `id`, not by the more memorable `label`, so writing one by hand requires looking up the target note's raw id first — something hgai had no UI shortcut for (unlike Quill, the project this whole Notes feature was modeled on, which has a "Copy embed link" button for exactly this reason). The assistant offered to add an equivalent "copy note link" helper; the user approved it with "yes, add that."

## Context
Quill's own implementation (`app/static/app.js:319-349`) wires "Copy identifier" and "Copy embed link" buttons in its note editor, both using whatever's currently in the Label field (not the last-saved label) for readability, falling back to the note's id if the label is empty. Quill's "embed link" specifically produces the *image*-syntax form (`![ref](note/ref)`), for embedding a note's content inline — not the plain hyperlink form the user actually needs here.

hgai's own note-link resolution (`renderNoteMarkdown()`, confirmed in the two prior sessions' turns on this feature) is strictly id-keyed: the rendering pipeline builds a `Map` of `id -> label` and looks up the captured link target directly against it, so only a real id resolves — a copy-to-clipboard helper is only useful if it embeds the real id, with the label purely as cosmetic link text.

## What Changed and Why
- **A plain hyperlink form (`[label](note:id)`), not Quill's embed form (`![label](note:id)`).** The gap this fixes is "I want to reference/link to another note by typing its name," not "I want to inline-embed that note's content" — hgai doesn't currently support note embedding at all (only media embedding, a separate mechanism), so mirroring Quill's embed-link button literally would generate markdown that renders as a broken or misinterpreted reference here, not a working feature.
- **`note:`, not `note/`, as the generated form** — both are equally valid and resolve identically as of the immediately preceding turn (`mutation_20260912124208_note_link_slash_syntax`), but `note:` is the original, more established form in this codebase (used in the section-header doc comment, the Content field's own inline hint text, and presumably any note content already written before slash support existed), so generating it keeps newly-copied links consistent with what's already out there rather than introducing a second "canonical" form with no real reason to prefer it.
- **Visible only for an existing (saved) note**, exactly like the Edit mode button and the note-history section — a new, unsaved note has no stable id yet, so there's nothing valid to copy until after a first save (confirmed the id field, `#note-form-id`, is empty for a new note per `openNoteModal(null)`'s existing branch).
- **Visible unconditionally for any existing note the current user can open** — unlike the Share button (owner-only, `noteIsOwner(n)` gate), copying a *reference* to a note doesn't require edit or share rights, only the ability to see it exists at all; if the modal opened successfully, the viewer already has that much access.
- **Uses the Label field's live (possibly unsaved) value**, matching Quill's own reasoning exactly (`app/static/app.js:325-329`, "a label just typed - but not yet saved - is picked up immediately"): the id is what actually makes the link resolve, so the label is free to reflect a just-typed rename without needing to save first — copying stays useful mid-edit, not just from Browse mode.

## Key Decisions
- Considered generating `note/<id>` instead, to steer new content toward the syntax that matches Quill's own convention (the reason slash support was added in the first place). Decided against it: nothing about slash is more "correct" now that both resolve identically, and defaulting new copies to the pre-existing, more prevalent form avoids splitting note content between two stylistically different-looking link forms for no functional benefit.
- Considered placing the button inside the Content field's toolbar (next to where a link would actually be typed) rather than the modal header. Placed it in the header instead, matching Quill's own placement choice and this modal's existing convention of putting note-level actions (Share, mode switches) at the top rather than embedded in a specific field's UI — the copied link's usefulness doesn't depend on which field is currently focused.
