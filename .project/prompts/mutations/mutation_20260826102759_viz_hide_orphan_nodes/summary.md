# Mutation Summary

## Intent
Hypernodes with no hyperedge relationships at all — orphans, or singleton entities not yet tied into any assertion — were rendered identically to every other hypernode in the 3D visualization, adding visual noise without contributing any structure to look at. The user asked to be able to hide them, framed as "only show hyperedges," but clarified the actual goal is decluttering: hypernodes that *are* part of a hyperedge are meaningful graph structure and should stay, only the disconnected ones should go.

## Context
"Orphan" is defined here strictly as "never appears as a `node_id` in any hyperedge's `members` list within the currently-rendered graph" — the same member-resolution concept `renderViz()` already builds (`nodeIdSet`, used since an earlier turn to let hyperedges reference each other as members) made this a natural extension: a hypernode's membership status was already implicitly knowable from the same data being scanned for a different purpose, it just wasn't being collected into its own set before.

## What Changed and Why
- **The referenced-hypernode-id set is computed once per graph, before hypernode nodes are pushed**, by scanning every hyperedge's raw `members` list directly (not reusing the `validMembers`/`vizMemberTargetId` machinery built for link-target resolution) — deliberately independent of whether that hyperedge *itself* ends up with zero other resolvable members and gets its own "members" branch skipped. A hypernode referenced by an otherwise-degenerate hyperedge is still a real member of something and shouldn't disappear just because its hyperedge happens to have no other visible participants.
- **Filtering happens by simply not pushing the node**, not by hiding it after the fact — since orphan hypernodes, by the exact definition used here, can never be the target of any relation-link (nothing references them), removing them from the `nodes` array can never leave a dangling link pointing at a node that no longer exists. This is the same reasoning already established for why hyperedges' own henode is always created regardless of member resolvability (a prior turn's fix) — applied here in the opposite direction, to confirm removal is always safe.
- **The toggle triggers a full `renderViz()` re-run, unlike the adjacent Labels/Media switches.** Those two only flip an in-memory flag that the already-rendered scene's tick loop respects (no nodes are added or removed) — this toggle changes which nodes actually exist in 3d-force-graph's underlying dataset, which can only happen through `.graphData()` being called again, and `renderViz()` is the one place that already does the fetch-and-build-and-set sequence correctly (including a `zoomToFit` that reframes the camera to the now-different node population, which is desirable here rather than an unwanted side effect — the camera was likely framed for a scene that just changed size).

## Key Decisions
- Read literally, "only show hyperedges" would mean hiding *every* hypernode, including ones that are actual hyperedge participants — but that would leave every relation-link either dangling or meaningless (a link with no visible endpoint), and would remove exactly the graph structure a hyperedge exists to describe. The clarifying sentence ("so that orphan/singleton hypernodes are not cluttering the display") makes the actual intent clear enough that implementing the literal phrase instead would have been the wrong call, not a faithful one.
- Made the toggle instantly reactive (auto re-render) rather than requiring a separate "Render" click, unlike the screen's existing `viz-status-filter` (which does require a manual click) — a toggle labeled and framed as a toggle should behave like one; the zoomToFit reframe that comes along with the re-render is treated as correct behavior for a control that changes what's actually in the scene, not friction to avoid.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the already-running dev server (frontend-only change, no restart needed) and a freshly-created headless Chrome profile (established practice this session). Created a real orphan test hypernode (no hyperedge references it), confirmed it renders normally before the toggle, then enabled "Hide orphan nodes" and confirmed via `State.viz3d.graphData()`: the orphan node was gone, `person:moe` (a real hypernode that's genuinely a member of several existing hyperedges) was still present, and the hyperedge node count was completely unaffected.
