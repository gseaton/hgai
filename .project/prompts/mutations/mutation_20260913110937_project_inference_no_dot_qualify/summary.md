# Mutation Summary

## Intent
The immediately preceding turn added an `only_new_hyperedges` toggle to Project Inference that, when a candidate's member didn't already exist in the target graph, rewrote that member's id to a graph-qualified form (`<source_graph_id>.<local_id>`) instead of duplicating it — reusing the dot-notation cross-graph reference convention built two turns earlier for the 3D visualization. The user rejected this: relation and member references in a projected hyperedge should never be modified from how they appear in the source, full stop — not duplicated, and not qualified either.

## Context
This correction exposed a real design mismatch from the prior turn, not just a preference difference. The dot-notation `<graph_id>.<local_id>` convention was built exclusively for `renderNoteMarkdown`... no — for the 3D visualization's `vizParseMemberRef()` (a pure frontend JS concern, see the cross-graph member reference feature from two turns ago) — it was never wired into HQL/SHQL's actual member/node resolution at the query engine level. Writing a hyperedge with a member like `hello-world.person:shemp` into a target graph would make that reference resolve correctly *only* in the 3D visualization UI; any HQL/SHQL query (`node: ?member bind: ?member_node`) would search for a hypernode literally identified `"hello-world.person:shemp"` — which doesn't exist anywhere — and silently fail to resolve it. Since the user's own stated purpose for the whole `only_new_hyperedges` feature (established two turns ago, in the original request that added it) was specifically "when a user/agent composes hypergraphs for query... operations," the dot-qualified form would have actively broken the one use case the feature exists for.

Before making this change, verified empirically (not just by re-reading code) that a *bare*, unqualified member reference resolves correctly without any special handling: `HypernodeSearchFilters.hypergraph_ids` and `HyperedgeSearchFilters.hypergraph_ids` both accept a *list* of graph ids, and both Mongo store implementations query them with `$in` — so a query run with a multi-graph `from:` (or against a `type: logical` graph whose `composition` includes both the projected-into target and its source) naturally finds a hypernode/hyperedge by id across every graph in scope, regardless of which specific graph the *referencing* edge document happens to live in. A hand-built test (a hyperedge stored in one graph, with a bare member id that only exists as a real hypernode in a second graph, queried via SHQL with `from: [graph-one, graph-two]`) confirmed the member resolves correctly with zero qualification needed.

## What Changed and Why
- **Removed the member-rewriting machinery entirely** rather than adjusting it — `_resolve_member_ref` and the `resolved_members`/`resolved_member_refs` variables from the prior turn are gone. The correct behavior for `only_new_hyperedges=True` turned out to be much simpler than what was built: don't call `_ensure_member_exists` (skip duplication), and otherwise change nothing. `candidate["members"]`/`_member_ids(candidate)` are now used identically regardless of the flag, exactly as they were before the toggle existed at all.
- **This also simplifies (and de-risks) the "safe to re-run" guarantee** that the prior turn had to work to preserve (resolving members *before* the dedup hyperkey check, specifically so a qualified id would be consistently reproduced on a second run). With no rewriting at all, `find_duplicate_hyperedge`'s hyperkey computation and the eventual `HyperedgeCreate` now always operate on the exact same member ids the candidate already had — the dedup-safety concern the prior turn introduced no longer exists, because there's nothing left to keep consistent across two computations.
- **`relation` was never modified in either turn's implementation** — only `members` ever went through any resolution/qualification logic. The user's prompt mentions "relation and member references" together, but there was no `relation`-rewriting code to remove; the docstring and field descriptions were corrected to avoid implying otherwise.
- **Corrected the docstring, API field description, and UI helper text together**, all three of which had described the (now-removed) qualification behavior in the prior turn — leaving any of them stale would have been actively misleading about what the toggle now does.

## Key Decisions
- Considered whether to keep *some* form of resolution (e.g., only qualifying members that are hyperedges, or only when a name collision is possible) rather than removing it outright. Rejected: the user's instruction is unconditional ("do NOT modify... the hyperedge references"), and the empirical verification confirmed there's no functional reason to qualify anything — a composed/multi-graph query resolves bare references correctly on its own, so any qualification would only ever be a net negative (breaking HQL/SHQL resolution) with no compensating benefit.
- Confirmed live, rather than assumed, that the fix actually achieves the user's original stated goal for this feature: ran the exact multi-graph SHQL query the user's own framing implies ("compose hypergraphs for query... operations") against a projected edge with a bare cross-graph member, and confirmed it correctly resolves — see Verification.
