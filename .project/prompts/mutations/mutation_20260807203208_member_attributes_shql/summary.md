# Mutation Summary

## Intent
The user wanted a working SHQL query example that returns the `attributes` (and by extension `label`) of a node referenced as a member of a hyperedge — a direct, concrete continuation of two prior asks in this conversation: "can HQL do this?" (answered no, SHQL can) and the subsequent SHQL `edge: id:` bugfix.

## Context
`notes/queries.md` is the user's own running scratch file of query examples, already containing several HQL/SHQL examples against a `hello-world` graph using `rel:member` relation and `group:three-stooges`/`group:rat-pack` node ids — a different naming convention than the checked-in `scripts/seed_data.py` seed data (`has-member`, bare ids), so the user clearly has their own dataset with this schema. The file's existing SHQL examples all `select: ?edge.members`, returning only raw `{node_id, seq}` pairs — exactly the limitation surfaced two turns ago when the user asked whether HQL can return member node labels/attributes (it can't; SHQL can). This request asks for the query that actually does it.

## What Changed and Why
Rather than answer only in chat, the example was appended directly to `notes/queries.md` in the same style and naming convention as the file's existing content (matching `rel:member`/`group:three-stooges`), consistent with how this file is clearly being used as a running library of working query snippets. Two variants were included: anchoring by a known co-member (the general case, usable without knowing any edge's literal id) and anchoring by the edge's own `id:` directly (showcasing the fix applied in the immediately preceding turn, appropriate since the user is actively exploring that exact capability).

Both queries were verified live before writing them down — a disposable throwaway server (`hgai_demo_validate5`, port 8399, torn down afterward) was seeded with a minimal `hello-world` graph using the user's exact `rel:member`/`group:three-stooges` naming (Three Stooges group + 3 person nodes with `attributes`), and both queries were confirmed to return the correct label/attributes for the referenced member nodes (3 rows excluding the anchor for the relation-anchored version; 4 rows including the anchor for the id-anchored version).

## Key Decisions
- **Verified against a purpose-built minimal graph matching the user's exact schema, not the demo-alpha dataset.** The user's `notes/queries.md` examples use `rel:member`/`group:*` naming, distinct from both `scripts/seed_data.py`'s `has-member` seed and this conversation's own `docs/decks/demo-alpha` dataset (`has-skill`/`staffed-on`/etc.). Building a small graph with the user's actual naming convention, rather than reusing an existing dataset with different relation names, meant the appended query examples could be copy-pasted against their real `hello-world` graph with no adaptation needed beyond swapping in the real other-member/edge ids if theirs differ.
- **Included two variants instead of one.** The "anchor by known member" form is the general-purpose answer that doesn't require knowing any specific edge id up front; the "anchor by edge id" form directly demonstrates the capability added in the prior turn and is the more natural fit when the user already has a specific edge in mind (as implied by "a hyperedge" in the request, and by the selected `notes/queries.md` snippet referencing a single specific edge).
