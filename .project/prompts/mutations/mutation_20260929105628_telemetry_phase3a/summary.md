# Mutation Summary

## Intent
Implement Phase 3a of docs/architect/telemetry-20260929061557.md §3a: the `__local-telemetry` hypergraph as a local, endpoint-free telemetry destination, with the isolation (mesh, permissions, listing) and retention the plan requires as "not optional."

## Context
Phases 1-3 built the queue/exporter foundation and REST/SHQL/MCP instrumentation, with local storage stubbed out (no-op `NullExporter` + a startup warning) pending this phase.

## What Changed and Why
`LocalHypergraphExporter.export()` writes each OTEL record as one hypernode via the platform's own `create_hypernode`, so it gets the same audit trail and is immediately SHQL-queryable — verified directly with a real `aggregate: {count, group_by}` query against the graph, storage-pushed-down. `select_exporter` was rewritten to match the plan's §2 pseudocode: local storage whenever no usable endpoint is configured, additionally whenever `HGAI_TELEMETRY_LOCAL_ENABLED=true`; a new `CompositeExporter` runs both destinations independently (one failing never blocks or duplicate-retries the other — it raises only if every destination failed). The three required isolation properties are implemented, not just documented: `HypergraphFilters.exclude_system` (a new, server-side, pagination-correct filter) hides `__*` graphs from the default `GET /api/v1/graphs` listing and the MCP hypergraph-list tool; `hgai_module_mesh/engine.py::_local_graph_ids()` excludes it from federation fan-out; admin-only access needed zero new code, confirmed by a test that exercises the *existing* `check_graph_permission`/`filter_accessible_graphs` against both an admin and a plain reader account. Retention uses a new `HypernodeSearchFilters.valid_from_before` filter and a repeated-requery-at-skip=0 deletion loop (not a client-side filter-after-fetch, which the write-up explains would fail to converge on a large collection), wired into a hgai/main.py-managed hourly background sweep mirroring the mesh scheduler's shape.

## Key Decisions
- **A real, non-hypothetical bug was found and fixed by the tests themselves, not assumed away**: the plan states the slug is "collision-free by construction" via its second-precision timestamp suffix, but two events with the same surface/feature/outcome/error.type in the same second — realistic at any real traffic volume — produce the identical slug and collide on the store's own uniqueness index. `_create_with_retry` stays optimistic (one insert, the plan's original zero-overhead intent in the common case) and retries once with a short random disambiguator only on failure, deliberately without inspecting *why* the first attempt failed, since a specific storage backend's exception type is exactly what this module must not need to know about to stay pluggable. A second failure is a real problem and propagates normally.
- **`prune_older_than` asserts its `cutoff` is never `None`** — `retention_cutoff()` returning `None` means "disabled," and a caller passing that straight through would otherwise build an unfiltered delete-everything query; the real scheduler path already guards this correctly, but the assert is there so a future caller can't get it wrong silently (confirmed by a test that this genuinely was reachable and dangerous before the guard was added).
- **Isolation is tested, not just implemented**: rather than trusting the "admin-only by construction" argument on paper, a test directly asserts `check_graph_permission` denies a non-admin and `filter_accessible_graphs` drops the graph from that account's list — the same claim the plan makes, made falsifiable.
- **The retention sweep runs whenever telemetry is enabled and retention isn't disabled**, independent of whether local storage is the active destination right now — a no-op sweep against a not-yet-created graph is cheap, and it means turning `HGAI_TELEMETRY_LOCAL_ENABLED` on later doesn't also need a restart to get retention.
