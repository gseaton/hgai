# Mutation Summary

## Intent
Fix a real bug surfaced in the immediately preceding conversation turn: SHQL `edge:` patterns silently ignore a literal `id:` key instead of filtering to that specific edge, so a query like `edge: { id: "some-edge-id", members: [...] }` matches *every* edge in the graph rather than just the named one.

## Context
The bug was discovered while answering a user question about whether HQL can join edge members to their full node docs (it can't — SHQL is the right tool). While verifying an SHQL example live, `edge: { id: edge-skills-dana, members: [{bind: "?member"}] }` returned 63 rows instead of the expected 4, revealing that `_eval_edge_pattern` in `hgai_module_shql/engine.py` never read an `id` key at all — only `bind`/`relation`/`flavor`/`tags`/`attributes`/`members`/`status`. This was saved to memory as a known limitation immediately after, with a note that it could be fixed if asked. The user then asked for the fix.

This sits in the same file recently touched by an unrelated upstream commit (`3e926c8`, 2026-08-07) that fixed a different SHQL member-matching bug (already-bound `bind` variables not being treated as anchors) and added `seq` positional matching — both discovered and worked around earlier in this same conversation before that upstream fix landed. This fix follows the same file's existing conventions closely (mirrors `_eval_node_pattern`'s `id` handling almost exactly) rather than inventing a new approach.

## What Changed and Why
`_eval_node_pattern` (hypernodes) already supported filtering by a literal or variable `id:`, resolving it via `_resolve_var` and passing it into `HypernodeSearchFilters.node_ids_in`. `_eval_edge_pattern` (hyperedges) had no equivalent — and `HyperedgeSearchFilters` has no dedicated `id`/`ids_in` field at all, only a generic `extra_filters: Optional[Dict[str, Any]]` pass-through that gets merged directly into the MongoDB query (`query.update(filters.extra_filters)` in `hgai_module_storage_mongodb/stores/hyperedges.py`) — the same mechanism edges already rely on for boolean operators like `$or`.

The fix mirrors the node pattern's `id` handling exactly: extract `pattern.get("id")`, resolve it (literal or `?var` via `_resolve_var`) before querying, skip the binding if a variable reference doesn't resolve, and — new for this function — also check `id` in the "already bound" fast path alongside the existing relation/flavor checks. The resolved id is threaded into `HyperedgeSearchFilters(extra_filters={"id": resolved_id})` rather than adding a new dataclass field, since `extra_filters` already exists for exactly this "arbitrary equality condition on the edge document" purpose and edges don't currently have (or need) a first-class `id_in` list-filter the way nodes do.

README.md's `### Edge Pattern` reference example was updated to list the new `id:` key, since it's now real, documented behavior rather than a silently-ignored no-op.

## Key Decisions
- **Reused `extra_filters` instead of adding a new `HyperedgeSearchFilters` field.** `HypernodeSearchFilters.node_ids_in` is a proper first-class field, which might argue for a symmetric `HyperedgeSearchFilters.id` or `.ids_in`. But `extra_filters` already exists specifically as the escape hatch for ad-hoc top-level Mongo conditions on edges (it's how `$or` already works), a single literal id is exactly that kind of condition, and adding a new dataclass field plus wiring it through the MongoDB store's `search()` would have been more surface area than the fix needed — the existing pass-through already does the job correctly.
- **No `$in`/list support was added for edge `id`.** The user's report and the bug were specifically about a single literal `id:` being ignored; matching the existing `_eval_node_pattern` precedent (single id, not a list) kept the fix narrowly scoped to the reported problem rather than speculatively broadening it.
- **No new automated test was added.** `_eval_edge_pattern` requires `get_storage()` (a live DB), and this project's existing test suite (`tests/test_shql.py`, added in the recent upstream `3e926c8` commit) only covers pure, DB-free helper functions (`_match_members`, `_match_members_expand`). Adding DB-mocking test infrastructure that doesn't exist anywhere else in the codebase was judged out of scope for this fix; instead, the fix was verified against a disposable, throwaway HypergraphAI server (seeded with the existing `docs/decks/demo-alpha/data/acme-eng-import.yaml` dataset) covering three cases — a real edge id, a nonexistent edge id, and the full existing `pytest tests/` suite (31 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before the change) — before considering the fix complete.
