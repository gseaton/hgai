# Mutation Summary

## Intent
The user asked why the Hypernodes list for an RDF-imported graph showed a node's id as the expanded IRI (`http://example.org/Adam`) while the same node's Edit modal showed something else (`ex:Adam`), and which of the two was the real identity.

## Context
Earlier this session, RDF import (`hgai/core/rdf_import.py`) was changed to mint hypernode ids and hyperedge relation values as full, expanded IRIs rather than compact `prefix:local` CURIEs. Every hypernode id this codebase had ever produced before that change was slash-free (e.g. `person:adam`), so nothing had ever exercised what happens when an id contains `/` — until RDF-imported full IRIs did, routinely (`http://...`).

## What Changed and Why
Investigating live (rather than guessing) showed the actual discrepancy wasn't a second, wrong id being displayed — reproducing the report against the current code showed the Edit modal's ID field came up genuinely *empty*, because `ui/js/api.js`'s `getNode`/`updateNode`/`deleteNode` (and the edge and space-scoped equivalents) build the REST URL by raw string interpolation (`/graphs/${graphId}/nodes/${nodeId}`) with no URL-encoding. For an id like `http://example.org/Adam`, that produces a path containing embedded `/` characters that FastAPI's default (single-segment) path parameter can't match — the request 404'd, the modal's fetch failed silently (caught by an empty `catch {}`), and the ID field was left showing its placeholder text. This exact class of bug — and its exact fix — already has a precedent in this codebase: `hgai/api/routers/media.py` uses `{media_id:path}` specifically because mesh-qualified media ids (`"server_id/local_id"`) also contain `/`, and its client-side calls in `ui/js/api.js` likewise never URL-encode the id, relying entirely on the server-side `:path` converter to accept the raw slash. The fix here mirrors that precedent exactly, applied to the four route files that expose node/edge CRUD by id.

## Key Decisions
- **Matched the existing `media_id:path` convention rather than adding client-side `encodeURIComponent()`.** Both would work, but the existing precedent already proves the raw-interpolation-plus-`:path`-converter approach works correctly in this codebase (verified: Starlette's `:path` converter matches literal, unencoded slashes in the URL), keeps the fix to the four router files rather than also touching `ui/js/api.js`'s dozen call sites, and keeps node/edge ids handled identically to how media ids already are.
- **Caught and corrected an unrelated mistake made while investigating.** A mutation-test cleanup step used `git checkout -- hgai/api/routers/hypernodes.py` as a "restore" fallback, which — since the file had uncommitted changes and no commit exists yet with today's fix — silently reverted the entire file to its last commit (wiping the routing fix, not just the deliberate test mutation). This was caught immediately by rereading the file and confirmed via `git status`/`git diff --stat` across all four touched router files before re-applying the fix and rerunning the full suite; nothing else was affected since only that one file had been touched by the bad command.
- **Verification, in order:** (1) reproduced the exact report live against the running code before touching anything; (2) found the true root cause via a direct API call (`getNode` returning "Not Found") rather than assuming; (3) found and matched the existing `media_id:path` precedent rather than inventing a new pattern; (4) fixed all 12 affected routes, not just the one node-GET path that reproduced the report, by auditing every router for the same `{node_id}`/`{edge_id}` shape; (5) added 14 storage-free regression tests and mutation-tested them (reverting one router's fix and confirming 3 tests fail, matching the earlier bug's exact symptom); (6) live-verified GET/PUT/DELETE with a full-IRI id on a disposable instance; (7) reproduced the original Web UI bug in the browser, confirmed it fixed, confirmed no console errors; (8) after user confirmation, restarted the user's actual running server (8357) and did one final live functional check (not just an OpenAPI-schema check, since FastAPI's OpenAPI output doesn't display the `:path` suffix and could have given a false negative) to confirm the fix is genuinely live. Full suite: 519 passed (2 pre-existing, unrelated mesh-ping failures excluded, consistent with every run this session).
