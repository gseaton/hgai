# Mutation Summary

## Intent
Implement Phase 3 ("MCP") of docs/architect/telemetry-20260929061557.md: instrument all 30 MCP tools with one decorator, reading each tool's own success/denied/error outcome from its existing return-value convention rather than reimplementing authorization or error classification.

## Context
Every tool in hgai_module_mcp/server.py already catches its own failures and returns a JSON string with a `"type"` key on failure (`_denied()`'s `PermissionDenied` shape, and each tool's own `except` blocks for `SHQLError`/`ExecutionError`/`ParseError`/etc.) — confirmed by reading `_guard_graph`/`_guard_admin`/`_guard_space` and several tool bodies (including `hgai_query_execute`) before writing any code. Verified via FastMCP's `list_tools()`/`ToolManager` that `functools.wraps`' `__wrapped__` chain keeps tool schemas (parameter names, types, required fields) exactly as they were before decoration.

## What Changed and Why
`track_tool` times the call, then classifies the *tool's own return value* (`_classify`): a JSON dict with `"type": "PermissionDenied"` is `denied`, any other `"type"` key is `error`, anything else is `ok` — exactly what the plan specifies ("the wrapper reads their return value, it doesn't reimplement authorization logic"). A `usage` event always fires with that outcome. On any non-`ok` outcome, a paired `kind: "error"` event also fires — extending Phase 2's REST/SHQL pattern (usage + error on failure) to MCP for consistency across surfaces, going slightly beyond the plan's terse MCP row but directly serving its own stated goal (error/bug reporting) and its schema example (`"hgai.mcp.tool": "hgai_hyperedge_create"`). Since most MCP failures are already-caught JSON envelopes with no live exception, a new `build_error_event_from_message` fingerprints from the envelope's `type`/`error` text instead of a traceback (empty `stack_frames`, frame key falls back to `surface_context:feature` so different tools returning the same generic error still fingerprint differently — verified by a dedicated test). A genuinely uncaught exception (not supposed to happen, given the codebase's own convention, but not assumed away) still propagates unchanged and is reported with a real traceback via the existing `build_error_event`.

## Key Decisions
- **`track_tool` lives in `hgai_module_mcp`, not `hgai_module_telemetry`** — telemetry never imports a surface module; a surface module lazily imports telemetry's generic building blocks. Mirrors exactly how Phase 2 placed the SHQL hooks inside `hgai_module_shql/engine.py` rather than inside telemetry.
- **A paired error event on every non-`ok` outcome** (not just uncaught exceptions) — a deliberate, documented extension beyond the plan's literal MCP-row wording, for the same reason Phase 2 already does this for REST/SHQL: a permission denial or a business-logic error is real signal for the "error / bug reporting" analysis question, and MCP shouldn't be second-class relative to the other surfaces already built.
- **No behavior change is possible by construction**: `track_tool` always returns the wrapped function's real value or re-raises its real exception; every telemetry call is wrapped in its own broad `except Exception: pass`.

## Verification
`python -m pytest tests -q` — 952 passed (the same 2 pre-existing, unrelated mesh-ping failures deselected as before). 19 new tests, plus a manual end-to-end check against the real `hgai_module_mcp.server` module: a denied `hgai_hypergraph_get` call and an `hgai_query_execute` failure both produced the expected usage + error event pairs (the SHQL-layer error from Phase 2 and the MCP-layer error both fired, with correctly redacted templates), and `mcp.list_tools()` confirmed all 30 tool input schemas are unaffected by the decorator.
