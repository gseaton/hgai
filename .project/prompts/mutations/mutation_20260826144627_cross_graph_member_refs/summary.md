# Mutation Summary

## Intent
A hyperedge's members list was implicitly scoped entirely to that hyperedge's own hypergraph — confirmed in this session's earlier read-only investigation ("How to reference a hypernode in graph 'alpha' as a member in a hyperedge in graph 'bravo'?"), which found no mechanism for a member to cross a graph boundary. The user asked for exactly that capability: a member `node_id` prefixed with another graph's id (e.g. `bravo.person:john`) should be understood as pointing at a hypernode/hyperedge living in that other graph, and the 3D visualization should be able to retrieve and render it correctly.

## Context
This follows directly from two read-only investigations earlier in this session: first confirming cross-graph member references weren't supported at all, then documenting HQL/SHQL's existing `from:` clause dot-notation (`mesh_id.server_id.graph_id`) as the established convention for graph-qualified identifiers in this codebase. The user explicitly asked for "the local graph using the dot-notation syntax used in HQL and SHQL" — a narrower, same-server variant of that convention (just `graph_id.local_id`, not the full mesh dot-notation), which the example (`bravo.person:john`) confirms.

This also builds directly on the immediately preceding session turns' 3D-visualization architecture: `renderViz()`'s per-graph fetch → build → render structure, the `hnode`/`henode`/`members` viz-node-kind scheme, the `${gid}::${id}` / `${gid}::he::${id}` viz-id namespacing convention, and the orphan-hiding toggle's precedent for filtering/materializing nodes based on membership data.

## What Changed and Why
- **Dot-notation, not the full mesh format.** The user's example is a single `graph_id.` prefix, not `mesh.server.graph`. Hypergraph IDs are already forbidden from containing `.` (`hgai/models/hypergraph.py:32-36`, pre-existing), so splitting a member `node_id` on its *first* dot is always unambiguous for a real graph-qualified reference, exactly mirroring how HQL/SHQL's own resolver disambiguates dot-notation.
- **The graph-qualifier is only honored when it names a graph the app actually knows about** (`State.graphsCache`, populated wholesale whenever the Visualize screen's graph selector loads — confirmed via `populateVizGraphSelect()` calling `_fetchAndCacheGraphs()`). This is a deliberate backward-compatibility safeguard: nothing in the schema forbids a plain hypernode/hyperedge `id` from containing a literal `.` (unlike hypergraph/mesh/server ids), so an unqualified prefix that doesn't resolve to a real graph falls through and resolves as a plain same-graph id, exactly as it did before this feature existed. Verified live with a hypernode id `v1.2:release-marker` referenced as a plain member — it resolved locally, unaffected by the new dot-parsing logic.
- **No backend schema or validation change.** `EdgeMember.node_id` was already, and remains, an unconstrained string — member existence isn't validated at creation time for same-graph references either (confirmed in this session's first investigation), so adding cross-graph validation now would be inconsistent with the existing design and out of scope for what was asked. The only backend change is a documentation update to the field description, so anyone creating hyperedges via the API can discover the convention.
- **Resolution uses a single-item lookup (`GET .../nodes/{id}` or `.../edges/{id}`), not a full graph fetch**, deliberately avoiding two problems a full-listing fetch would have: (1) the target graph's node/edge listing is paginated (`VIZ_FETCH_LIMIT`), so a large target graph could silently omit the one referenced element; (2) fetching an entire unrelated graph just to visualize one referenced node would flood the scene with content the user never selected. A node_id is tried as a hypernode first, then as a hyperedge — mirroring exactly how same-graph member resolution already disambiguates between the two id spaces (hyperedges are first-class and may be members of other hyperedges, an invariant established earlier this session).
- **Only the referenced node/hyperedge itself is visualized — its own further member structure is not expanded**, even when the target is itself a hyperedge. This is a deliberate scope decision: recursively expanding a cross-graph hyperedge's own members would risk unbounded traversal across graph boundaries (including circular references between graphs), and the user's phrasing ("knows how to retrieve and visualize *that member node*") describes a single referenced element, not its transitive substructure. A cross-graph hyperedge stub is given `arity: 0` and its tooltip omits the now-inapplicable member-count text rather than showing a misleading "0 members."
- **The scene-building logic was restructured into two passes (materialize all directly-selected graphs' own nodes first, then build links and lazily materialize any still-missing targets) specifically to prevent a duplicate-id collision**: if a hyperedge in a directly-selected graph 'alpha' cross-references a node in graph 'bravo', and the user *also* has 'bravo' selected for direct viewing, both code paths would otherwise try to create a node with the same viz id (`bravo::person:john`). The two-pass structure guarantees the "real" per-graph push always exists (or gets created) before the cross-graph fallback ever checks for it, so the cross-graph path only ever fires for something that genuinely isn't otherwise present — verified live (see below) that selecting both graphs produces no duplicate and the previously-stub'd hyperedge upgrades from `arity: 0` to its real member count once its own graph is directly selected.
- **A cross-graph node is visually flagged** (dashed amber label style, an explicit "↳ external reference · graph bravo" tooltip note, and a `(bravo)` suffix on its on-screen label) rather than rendered identically to a local node — otherwise a user viewing only graph 'alpha' would see an unexplained extra node with no indication it actually lives elsewhere, which would undermine rather than support the "visualize" half of the request. Clicking it still shows its full raw JSON in Element Details, which already includes its true `hypergraph_id` (`bravo`) with no code changes needed there, since the raw hypernode/hyperedge payload already carries that field.

## Key Decisions
- Considered whether to also support the fuller mesh dot-notation (`mesh.server.graph`, `space/graph`) for member references, since the user had asked about that syntax in the immediately preceding question. Scoped this out: the user's request here explicitly says "the local graph" and gives a same-server, non-space-scoped example — extending to remote-mesh member references would require resolving through `hgai_module_mesh`'s HTTP-federation machinery (built for query-time federation, not persisted member-reference resolution) and was neither asked for nor a small extension of what was asked.
- Considered eagerly validating/rejecting a cross-graph reference to a nonexistent graph or node at hyperedge creation time. Rejected to stay consistent with the existing, deliberate design where member existence is never validated at creation (same-graph or otherwise) — an unresolvable reference (cross-graph or local) simply doesn't render as a link, exactly as any other broken member reference already behaves.
- Considered whether a resolved cross-graph hyperedge target should recursively expand its own members (matching how every hyperedge in a directly-selected graph always gets its own full member fan-out). Rejected in favor of a single-level leaf rendering, both to bound the traversal (avoiding infinite loops from circular cross-graph references) and because the request's phrasing describes visualizing the referenced member, not importing its entire substructure.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the running dev server (had to be restarted this session — confirmed via `pgrep`/`ss` before starting) and a freshly-created headless Chrome profile (established practice this session, avoids stale-cache false results). Created real cross-graph test data via the API: hypergraph `bravo` with hypernodes `person:john`/`person:jane` and hyperedge `edge:bravo-team` (`teammate`, members john+jane); a hyperedge `edge:cross-test` in the pre-existing `alpha` graph with four members — a local hypernode (`person:tommy-moore`), a cross-graph hypernode ref (`bravo.person:john`), a cross-graph hyperedge ref (`bravo.edge:bravo-team`), and a deliberately-broken cross-graph ref (`bravo.person:does-not-exist`) — confirming the model layer accepts dot-prefixed member ids with zero schema changes.

- **Only `alpha` selected**: both `bravo::person:john` (hnode) and `bravo::he::edge:bravo-team` (henode) appeared in the rendered scene despite `bravo` never being selected, each correctly tagged `crossGraph: true` with `graphId: "bravo"`. The broken reference correctly resolved to nothing (edge arity 3, not 4) rather than erroring.
- **Label/tooltip verification**: the on-screen label read `John Bravo (bravo)` with CSS class `viz-label-node-external` (dashed amber styling) applied; the hover tooltip read `↳ external reference · graph bravo`; the cross-graph hyperedge's tooltip correctly omitted the misleading member-count text.
- **Element Details verification**: clicking the cross-graph hypernode showed its full raw JSON with `"hypergraph_id": "bravo"` — correct attribution, distinct from the referencing hyperedge's own graph (`alpha`).
- **Both `alpha` and `bravo` selected**: no duplicate nodes (`bravo::person:john` and `bravo::he::edge:bravo-team` each appeared exactly once); `edge:bravo-team`'s arity correctly upgraded from the stub's `0` to its real value `2` (john + jane) since `bravo`'s own edges are now directly rendered with full member expansion; `person:jane` was present (only reachable via `bravo`'s own data, confirming Pass A ran correctly).
- **Backward-compatibility check**: a hypernode `v1.2:release-marker` (a literal dot in its id, prefix `v1` not a real graph) referenced as a plain member resolved locally as before — not misinterpreted as a cross-graph reference.
- **No JS errors**: installed a global `error`/`unhandledrejection` listener before any render and cycled through four graph-selection combinations (`alpha`, `alpha+bravo`, `bravo` alone, `alpha+bravo+hello-world`) — zero errors recorded across all of them.
