# Mutation Summary

## Intent
Unlike the two prior decks this session (`demo-bus-dev-20260817` and `demo-spec-ops-20260817`, both BD/product-manager-audience business briefings with a full artifact package — main deck, presenter notes, data files, query files, in a dedicated folder), this request asked for a single markdown file at an explicit path (`docs/demos/demo-20260817-ai-context-memory.md`, a new top-level folder distinct from the established `docs/decks/` convention) focused narrowly and deeply on one topic: HypergraphAI as an AI agent memory engine across five specific, named memory tiers — working, session, episodic, semantic, and procedural — with comparisons to SQL/RDBMS and traditional semantic knowledge graphs specifically through the lens of MCP-served agent memory.

## Context
- The user's phrasing ("agentic working, session, episodic, semantic, and procedural memory handling") specifies five distinct tiers, notably separating "working" and "session" as two different things — a refinement beyond the four-tier framework (working/episodic/semantic/procedural) found in `docs/design/ai-knowledge-store.md` (read earlier in this session while drafting the greenfield `build-plan.md`) and beyond the same four-tier table already used in both prior decks this session. This request's five-tier model was treated as the authoritative structure to build around, with "session" defined as a distinct tier: broader/more persistent than "working" (a single step's scratch state) but still scoped to the current, still-open conversation, as opposed to "episodic" (durable record of past, closed sessions).
- No audience was specified this time, and the file path (`docs/demos/` rather than `docs/decks/`) reads as a more general technical/enablement location than the two audience-labeled BD decks. The deck was written to be accessible to a mixed technical/product audience rather than tailored to a specific vertical (no defense framing, no fictional customer disclaimers needed since the scenario — a generic SRE incident-investigation agent for a fictional company, "Acme Corp" — is not domain-sensitive in the way the specops deck's scenario was).
- Reused and extended established conventions from this session's prior decks: the "live vs. roadmap" honesty table (avoiding the existing investor deck's inferencing overclaim, per this session's established practice), and the verified-safe SHQL pattern for extracting multiple unknowns from a multi-member hyperedge (independently pre-binding every variable via top-level, type-checked `node:` patterns before using them as pure join-constraint anchors in the `edge:` pattern) — established while building the specops deck's q04 query, after identifying that SHQL member sub-patterns do not enforce `type:` at match time. That same technique was required again here for Section 11's cross-tier query (a 4-member `incident-conclusion` hyperedge), and was applied from the start rather than needing a later correction pass.

## What Changed and Why
Created one new self-contained file, `docs/demos/demo-20260817-ai-context-memory.md`, structured around a single running example built specifically to have a natural home in all five memory tiers at once:

- **Working memory** — a single transient hypernode (a scratch comparison note), tagged by session, explicitly called out as the one tier this platform expects *not* to be retained indefinitely.
- **Session memory** — a hypernode plus a hub hyperedge representing "what this open conversation currently knows" (customer, incident, current hypothesis).
- **Episodic memory** — the deck's centerpiece: a 4-member hyperedge (`incident-conclusion`) recording a *past* session's root-cause conclusion, with provenance (`investigator_agent`) and `confidence` fields, deliberately chosen as the example with the most simultaneous participants precisely because "who concluded what, from what evidence, how confident" is the natural shape of an AI agent's own distilled reasoning — a sharper, more memory-specific N-ary example than either prior deck's (staffing, MEDEVAC) since it's about representing the agent's reasoning provenance itself, not an external business fact.
- **Semantic memory** — durable, session-independent entities (customer, service, database) and one `depends-on` edge, deliberately reused as a member in the episodic edge above, so the deck could demonstrate a genuine cross-tier join (Section 11) rather than presenting five tiers as five isolated examples.
- **Procedural memory** — a single `Procedure` hypernode whose `attributes.steps` list explicitly instructs an agent to query episodic memory before re-deriving an analysis — written so the deck's own Section 13 ("the loop that actually matters") could point back at this as a concrete instance of procedural memory directing an agent's use of the other tiers, rather than treating procedural memory as an inert checklist.
- **Three "why hgai over X" sections**, each re-derived for the memory use case specifically rather than reusing the prior decks' general-purpose framing verbatim: the SQL argument centers on schema rigidity against *emergent* memory-record shapes (a new memory kind requires a new table/migration, versus a new `relation` value); the RDF argument adds an operational-fit point beyond reification cost — that traditional triple stores are typically tuned for stable curated reference data, not the high-volume churn working/session tiers generate; the vector-store argument centers on tier-blindness and the absence of exact/structural/point-in-time lookup, framed as a table of specific questions a bare vector index cannot answer.
- **A dedicated lifecycle/hygiene section** (Section 18) was added beyond what either prior deck covered — judged necessary because this deck, uniquely among the three, asks the reader to actually adopt a five-tier tagging convention operationally, and different tiers warrant different retention treatment (working memory expected to be discarded; semantic/procedural treated as system-of-record data) — including an honest roadmap note (Section 19) that automatic tier-lifecycle enforcement (e.g. auto-expiring working memory, auto-promoting session to episodic) is an application-level pattern to build on top of the live write path today, not a built-in platform behavior, so as not to overclaim automation the platform doesn't yet provide.

## Key Decisions
- **Single file, no companion data/query/presenter-notes files** — matched exactly to what was requested (a slide deck at one explicit path, no mention of separate demo artifacts this time, unlike the two prior decks which explicitly asked for "other necessary demo artifacts"). All YAML/HQL/SHQL/JSON snippets are inline and self-contained rather than split into a `data/`/`queries/` folder structure.
- **Five tiers, not four** — deliberately followed the user's explicit five-way phrasing rather than collapsing "working" and "session" back into the four-tier framework used elsewhere in this session's prior work, since the user's wording was specific and a five-tier model is a coherent, definable refinement (working = current step's scratch state; session = the current conversation's broader active context) rather than a redundant split.
- **Domain-neutral scenario** (generic SRE/incident-investigation agent) rather than reusing either prior deck's business or defense framing — chosen because no audience was specified and the topic itself (agent memory architecture) is broadly applicable across verticals; a defense- or contract-staffing-specific scenario would have narrowed the deck's applicability without adding to its argument about memory specifically.
- **Verified every SHQL pattern against the established safe-binding technique before writing it**, rather than drafting first and correcting later (as happened with the specops deck's q04) — applied the lesson learned in that earlier pass proactively, since the cross-tier query in Section 11 has the same multi-member, multi-wildcard shape that previously required a fix.
