# Mutation Summary

## Intent
Following an earlier design discussion (captured separately under `.project/prompts/asks/ask_202609090959_hyperkey_dedup_temporal/`), the user asked to implement the recommended fix: allow a hyperedge with the same relation, flavor, and members to exist more than once in a graph as long as each instance has a distinct `valid_from`/`valid_to` window — e.g. "moe, larry, shemp" as the Three Stooges lineup during two separate historical eras — while still rejecting a true exact duplicate.

## Context
The prior investigation established that hyperedge identity/dedup is driven entirely by a SHA-256 "hyperkey" (`generate_hyperkey()` in `hgai/core/engine.py`), computed from `relation` + sorted member IDs + hypergraph ref only — `valid_from`/`valid_to` (and `flavor`) were never part of it. A DB-level unique compound index `(hyperkey, hypergraph_id)` (`hgai_module_storage_mongodb/indexes.py:66-74`) enforces this at the storage layer, meaning two hyperedges with the same relation+members always collided regardless of date range or explicit custom `id`. It was also noted that the app-level routers only pre-check `id` collisions (giving a clean 409), not hyperkey collisions — a hyperkey clash previously fell through to an uncaught pymongo `DuplicateKeyError`.

## What Changed and Why
`generate_hyperkey()` now takes optional `valid_from`/`valid_to` and hashes a canonical (UTC-normalized) form of them alongside the existing fields, so two edges with identical relation/members but different validity windows get different hyperkeys — and thus different default auto-generated ids, and no longer collide on the unique index — while an edge with the exact same window as an existing one still correctly hashes identically and is still rejected as a duplicate. `flavor` was deliberately left out of the hash, matching the user's stated scenario (same flavor, different dates should still be treated as related-but-distinct facts about time, not distinguished by flavor).

Both places that computed a hyperkey — `create_hyperedge()` and the recompute step inside `update_hyperedge()` — were updated to pass the edge's (or patch's, falling back to the existing edge's) validity window through, so the identity stays consistent whether an edge is created fresh or edited in place. This means editing an edge's date range does regenerate its hyperkey going forward — flagged as intentional in the design discussion (a moved validity window is a genuinely different temporal fact), not something this change tries to prevent.

To close the "raw DB error" gap surfaced during the design investigation, a new `engine.find_duplicate_hyperedge()` helper was added and wired into both hyperedge-creation routers (`hyperedges.py` for unowned graphs, `spaces.py` for space-owned graphs) so an exact-duplicate hyperkey now produces the same clean, informative `409 Conflict` response users already get for an `id` collision, rather than leaking an unhandled `DuplicateKeyError`.

## Key Decisions
- **Canonicalization of datetimes for hashing:** `_normalize_hyperkey_instant()` normalizes any timezone-aware or naive datetime to UTC ISO-8601 before hashing, and keeps `None` (unbounded) as Python `None` in the hashed payload rather than a string sentinel — verified via a dedicated test (`test_hyperkey_instant_normalizes_across_timezones`) that the same instant expressed in UTC, a `-5:00` offset, and as a naive datetime all produce the identical hyperkey. This avoids silently treating equivalent inputs as distinct (which would let true duplicates slip through) while still keeping "no bound at all" distinguishable from any concrete bound.
- **No DB index/schema migration performed or required:** the existing `(hyperkey, hypergraph_id)` unique index already does the right thing once the hash itself reflects the temporal window — this is why the fix is contained to `engine.py` plus router-level UX, with zero changes to `hgai_module_storage_mongodb/indexes.py`.
- **`flavor` intentionally excluded** from the hash, per the user's example — not implemented, but called out again here as a natural, symmetric follow-up if ever needed.
- **Overlap prevention (e.g., disallowing 1958–1959 and 1958.5–1959.5 as "different enough") was explicitly NOT implemented** — this was flagged in the design discussion as a distinct feature (an application-level interval-overlap check) beyond what hashing alone can express, and the user's go-ahead was for "it" (the described hash + pre-check design), not a broader validity-overlap system.
- **Verified against a live, isolated instance** rather than only unit tests: spun up a second `hgai.main` process on an unused port against a throwaway MongoDB database (`hgai_clone_test`, never touching the user's real `hgai` database or their already-running dev server on port 8357/pts 9), created the two-era Three Stooges lineup via the real HTTP API, confirmed both `201 Created` with distinct auto-generated ids, confirmed a third exact-duplicate attempt (shuffled member order, different explicit custom id) correctly got `409` with the new friendly message, then tore down the test process and dropped the throwaway database. Also confirmed via `git stash` that 3 pre-existing, unrelated `test_mesh.py` failures are present on `main` before this change (network/mesh tests, not touched here) so they aren't misattributed to this work.
