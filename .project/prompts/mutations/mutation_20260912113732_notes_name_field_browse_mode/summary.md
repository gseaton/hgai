# Mutation Summary

## Intent
Extend the per-account Notes feature with a separate human-readable `Name` field (distinct from `Label`), and restructure the note editor modal around a new default "Browse" mode — a minimal, read-focused view (Label, Name, rendered content, and the mode switcher only) — with the existing full-form editing experience demoted to an explicit "Edit" mode the user opts into. The Name field should also drive sorting/display in the folder sidebar and appear in the notes table listing.

## Context
This follows two prior turns that built the Notes feature (model, storage, REST API, sharing, UI) and its Quill-inspired tag-based folder sidebar. The user's phrasing ("keeping the Label field as unique note identifier field") was interpreted as "don't change what Label does" rather than a literal database uniqueness constraint — Label was never actually DB-enforced-unique in this implementation (only `id`, a server-generated UUID, is), and the reference note-taking app this whole feature has been modeled on explicitly documents that its own `label` field is *not* required to be unique either ("labels are not required to be unique... first match wins if multiple notes share a label"). Enforcing a new uniqueness constraint would have been a materially different, riskier change (per-owner scoping, duplicate-handling UX, migration of any existing non-unique data) that the request didn't specify enough detail about to build confidently — so this turn adds `Name` alongside the existing `Label` without changing Label's semantics, and states that assumption plainly here rather than silently guessing at enforcement details.

## What Changed and Why
`name` was added as an ordinary optional string field (empty-string default, same shape as `label` but without the `required` constraint), threaded through the full stack the same way `label` already was: the Pydantic model, the mutation-audit-trail tracked-fields list, the storage patch/update path, and the Mongo store's search clause (so searching now matches label, name, or text).

The modal's three-mode restructuring follows the request's explicit distinction between two already-similar-looking states: the *old* "Preview" mode (full form visible, Content area showing rendered output instead of raw Markdown) stayed exactly as it was, and a *new*, stripped-down "Browse" mode was added alongside it — same rendered content, but with Tags/Status/Media/History and the raw-Markdown textarea entirely absent, leaving just Label, Name, and the rendered content. Browse becomes the default entry point for an existing note (since viewing, not editing, is the more common first action once a note already has content), while a brand-new note still opens directly into Edit (there's nothing yet to browse). This meant lifting the mode-switcher buttons out of the Content section (where they only ever toggled between raw/rendered Content) to a new modal-wide bar directly under the header, since Browse's effect isn't scoped to one section anymore — it hides most of the modal.

The permission interaction was extended to match: an account with only view access to a shared note already couldn't save changes (from the prior sharing-feature turn), but could previously still *enter* Edit mode and see input fields it wasn't allowed to submit — a confusing, inconsistent state. The Edit-mode button is now hidden entirely for a non-editable note, and a `noteModalEditable` flag (set once per modal open) gates Save's visibility uniformly across whichever mode is active, not just Browse.

Sorting and display in the folder sidebar switched from `label` to `name || label` — using the note's Name as the primary sort key and display text when set, falling back to Label for notes that don't have one, per the request's explicit instruction. When a Name is shown, the Label still appears as disambiguating meta context (alongside the existing id-suffix), since two notes can share a Name just as easily as they can share a Label.

## Key Decisions
- **Label's semantics are unchanged, not made database-unique** — see Context above; this was a judgment call under ambiguity, made explicit here rather than silently assumed, so it's easy to correct if it doesn't match what was intended.
- **A brand-new note still opens into Edit, not Browse** — Browse's whole purpose is displaying existing rendered content; defaulting an empty, just-created note into a view showing nothing useful would be actively unhelpful, so this reads the request's intent ("displays the rendered content of the note") as applying to notes that already have content.
- **Folder-tree sort/display uses Name-or-Label as one combined key, not Name-only** — sorting purely by Name would scatter every unnamed note to wherever an empty string collates (typically the very top), which reads as broken rather than intentional; falling back to Label keeps every note's position in the tree meaningful regardless of whether it has a Name.
- **Hiding the Edit button for non-editable notes was an extension beyond the literal request, made because the new three-mode structure surfaced a real gap**: without it, a viewer-only account could open Edit mode, see live input fields, type into them, and only discover on Save (now hidden) that none of it could persist — worse than the prior two-mode version, where at least the fields themselves were disabled. Addressed proactively rather than left as a known rough edge.

## Live Verification Performed
Started an isolated test server and seeded three notes in one folder: two with distinct Name values on opposite ends of the alphabet from their Labels (`ZZZ Label First` / name `Alpha Named`, and `AAA Label Second` / name `Zebra Named`), and one with no Name at all, to specifically stress-test the name-driven, label-falling-back sort.

Confirmed the notes table shows the new Name column correctly (including an em-dash placeholder for the unnamed note); confirmed the folder sidebar sorted and displayed by Name-or-Label exactly as designed (`Alpha Named`, then `No Name Note` — sorting by its Label since it has no Name — then `Zebra Named`), with Label shown as meta context only for the two named entries; confirmed opening an existing note defaults to Browse mode showing exactly Label + rendered content (Name subtitle correctly absent when blank); confirmed Edit mode shows the full form with the new Name input alongside Label; confirmed Preview mode shows the full form with rendered content in place of raw Markdown, distinct from Browse; confirmed editing the Name field, saving, and reopening correctly displayed the new Name in Browse's subtitle and immediately re-sorted the note's position in the folder tree.

Also created a second test account, shared a note with it as viewer-only, and confirmed: the modal title read "(view only)", only Browse and Preview mode buttons appeared (Edit was completely absent, not just disabled), and the footer showed no Save button in any available mode.

One real bug surfaced and was resolved during this verification session, unrelated to the code changes themselves: browser automation's `type` action intermittently populated a field's `placeholder` attribute's visual appearance without actually setting its `.value` (a known quirk encountered earlier in this same session) — worked around each time by triple-clicking to select-all before typing and verifying via a direct JS read of `.value` before proceeding, rather than trusting the screenshot's rendered text alone.

Test server killed and `hgai_notes_name_browse_verify` database dropped afterward, along with the temporary `viewerbob` test account (left in place is harmless — it's an isolated throwaway database that was fully dropped). Full test suite: 84 passed, same 3 pre-existing unrelated `test_mesh.py` failures — no regressions in `tests/test_notes.py`'s pure permission-logic tests, which don't touch the `name` field or mode-switching UI at all.
