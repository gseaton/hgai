# Mutation Summary

## Intent
The user wanted a complete, presentable business-development briefing package for a specific, named audience — BD and product managers at large U.S. defense professional-services and technology-consulting companies — that explains HypergraphAI (hgai) at the concept level (not an engineering deep-dive) while still proving its claims with one concrete, runnable example. They specified five required content threads: (1) core hypergraph principles/concepts, (2) hgai as a general semantic knowledge storage platform independent of AI use cases, (3) hgai as AI context memory both within a session and across sessions, (4) how MCP's opening of models to "almost any system" lets agents not just read/retrieve but persist and query their own expensive, distilled reasoning across turns and sessions, and (5) at least one complete, simple, step-by-step example proving hgai's advantage over traditional SQL RDBMS and traditional semantic knowledge graphs (RDF/triple stores). They also asked for supporting demo artifacts by name — TTL data files and demo query files.

## Context
- This repo already has two established deck conventions to match: `docs/decks/demo-alpha/deck-demo-alpha.md` (an engineering-audience, fully executable walkthrough with a `data/` + `queries/` folder structure, `---`-delimited slides, and an explicit "live vs. roadmap" honesty section for inferencing) and `docs/investor-pitch-deck.md` (a punchier, business-toned deck for a different audience — investors). Both were read in full before drafting, to match established tone/structure conventions in this repo rather than inventing a new format.
- The investor deck was found to overclaim a capability — it presents SKOS inferencing as "Built In" and "automatic" — that this session's own persistent memory (`hgai_inferencing_status.md`) had already established as dead code with zero call sites as of a prior audit (2026-08-07). This was a live, active editorial decision in drafting the new deck: deliberately follow demo-alpha's honest "live vs. roadmap" convention instead of the investor deck's overclaiming one, given this new deck's audience (defense/gov consulting BD staff) is professionally exposed if they repeat an inaccurate capability claim to a federal customer during their own diligence or a later sales conversation. This reasoning is stated explicitly in the new deck's own "What's Real Today vs. Roadmap" section and again in the presenter notes' Q&A entry on inferencing.
- Verified the exact real SHQL member-pattern syntax against `demo-alpha`'s actual query files (`members:` sub-patterns wrapped in `node: {...}`, e.g. `node: { bind: "?person", type: Person }`) before writing this deck's SHQL query file — an earlier document in this same session (`build-plan.md`, the separate greenfield-rebuild plan) had used a different, unwrapped shorthand (`{ bind: "?person" }`) for its own illustrative SHQL examples, which is a v2/hypothetical spec choice for a from-scratch rebuild, not the real, currently-running v1 system's syntax. Since this new deck is presented as a demo of the actual, current, running hgai product to a business audience who may ask to see it run live, correctness against the real engine (not the greenfield spec) was treated as the binding requirement here.
- Read `docs/dev_notes/hgai-improvements-20260328.md`, `docs/architecture/hypergraph_ai_design_notes.md`, and (from earlier in this session) `docs/design/ai-knowledge-store.md` for grounding on the AI-memory-tiers narrative (working/episodic/semantic/procedural memory) used in the deck's Section 7 — adapted from that design essay's six-tenet framework into plain business language rather than reproducing its technical vocabulary.

## What Changed and Why
Created a new, self-contained deck package at `docs/decks/demo-bus-dev-20260817/`, structured to mirror `demo-alpha`'s file layout (`deck-*.md` + `data/` + `queries/`, plus a presenter-notes companion file) but written at the tone and depth appropriate for a non-engineering audience:

- **The main deck** (`deck-hgai-defense-bd.md`) addresses each of the user's five required threads as its own section, in the order requested, and ends with defense/gov-specific deployment framing and a business-fit/next-steps close tailored to a BD audience evaluating whether/how to adopt or resell the platform (not an investor audience being asked to fund it).
- **One complete worked example**, satisfying requirement 5 directly: a fictional task-order staffing scenario chosen specifically because U.S. defense-consulting BD/PM staff live in exactly this domain (task orders, labor categories, contract mods, clearances) and because the natural fact — "person X staffed on task order Y in labor category Z, approved by W, effective on date D" — is genuinely N-ary (4+ simultaneous participants), which is the precise case where SQL (junction table) and RDF (manual reification) both visibly strain and hgai's native hyperedge does not. The same dataset was deliberately reused, rather than introducing a second unrelated example, to also carry the AI-memory narrative (requirement 4): an "AI-generated risk assessment" hyperedge was added to the same scenario, with explicit provenance/confidence/session fields, so the deck could show — with the same data, same file set — an agent's distilled conclusion being persisted and later retrieved for free.
- **Three parallel data files** (`staffing-hgai-import.yaml`, `staffing-rdf-comparison.ttl`, `staffing-sql-comparison.sql`) model the identical fact set three ways, so the visual/structural contrast (one hyperedge vs. a manufactured RDF resource plus ~7 triples vs. a junction-table row referencing three foreign keys) is directly comparable rather than asserted in prose.
- **Seven query files** — five real hgai HQL/SHQL queries (current roster, before/after a point-in-time labor-category change, a multi-hop SHQL join to each person's manager, and retrieval of the AI-generated hyperedge by tag) plus two comparison files (an equivalent SQL join query and an equivalent SPARQL query against the reified Turtle data) — give a presenter runnable, side-by-side artifacts for the same underlying business question, rather than only inline code snippets in the deck.
- **Presenter notes** were added as a distinct deliverable (not requested by name, but judged necessary to make the deck actually usable by a BD presenter who is not the platform's technical expert) covering timing, audience calibration, and honest answers to the hardest anticipated questions this specific audience is likely to ask — including a direct, non-defensive comparison to Palantir Foundry/Gotham, since that comparison is functionally guaranteed to come up in a room of defense-consulting BD staff and an unprepared presenter improvising an answer live is a real risk to get wrong.

## Key Decisions
- **Fictionalized all scenario specifics explicitly** (task order number, contract vehicle number, customer organization name, all personnel) and labeled them as such in both the deck and the data files, rather than using a real or thinly-veiled real defense program/customer name for flavor — chosen to eliminate any ambiguity about whether the example represents real government data or a real customer relationship, given the audience and the risk profile of getting that wrong in a defense-industry sales context.
- **Did not reuse the investor deck's revenue-stream/business-model framing** for this deck's closing section — that framing was written for investors deciding whether to fund HypergraphAI; this audience is potential adopters/partners/resellers deciding whether to use or represent the platform, so the closing section was written fresh around practice-area fit, internal-pilot sequencing, and a low-commitment next step (sandbox access, technical follow-up meeting) instead.
- **Verified SHQL/HQL syntax against the actual, currently-running system's proven query files** (`demo-alpha`) rather than the separate in-progress greenfield rebuild spec (`build-plan.md`) authored earlier in this same session — the two documents serve different systems (the real v1 product vs. a hypothetical v2 rebuild) and conflating their syntax would have shipped a demo artifact that fails against the system it claims to demonstrate.
- **Chose not to include a slide restating "SKOS inferencing is built in"** even though the existing investor deck in this same repo makes that claim — resolved in favor of the more conservative, verified claim (data model supports declaring inference relations; query-time evaluation is not yet wired up), on the judgment that this specific audience's own professional risk (representing capabilities to federal customers) outweighs the marketing appeal of the stronger claim.
