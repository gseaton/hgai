# Mutation Summary

## Intent
Every label, link label, and media thumbnail in the 3D visualization is a flat 2D `<div>`/`<img>` living in a single DOM overlay layer (`#viz-label-layer`) positioned on top of the WebGL canvas — a deliberate architectural choice from earlier turns (reusing the existing camera-projection math built for labels rather than doing true Three.js sprite/texture rendering, which was explicitly ruled out for cost/complexity reasons when thumbnails were added). That overlay approach has a real gap: DOM elements stack by plain DOM/paint order by default, with no inherent relationship to each element's actual 3D depth. A label or thumbnail for something far from the camera could — and did — paint over a label, thumbnail, or link-label belonging to something much closer, purely because it happened to come later in the array/DOM order, not because it was actually in front.

## Context
`vizLabelTick()` already runs on every animation frame and already computes, for every positioned element, a `dist` value via `vizProjectPoint()` — specifically the clip-space `w` term, which (established in an earlier turn, when it was first used for perspective-correct thumbnail *sizing*) equals camera-space depth for a standard perspective projection matrix. That same distance value is the natural, already-available signal for depth-correct *stacking* too — no new computation was needed, just a second consumer of a number the tick loop was already producing every frame for a different purpose.

## What Changed and Why
- **One shared z-index formula (`vizZIndexForDist`) applied identically across all three DOM-overlay element kinds** (node labels, link labels, media thumbnails), rather than three independent per-group scales, specifically so ordering is correct *across* kinds, not just within each — a hyperedge's relation-link label needs to be able to outrank a farther hypernode's name label, and vice versa, which only works if both are placed on the same numeric scale.
- **Recomputed every frame, not once at render time**, because the whole point is that depth ordering must track the camera as it moves — a static z-index assigned when the graph data loads would only be correct for the camera position at that instant, and would drift wrong the moment the user orbits, zooms, or pans (including the Shift+drag pan added a few turns ago).
- **`isolation: isolate` on `#viz-label-layer`** closes off a subtle correctness gap in the fix itself: CSS z-index on an element only stacks relative to *siblings within the same stacking context*. Without forcing `#viz-label-layer` to establish its own context, a very large or very negative z-index value assigned to one of its descendants could, in principle, participate in stacking decisions against elements *outside* the layer (the canvas, or other page chrome) if the browser's default stacking-context rules ever put them in the same context — a class of bug that's easy to introduce silently and hard to notice until some unrelated part of the page also starts using z-index. Isolating the layer removes that risk entirely, regardless of what values the per-frame formula produces.

## Key Decisions
- Did not attempt true Three.js depth-buffer integration (rendering labels/thumbnails as actual scene objects that occlude/are-occluded-by the real sphere and line geometry) — that would fix a *different*, more fundamental limitation (a DOM overlay element will still always paint in front of the raw WebGL geometry itself, regardless of this fix), but it's a much larger architectural change already explicitly deferred in an earlier turn's design discussion, and the user's report — specifically naming labels, media, and links, all of which are DOM-overlay elements — matches the DOM-vs-DOM ordering bug this fix addresses, not DOM-vs-WebGL occlusion.
- Used a large positive baseline (`1000000 - dist * 10`) rather than a raw negative z-index, purely for readability when debugging (positive z-index values in devtools are less confusing than large negative ones) — with `isolation: isolate` in place, the actual sign and magnitude don't matter for correctness, only the relative ordering does.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the already-running dev server (frontend-only change, no restart needed) and a freshly-created headless Chrome profile (established practice this session, to rule out stale-cache false negatives). Confirmed `vizZIndexForDist(100) > vizZIndexForDist(500)` (closer distance yields higher z-index) and that `#viz-label-layer`'s computed `isolation` style is `isolate`. Rendered the real `hello-world` graph with both labels and media thumbnails enabled, waited for the force-simulation and initial `zoomToFit` camera animation to fully settle (an early verification pass, taken before settling completed, produced spurious "violations" purely from comparing z-index set on one animation frame against distances recomputed moments later from still-moving node positions — a test-timing artifact, not an implementation bug, confirmed by re-checking with a longer settle wait), then captured every positioned label, link-label, and thumbnail's actual distance and rendered z-index and sorted by distance: 99 of 100 elements were in strictly correct z-index order, and the single exception was between two link labels separated by 0.01 world units of depth — effectively identical depth, and the visual difference at that scale is imperceptible; not the substantial-depth-difference bug being fixed. Full `pytest` suite: 45 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes. Left the dev server running afterward and killed only the headless Chrome test instance. `git status --short` shows `ui/js/app.js` and `ui/css/hgai.css` as this turn's changes.
