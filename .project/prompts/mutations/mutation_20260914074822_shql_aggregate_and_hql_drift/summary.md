# Mutation Summary

## Intent
Follow-through on a prior read-only assessment ("should HQL be sunset in favor of SHQL?") where the recommendation was: don't sunset HQL yet, but close the one real capability gap (SHQL has no `aggregate`/`group_by`) and fix small pieces of documentation/integration drift discovered along the way, as lower-risk, immediately-valuable steps regardless of the eventual sunset decision. The user approved and asked for exactly three of the recommended follow-ups to be implemented now.

## Context
- This session's prior turn established (via direct code reading, not speculation) that SHQL is already a near-superset of HQL — mesh dot-refs, space-scoped `from:`, point-in-time `at:`, `distinct`, `limit`/`offset`, and `infer:` are all already present in `hgai_module_shql/engine.py` — with `aggregate`/`group_by` the one feature that existed only in `hgai_module_hql/engine.py`.
- The project's own README documents an explicit `### HQL vs SHQL` comparison table and a `### Language Structure` YAML reference for SHQL, so both the table and structure listing needed updating alongside the engine change to avoid immediately reintroducing the same kind of doc drift the assessment had flagged.
- `ui/js/app.js`'s `fetchInferredEdges` (feeding the 3D visualizer's "Show inferred edges" toggle) was identified in the assessment as the one place the UI silently depended on HQL specifically, via a hand-built HQL query string, even though the rest of the "Query" UI offers both languages as peers.
- This codebase's own testing convention (per `tests/test_inference.py`'s comment: "matching this project's convention of unit-testing pure logic and live-verifying DB-dependent code") is to verify storage-backed query-engine behavior live rather than via mocked integration tests — followed here by standing up a throwaway MongoDB container + local server, seeding `hello-world`, and hitting the real `/shql/query` endpoint, rather than inventing new DB-mock test infrastructure that doesn't otherwise exist in the repo.

## What Changed and Why

**1. `aggregate`/`group_by` on SHQL (`hgai_module_shql/engine.py`)** — Added the `aggregate` field read and a computation block that is almost a literal copy of HQL's: same `count`/`group_by` keys, same "unknown" fallback for a missing field, same additive `**agg_results` spread into `meta`. Placed after DISTINCT dedup and before ORDER BY/OFFSET/LIMIT, so `count`/`groups` describe the whole matched result, not just the returned page — this is the only place in SHQL's pipeline structurally analogous to where HQL computes it (SHQL doesn't have anything positioned there today besides the dedup step). One real difference, documented in-code and in the README: an HQL item is the raw returned *document*, so `group_by: relation` reads a plain top-level key, while an SHQL item is a `select:`-projected *row* keyed by variable (e.g. `select: [?e.relation]` → row key `"e.relation"`) — `group_by` in SHQL names that projected key, not a raw entity field. This is a necessary consequence of SHQL's variable-binding model, not a shortcut.

  While implementing this, found and fixed a real, separate bug blocking the *next* item: `_eval_edge_pattern`'s inference block was gated `if infer and resolved_rel:`, but `expand_edge_closure` (the function it calls) is relation-agnostic — it reads each candidate edge's own `relation` field, exactly like HQL's equivalent call. The `resolved_rel` requirement only actually belongs to the transitive-reachability sub-check a few lines below, which does need a concrete relation to walk. Left as `if infer and resolved_rel:`, an edge pattern with no `relation:` filter and `infer: true` (i.e. "give me every inferred edge in the graph, any relation") would silently return nothing — which is exactly the shape of query item 3 needed to issue. Fixed by moving the `resolved_rel` check down to just the transitive sub-block.

**2. Fix known drift (`hgai/main.py`, `README.md`)** — `"shql"` added to the static `capabilities` list in `/api/v1/server/info` (it listed `"hql"` but never `"shql"`, even though the SHQL module has been mounted and stable for a while). The Roadmap bullet promising an "HQL `infer:` clause" was deleted — it's not just shipped, it described a syntax (`infer: transitive`) that isn't what actually shipped (`infer: true`, boolean), so it was doubly stale. The `### HQL vs SHQL` table and SHQL's `### Language Structure` block were updated for consistency with item 1 — aggregation is no longer an HQL-exclusive line item, and `aggregate:`/`infer:` were missing from SHQL's otherwise-exhaustive field listing.

**3. Migrate `fetchInferredEdges` off HQL (`ui/js/app.js`)** — Replaced the hand-built HQL query string and `HGAI_API.runQuery` call with an equivalent SHQL query (`where: [{edge: ?edge}]`, `infer: true`, `select: [?edge]`) and `HGAI_API.runShqlQuery`. Because SHQL projects rows keyed by variable rather than returning flat documents, the result-parsing step now unwraps `row.edge` before applying the existing `_inferred` filter — the synthesized-edge shape itself (`relation`, `flavor`, `members`, `_inferred`, `_source_edge`, `_axiom`) is identical either way, since both languages ultimately call the same `hgai/core/inference.py` primitives. Also added a parallel `'Aggregate: count by relation'` entry to `SHQL_EXAMPLES` (mirroring the existing HQL example of the same name) so the new capability is discoverable in the Query (SHQL) screen's Examples panel.

## Key Decisions
- **Where to insert the aggregate block in SHQL**: chosen to run pre-pagination (before ORDER BY/LIMIT/OFFSET) rather than post-, so `count`/`group_by` reflect the whole matched result rather than one page — the only sensible aggregate semantics, and the position HQL's equivalent occupies relative to its own (different) pagination mechanism.
- **Fixing the `resolved_rel` gating bug rather than writing the migrated query around it**: the alternative — keeping a `relation:` filter in `fetchInferredEdges`'s SHQL query to dodge the gate — would have changed its actual semantics (only expanding one relation's edges, not "every inferred edge in the graph," which is what the viz toggle promises). Fixing the underlying gate was the only option that actually satisfies "migrate to SHQL syntax" rather than "migrate to a narrower SHQL query."
- **Verification approach**: followed the project's own stated convention (unit-test pure logic, live-verify DB-dependent code) rather than introducing new mocked-storage test infrastructure that doesn't exist elsewhere in the repo. Stood up a disposable MongoDB container + local server, seeded `hello-world`, added an `owl:inverse-of` axiom edge, and hit `/api/v1/shql/query` directly to confirm: (a) the aggregate query returns `meta.count: 4` / `meta.groups: {has-member: 3, sibling: 1}` as expected; (b) the bare `- edge: ?edge` + `infer: true` query (exactly what `fetchInferredEdges` now sends) returns 5 synthesized `_inferred: true` "member-of" edges alongside the 5 literal edges — proving both the aggregate port and the gating-bug fix work end-to-end, not just by code inspection. The container and server were torn down afterward; no state persists from this verification.
- Ran the full existing test suite (`pytest tests/`) before and after via `git stash` — confirms 3 pre-existing `test_mesh.py` failures are unrelated to this change (identical failures with the change stashed out), and all 84 other tests (including all HQL/SHQL/inference suites) pass unchanged.
