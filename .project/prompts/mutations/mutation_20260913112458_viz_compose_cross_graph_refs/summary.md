# Mutation Summary

## Intent
Two immediately preceding turns established that `project_inference()`'s `only_new_hyperedges=True` mode deliberately leaves a projected edge's member references bare/unmodified (no graph-qualified dot-prefix), on the basis that a bare reference already resolves correctly once the target (hyperedges-only) graph is queried *alongside* its canonical source graph(s) via HQL/SHQL's multi-graph `from:` semantics. The user now asked for the 3D Visualization to honor that exact same composed-query semantic: when multiple graphs are selected together for viewing, a bare member reference that doesn't resolve within its own graph should resolve against any of the *other* currently-selected graphs too — both for the specific "hyperedges-only graph + its canonical source" scenario, and more generally for any two (or more) selected graphs where one references something the other defines.

## Context
`renderViz()` already had a cross-graph resolution mechanism from an earlier session turn (`vizParseMemberRef`/`crossGraphNodes`/the `crossHit` field on `vizMemberTargetId`'s return value), but it only activated for *explicitly* graph-qualified references (`bravo.person:john`) — a bare reference was only ever checked against its own hyperedge's graph. This left exactly the gap the user described: a hyperedges-only projected graph's bare member references (the correct, intended shape as of the immediately preceding turn) had no way to resolve to a canonical node in a *different*, also-selected graph — they'd simply show as unresolvable, dropped from the visualization entirely, even with both graphs selected side by side.

## What Changed and Why
- **Extended the existing resolver rather than building a new mechanism.** `vizMemberTargetId` already had three concerns cleanly separated (dot-qualified cross-graph, own-graph bare, not-found) with a `crossHit`-based lazy-materialization path in Pass B already built to handle "this target isn't in `nodesById` yet." Adding a fourth branch — bare reference, search other selected graphs — needed no new plumbing: it reuses the identical `crossHit` shape (`{vizId, raw, isEdge}`) the dot-qualified path already produces, so Pass B's materialization logic didn't need to change at all.
- **"Own graph first" precedence is structural, not an extra check.** The new fallback loop only runs *after* the existing own-graph `nodeIdSet`/`hedgeIdSet` checks have already failed to match — so a hyperedge in graph B referencing an id that genuinely exists locally in graph B never even reaches the cross-graph fallback, regardless of whether some other selected graph happens to share that same id. Verified explicitly (see below) with a deliberately ambiguous case: two selected graphs both defining `person:shemp`, confirming the referencing edge's own graph's copy always wins.
- **"First match wins" among other selected graphs**, in `graphIds`' own order (the multi-select's selection order) — the same "no guessing across multiple candidates" precedent this codebase already applies elsewhere (e.g. `_ensure_member_exists`'s now-mostly-retired source-graph search, which used the identical `for src_gid in source_graph_ids: ... return first match` pattern). Genuine ambiguity (the same id meaningfully existing in two DIFFERENT graphs neither of which is the referencing edge's own) is a rare, inherently ambiguous case with no clearly "more correct" answer — a deterministic tie-break is preferable to either erroring or silently picking randomly.
- **A reference resolved this way is NOT flagged `crossGraph: true`/given the dashed "external reference" styling** in the common case, unlike the dot-qualified path. This is a deliberate, structural consequence of reusing Pass A's already-pushed nodes: since the target graph is, by definition, one of the graphs the user directly selected to view, its nodes are already present as ordinary content by the time Pass B runs — there's nothing "external" about it from the viewer's perspective, unlike the dot-qualified case where the referenced graph might not be selected/visible at all. The dashed styling still correctly applies in the one remaining edge case where it's warranted: the target graph's own copy of that node was hidden by the orphan-nodes toggle, so the `crossHit` fallback genuinely does materialize a stand-in — verified this distinction empirically rather than assuming it (see Verification).

## Key Decisions
- Considered flagging every reference resolved via the new fallback as `crossGraph: true` regardless, for a uniform "this came from resolution logic, not a plain local hnode push" visual signal. Rejected: it would mislabel the overwhelmingly common case (both graphs directly selected, the whole point of "composing hypergraphs for Visualize") as "external" when the referenced node is, in every meaningful sense, just as present and selected as anything else in the scene — the dashed/amber treatment is specifically meant to flag "you're seeing something you didn't directly select," which doesn't apply here.
- Confirmed the choice to scope the fallback to only *other currently-selected* graphs (not, say, every graph the app knows about via `State.graphsCache`) matches both the user's own framing ("included hypergraph B", "included hypergraph A" — i.e. graphs the user has deliberately brought into view together) and the underlying HQL/SHQL precedent this mirrors, where a query's `from:` list is exactly the set of graphs in scope for resolution — nothing outside it is searched.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the running dev server (no restart needed — frontend-only change) and a freshly-created headless Chrome profile. Built isolated test data mirroring the user's own example exactly: `viz-canon` (a canonical source graph with real `person:shemp`/`person:moe` hypernodes) and `viz-inferonly` (a hyperedges-only graph with one hyperedge whose members are the bare, unqualified ids `person:moe`/`person:shemp` — deliberately not dot-qualified, matching the corrected projection output from the two immediately preceding turns) — both deleted afterward.

- **Both graphs selected together**: the scene correctly contained exactly one `person:shemp` node (`viz-canon::person:shemp`, the real canonical one — no duplicate, no separately-materialized stub) and the hyperedge's relation link correctly pointed at it; both resolved members showed `crossGraph: false` (ordinary, unflagged nodes), confirming the "already present via Pass A, no external styling" design choice.
- **Only `viz-inferonly` selected** (canon not selected): the henode correctly showed `arity: 0` and no `person:shemp`/`person:moe` nodes were created at all — confirming the fallback is correctly scoped to *currently-selected* graphs only, not a blanket search across every graph the app has ever seen, and that an unresolvable-in-scope reference still degrades gracefully exactly as before.
- **Precedence test**: added a *second*, distinct `person:shemp` hypernode directly inside `viz-inferonly` itself (deliberately colliding with `viz-canon`'s), re-rendered both graphs together, and confirmed the hyperedge's relation link correctly pointed at `viz-inferonly::person:shemp` (its own local copy) rather than `viz-canon::person:shemp` — both nodes were present in the scene independently (each graph's own real content, as expected), but only the local one was ever chosen as the link target.
- **No regressions across mixed renders**: installed a global `error`/`unhandledrejection` listener and cycled through four graph-selection combinations, including a 3-graph render mixing real demo data (`hello-world`) with both test graphs — zero JS errors in any of them.

Full `pytest` suite: 84 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes.
