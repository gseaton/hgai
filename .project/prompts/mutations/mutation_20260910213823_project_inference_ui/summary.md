# Mutation Summary

## Intent
Complete the one piece of Step 6 (materialization) explicitly deferred in the prior turn: a dedicated UI screen for "Project Inference," so a user can select source hypergraph(s), choose what to project, pick or create a target hypergraph, preview the result, and commit — without needing to script curl calls against the REST API built in the previous turn.

## Context
The backend (`project_inference` engine function, `POST /graphs/{graph_id}/infer/project` REST route) was already built and verified in the prior turn, but only supported an immediate-write call shape — there was no way to see what a projection would do before it did it. This app has an established, explicit convention for exactly this situation (first built for the clone/duplicate feature, then the mutation-history audit trail): never let a write happen without the user seeing what it will produce first. Building the screen surfaced that the backend itself needed a small but real addition — a `dry_run` mode — to honor that convention properly, rather than trying to fake a preview client-side from data the backend didn't expose (e.g., which candidates would be skipped as duplicates, which the client has no way to know without asking the server).

## What Changed and Why
`project_inference` and its REST route both gained `dry_run`, and the return shape was generalized to a `preview` list — every candidate tagged `new`/`skip`/`error` — populated identically whether previewing or committing, so the exact same UI rendering code handles both states (a "Preview" heading with counts before commit, a "Result" heading with the same shape plus real edge ids after). `dry_run=True` also suppresses target-hypergraph auto-creation, so previewing a projection into a not-yet-existing graph creates nothing at all, not even the graph itself.

The UI screen follows the same source-graph multi-select pattern already used by Visualize, the same id/label fields already used by the "New Hypergraph" creation form, and a card-list rendering style consistent with the mutation-history timeline built earlier this session. The two mode checkboxes (Expand axioms / Transitive closure) map onto the backend's single `mode` string (`"expand"`, `"transitive"`, or `"both"`) rather than exposing that internal representation directly, since "pick one or both of these two things" is the more natural UI shape. The commit button is disabled by default and re-disabled on *any* form change, only re-enabling after a fresh Preview whose request exactly matches what would be sent on commit — this is the concrete mechanism enforcing "never write without a shown preview," not just a suggested workflow.

Live browser verification exercised the complete flow against a real (isolated) server and database: selected a source graph, chose "New hypergraph" as target, ran Preview (correctly showing "1 would create, 0 already exist" with the exact superproperty-projected fact from the seeded axiom+fact data), committed via "Confirm & Project" (correctly showing "1 created, 0 already exist" with the real edge id), then ran Preview again with no changes and confirmed it now correctly reports "0 would create, 1 already exist" with a SKIP badge — the idempotency property from the prior turn's backend work, now visibly confirmed through the actual UI a user would use.

## Key Decisions
- **`dry_run` was added to the backend in this turn, not deferred** — building the UI screen made concrete what the prior turn's engine/REST-only delivery couldn't fully support (a real preview, not a guess); this is exactly the kind of gap that surfaces by building the actual consuming surface rather than stopping at "the API exists."
- **One `preview` list shape serves both preview and commit states** — avoided building a separate "preview result" and "commit result" rendering path; the only material difference is the heading text and whether entries carry a `created_edge_id`.
- **The commit button's re-enable condition compares the exact serialized request, not just "was Preview clicked at some point"** — changing the source selection, mode, relation, PIT, or target after a preview correctly invalidates it and requires a fresh Preview, closing the same class of "you approved X but I did Y" gap this app has consistently guarded against elsewhere this session.
- **A real bug during manual verification turned out to be browser HTTP caching**, not application code: the test browser tab had cached an older `api.js` from earlier in this same session (before `projectInference` was added), producing an `HGAI_API.projectInference is not a function` error that looked like a shipped bug until confirmed via `curl` that the server was serving the correct, updated file, and a hard reload (`Ctrl+Shift+R`) resolved it. Noted here so it isn't mistaken for an application defect on a future read of this history.
- Full test suite: 72 passed (unchanged — this turn's changes are UI- and dry-run-flow-specific, verified live rather than via new unit tests), same 3 pre-existing unrelated `test_mesh.py` failures.
