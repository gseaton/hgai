# Mutation Summary

## Intent
The user supplied a reference illustration, `docs/design/hypergraphai-hyperedge-virtual-3d-graph-via-representation.png` (a slide titled "HypergraphAI - 3D Visualization of Hyperedges"), and asked for the Visualize tab's 3D layout to be refactored to follow it as an example of how to illustrate a hyperedge in 3D.

## Context
The image shows a clean, top-down, three-tier box diagram for a single example hyperedge (`edge:original-stooges`, flavor `hub`, 4 members): a rounded-rectangle box for the hyperedge itself at the top, connected straight down by an arrow labeled `flavor/hub` (bold magenta) to a "hyperedge/members" box (with "members" itself highlighted green), which then fans out via four curved, bold-orange `rel:member` arrows to four member boxes (`group:three-stooges`, `person:moe`, `person:larry`, `person:shemp`) arranged in a row along the bottom. Every box — hyperedge, members, and member nodes alike — shares the same neutral light-grey style; all the color in the diagram lives on the edge labels, which encode structural role (flavor-edge vs. relation-edge) rather than the specific flavor or relation value (that's carried in the text).

The prior 3D implementation (from the last two Visualize mutations) already built the correct hyperedge→"hyperedge"-link→"members"→relation-links→member structure and had per-flavor rainbow coloring plus a physics-driven organic layout with no imposed hierarchy — visually, multiple hyperedges just floated in one undifferentiated cloud, and node colors carried flavor information the diagram doesn't attempt to convey at all (the diagram is about structural illustration, not domain-typing).

## What Changed and Why
- **Explicit 3-tier vertical layering**: added a custom d3-force (`vizLayerForce`) that pulls hyperedge nodes toward Y=+160, virtual "members" nodes toward Y=0, and real member hypernodes toward Y=-160, layered on top of the existing charge/link/center forces `3d-force-graph` already runs. This generalizes the diagram's single-hyperedge top-down hierarchy to a full multi-hyperedge scene: all hyperedges settle into a shared top layer, all their "members" hubs into a shared middle layer, and all real entities into a shared bottom layer, with X/Z spread still handled by the normal physics forces. Verified live that average Y per tier separates in the expected top>middle>bottom order and a wide screenshot shows the intended stacked structure.
- **Nodes restyled as boxes, not colored spheres with floating text**: the existing DOM-overlay label system (built in the prior mutation for the label on/off toggle) was extended so node labels render as actual rounded-rectangle chips (light background, dark text, border, shadow) sitting over each node's WebGL sphere — much closer to the diagram's box style than the previous plain drop-shadowed floating text. The underlying spheres are kept (small, colored by entity type for hypernodes) purely as click targets and a subtle depth cue; they're no longer the primary visual carrier.
- **Color moved from nodes to edges, encoding structural role**: dropped the five-color flavor palette entirely. The hyperedge→members link is now always the diagram's magenta (`#be185d`), labeled `flavor:<flavor>`; every members→member link is always the diagram's amber (`#f59e0b`), labeled with the hyperedge's relation. The specific flavor/relation value is no longer lost — it's still fully present in the label text — but the *color* now consistently signals "this is a flavor-edge" vs. "this is a relation-edge" everywhere in the scene, matching how the reference diagram uses color. Hypernode entity-type coloring (a genuinely useful signal for exploring real domain data that the reference diagram doesn't address) was deliberately kept on the underlying spheres rather than discarded, so this is colored by structural role on the edges plus entity type on the (secondary) spheres, rather than a wholesale copy of the diagram's fully-neutral node treatment.
- **Hyperedge node label fixed to show the hyperedge's own identity**: previously the top box displayed the hyperedge's *relation* string; the reference diagram's top box instead shows the hyperedge's own `id` (`edge:original-stooges`). Fixed the `henode` label to prefer the hyperedge's own `label`/`id`/`hyperkey`, with `relation` moved to a separate field surfaced in the hover tooltip — this was a real mismatch the reference caught, not just a styling change.
- **"members" node gets a green accent**, echoing the diagram's green-highlighted "members" word within its "hyperedge/members" label — implemented as a CSS modifier class rather than literally reproducing the compound label text, since the app already displays "members" as its own dedicated node.
- **Legend simplified** from a per-flavor color list to a fixed two-row "edge kind" key (flavor-edge magenta, relation-edge amber), matching the new fixed edge-kind coloring; hypernode type-color entries are unaffected.

## Key Decisions
- **Layering via a custom force, not fixed coordinates**: pinning nodes to exact fixed positions (`fx`/`fy`/`fz`) was considered but rejected in favor of a soft pull-toward-tier force, so nodes within a tier still get natural physics-based spacing (via the existing charge/link forces) instead of a rigid, overlap-prone grid — this keeps the scene readable and interactive (draggable, still influenced by search/highlight) rather than static.
- **Kept type-based coloring on hypernode spheres despite the reference diagram being fully neutral**: the diagram is a generic illustration of hyperedge *structure* and doesn't address domain entity typing at all, whereas this app is used to explore real hypergraphs where "what kind of thing is this node" is valuable at-a-glance signal, backed by the existing type legend/filter feature. Moving all color onto the edges (matching the diagram) while preserving type color on nodes' underlying spheres (not carried over to the new diagram-style requirement) was judged the best balance between fidelity to the requested reference and not regressing a feature the user hasn't asked to remove.
