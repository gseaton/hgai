# Mutation Summary

## Intent
Immediately after adding the `mutations` audit-trail field and its display in the read-only View/Detail modal (previous session turn), the user asked for the same history to also be visible — but strictly read-only — inside the Edit modals for hypernodes and hyperedges themselves, so a user editing a record can see its change history without switching to the separate View action.

## Context
The `mutations` field and its rendering helper (`renderMutationHistory()` in `ui/js/app.js`) already existed from the prior turn, wired only into `showDetail()` for the View (eye icon) modal. The edit modals (`modal-node`, `modal-edge` in `ui/index.html`, driven by `openNodeModal()`/`openEdgeModal()` in `ui/js/app.js`) already had an established section-based layout (Identity → Classification → Temporal Validity → [Members, edges only] → Media → Attributes), and already distinguish edit mode from create/clone mode via the `isEdit`/`isClone` flags introduced by the earlier clone/duplicate feature.

## What Changed and Why
Rather than duplicating the rendering logic, `renderMutationHistory()` was generalized to take a `containerId` and a `showHeading` option, so the same function serves both the View modal (own heading + visibility toggle on itself) and the new edit-modal History section (no redundant heading, since the section already has one via its `node-form-section-header`).

A new "History" section was added as the last section of both edit-modal forms, explicitly labeled "read-only audit trail" in its subtitle so it's unambiguous to the user that this is inspection-only — it contains no form inputs, just the rendered timeline, so there was nothing to make "read-only" beyond not putting form controls there in the first place. The section starts hidden (`d-none`) and is only ever shown inside `openNodeModal`/`openEdgeModal`'s true-edit branch, immediately after that branch successfully fetches the existing record and populates the rest of the form — matching exactly when a "history" meaningfully exists. It is explicitly kept hidden for both the plain-create path and the clone path (even though clone pre-populates fields from a source record's content, per the earlier clone feature, the clone target is a brand-new record and correctly has no mutation history of its own until saved).

## Key Decisions
- **Reused the existing `renderMutationHistory` function via a generalization rather than writing a second renderer** — the delta-formatting and timeline-item logic (badges, `field: old → new` rows) is identical between the View modal and the edit modals; only the heading and container differ, which a parameter covers cleanly without duplicating markup logic.
- **Section hidden by default, shown only for genuine edits** — placed the show/populate call inside the same `try` block that already fetches and populates the rest of the edit form, so a fetch failure (existing silent `catch {}` behavior, unchanged) also naturally leaves history hidden rather than showing a stale or empty section.
- **Verified live in the browser** against a third isolated test server + throwaway MongoDB database (created via curl, never touching the user's real server): confirmed the Hypernode edit modal shows the correct 2-entry MUTATE/CREATE history at the bottom, confirmed the "New Hypernode" (create) modal has no History section at all, and confirmed the Hyperedge edit modal shows its own correct history (including a `members` delta rendered as JSON) — then tore down the test server and dropped the database. Full test suite re-run clean afterward (57 passed; same 3 pre-existing unrelated `test_mesh.py` failures as before).
