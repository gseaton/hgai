# Mutation Summary

## Intent
Give the AI Agent Chat feature (completed across the prior four phases) the ability to fetch and read the content of a web page as part of answering a chat prompt — e.g. "read this URL and summarize it," or a page referenced by a hypergraph's own data.

## Context
The chat agent's tool set was already extensible by design (`engine.build_agent()`'s `tools=[...]` list) and the project had just established a clear precedent in Phase 2 for *how* to add a tool: a small, purpose-built custom Agno `Toolkit` rather than reaching for a heavier off-the-shelf option whose behavior or dependency footprint doesn't quite fit (that precedent was `HgaiMcpToolkit`, built instead of `agno.tools.mcp.MCPTools` to avoid a dependency-version conflict). The same reasoning applied again here: Agno ships `agno.tools.website.WebsiteTools`, but its `read_url()` defaults to crawling up to 3 levels deep and 10 links per call — a real mini-crawler, not a single-page read, and a surprising amount of unbounded latency/token cost to trigger from one chat tool call. A user asking "read this page" reasonably expects exactly one page fetched, not an unbounded crawl of whatever it links to.

Because this tool's URL argument can originate from an LLM tool call — and that LLM has, by design, already been reading content from other web pages and hypergraph data in the same conversation — the request surface is untrusted in a way most of this project's other endpoints aren't: a page the agent read earlier, or the hypergraph data itself, could contain text engineered to get the model to "helpfully" fetch an internal address on the next turn (classic prompt-injection-to-SSRF chaining). This was treated as a real risk to design against up front, not an afterthought: the OWASP-adjacent SSRF category is exactly the kind of vulnerability the project's own standing engineering guidance calls out to actively avoid introducing.

## What Changed and Why
`web_toolkit.py`'s `_check_url_safety()` resolves the target hostname and rejects it if any resolved address is loopback, RFC1918/ULA private, link-local (which includes the `169.254.169.254` cloud-metadata address many SSRF exploits specifically target), reserved, multicast, or unspecified — using Python's stdlib `ipaddress` module, so this needed no new dependency. Critically, this check re-runs at *every* redirect hop the fetch follows (the code manually loops over redirects rather than letting `httpx` auto-follow them), not just against the URL the model originally asked for — a same-origin-looking URL that 302s to an internal address is a well-known way to slip past a check that only validates the first hop, so `follow_redirects=False` was used deliberately to keep control of that validation.

Response handling caps total size at 2MB (streamed, so an oversized response is aborted mid-download rather than after fully downloading it) and only actually processes HTML/plain-text/JSON content types — anything else (a PDF, an image, arbitrary binary) gets a clear "unsupported content type" message instead of raw bytes dumped into the model's context. HTML is parsed with BeautifulSoup: script/style/nav/header/footer tags are stripped before extracting visible text, and the result is truncated to 12,000 characters with an explicit note if it was cut — bounding both the token cost of one fetch and the chance of a single huge page derailing the rest of the conversation's context budget.

## Live Verification
Verified in three layers, following the same discipline as every other network-touching piece of this feature:
1. Pure-logic unit tests (IP classification, URL safety with DNS mocked, HTML extraction, truncation) — no network dependency, safe for CI.
2. A direct spike script: a real Agno `Agent` (real Claude Haiku call) successfully used the tool via Agno's default docstring/type-hint introspection (not the manual JSON-schema path `HgaiMcpToolkit` needed) to fetch `https://example.com` and correctly reported its heading; separately, direct calls confirmed the SSRF guard blocks `http://127.0.0.1:8357/...`, `http://169.254.169.254/...`, and `file:///etc/passwd`, and that a real http→https redirect chain (`http://example.com`) still resolves correctly.
3. Full browser verification through the actual chat panel: asked the live agent (Claude Sonnet 5) to fetch `https://example.com` and got the correct heading back through the real UI; then asked it to fetch the server's own `http://127.0.0.1:8357/api/v1/agent/vendors` — the tool correctly refused, and the model itself explained the refusal to the user in plain language (a second, independent layer of defense on top of the tool-level block). Zero console errors throughout.

Test artifacts (chat sessions created during verification, the temporarily re-enabled vendor/model) were cleaned up afterward, restoring the vendor/model catalog to the same disabled default state Phase 4 left it in.

## Key Decisions
- **Custom single-page fetch tool over `agno.tools.website.WebsiteTools`**: bounded, predictable cost and latency per tool call, matching what a chat user actually expects from "read this page."
- **Manual redirect loop with `follow_redirects=False`, re-validating safety at every hop**: the only way to close the redirect-based SSRF bypass; letting `httpx` auto-follow redirects would only validate the URL the model provided, not where it actually ends up.
- **Reject unsupported content types outright rather than attempting to process everything**: protects both cost (a giant binary file) and correctness (garbage text extracted from a non-HTML payload) with a clear, actionable message back to the model instead of silently doing the wrong thing.
