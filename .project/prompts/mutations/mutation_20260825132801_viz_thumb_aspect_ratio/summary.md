# Mutation Summary

## Intent
The immediately preceding turn made the 3D visualization's default-media thumbnails scale correctly with camera zoom, but forced every thumbnail into a fixed square sized to match the node's sphere, then cropped that square into a circle via CSS (`object-fit: cover; border-radius: 50%`). For any image whose real proportions weren't square — which is most real photos — `cover` crops whatever doesn't fit the square, and the circular mask then crops further still, discarding real image content (a face at the edge of a portrait, a caption strip along the bottom, etc.). The user wanted the actual image proportions preserved — nothing forced into a circle, nothing cut off.

## Context
The previous turn already established the sizing pipeline this fix extends: `vizLabelTick()` computes a "target size" per frame from the node's sphere radius and current camera distance, matching the sphere's own perspective-correct on-screen size. That target size was previously applied identically to both width and height (a forced square), then the CSS cropped that square to a circle. Fixing the crop required going one step further back than the CSS — the browser doesn't know an image's real proportions until it's actually decoded, so the aspect ratio has to be captured once (when the thumbnail's blob first loads) and then factored into the per-frame sizing math the same way distance already is.

## What Changed and Why
- **Aspect ratio is read once, from the decoded image, not guessed or hardcoded.** `vizLoadThumbnails()` already sets each `<img>`'s `src` to a freshly-created blob URL; it now waits for that image to actually finish decoding (the `load` event) before reading `naturalWidth`/`naturalHeight` off it, and stores the ratio on that thumbnail's tracking entry. This is the one genuinely new piece of async work in this fix — everything downstream just consumes the resulting number.
- **The target size still comes from the sphere (per the previous turn), but now bounds only the larger dimension.** For a wide image, the target size becomes the width and the height is derived (`target / aspect`); for a tall image, the reverse. This keeps the "same size as the geometric shape, respects zooming" behavior from the previous turn intact — the thumbnail's largest extent still tracks the sphere's on-screen size at the current camera distance — while letting the smaller dimension be whatever it needs to be to keep the image's real proportions, rather than stretching or cropping it to force a square.
- **`object-fit: contain` replaces `object-fit: cover`, and `border-radius` dropped the circular mask.** With width/height now set to the image's exact real proportions, there should be no cropping or letterboxing left for `object-fit` to do at all — `contain` is kept purely as a defensive fallback for any sub-pixel rounding in the size calculation, not as the mechanism actually preventing cropping (that's the aspect-ratio-aware sizing itself). The border-radius became a small rectangular rounding (`6px`, matching the same convention already used for the Nodes/Edges table thumbnails) instead of a full circle, since forcing a circular mask onto a rectangular, unstretched image would just reintroduce the exact cropping problem being fixed.
- **Left the Nodes/Edges list-table thumbnails (`.table-thumb`) untouched.** Those already crop to a fixed small square via `object-fit: cover` — but the user's report specifically named "the media graph visualization," and a small fixed-size grid-cell thumbnail in a table row is a different, more conventional UI pattern (like a file browser or inbox) where uniform cropping is expected and the image is a secondary affordance, not — as in the 3D visualization — the primary visual representation standing in for the node itself.
