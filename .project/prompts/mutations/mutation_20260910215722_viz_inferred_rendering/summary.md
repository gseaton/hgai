# Mutation Summary

## Intent
Surface the inferencing engine's results (built over the prior several turns of this session) in the Visualize 3D graph screen, so a user can see facts that are logically implied by declared axioms (inverse-of, symmetric, superproperty/broaderTransitive relations) overlaid on the literal hypergraph, without those facts ever being persisted. This was the last explicitly requested piece of the inferencing plan — deferred once when Step 5 scoped it out of the HQL/SHQL/MCP/REST surfacing work, and offered again as a next step after the Project Inference materialization UI was completed last turn.

## Context
The reasoning engine (`hgai/core/inference.py`) and its `infer: true` trigger were already fully wired through HQL, SHQL, MCP, and REST in prior turns of this session, with a separate explicit "Project Inference" UI for materializing results permanently. The Visualize screen itself already had an established architecture for rendering hyperedges as a henode + virtual "members" node + "hyperedge" link + per-member "relation" links, all flowing through one generic per-edge construction pass (Pass A / Pass B in `renderViz()`), plus an existing `_dim` flag mechanism for type-filtering that needed to stay orthogonal to any new coloring. The scope decision — deliberately fetching only axiom-expansion results here, not transitive-closure — follows from `check_transitive` needing a targeted start/end pair or relation, which doesn't fit a "render the whole graph" query; that case is better served by the dedicated HQL/SHQL/REST/MCP surfaces already built.

## What Changed and Why
Because inferred edges are already returned by the existing `infer: true` HQL query path as plain edge-shaped objects (tagged `_inferred: true`, `_source_edge`, `_axiom`), no new rendering code path was needed — the fix was to fetch them opt-in (via a new "Show inferred edges" checkbox) and thread one boolean flag (`_inferred`) and one color constant (`VIZ_INFERRED_COLOR`) through the *existing* generic construction pipeline that already builds henodes, members-nodes, and relation-links identically for every edge, literal or inferred. This is why the change touches many small call sites in `app.js` (henode creation, members-node creation, link creation, tooltip builder, click handlers, legend) rather than adding a parallel rendering path.

A distinct color (a purple/lavender `#c084fc`, chosen to be visually unlike any existing flavor or relation-link color) was used instead of a dashed-line or opacity treatment, since 3d-force-graph link dashing is unreliable across renderers and a solid distinct color reads clearly at a glance in a 3D scene. The inferred fetch was placed before focus-filtering in `renderViz()`'s Phase 1 so inferred edges participate in the same neighborhood-BFS truncation and filtering logic as literal edges, rather than being bolted on afterward as a special case.

## Key Decisions
- **Axiom-expansion only, not transitive-closure, for this fetch.** `check_transitive`'s closure/path modes need a specific start point (or at minimum a relation to walk), which doesn't compose with "render this whole graph's neighborhood." Transitive reachability stays reachable via HQL/SHQL/REST/MCP, not the Visualize screen.
- **One `_inferred` flag reused everywhere, no separate inferred-rendering path.** Every place that already branches on data (color pickers, tooltip builder, click handlers) got one extra ternary/conditional rather than a parallel code path, keeping the existing `_dim` (type-filter) mechanism automatically compatible — confirmed by reading `vizRecomputeDim()` before making changes, since `_dim` is checked first in every color accessor.
- **Verification used direct JS execution against the live `State.viz3d` graph instance and `vizShowDetail()`, not raw pixel clicks.** 3d-force-graph's underlying three.js OrbitControls treats any sub-pixel mouse jitter between mousedown/mouseup (inherent to synthetic browser-automation clicks) as a camera drag, which silently cancels the raycast click event without erroring — a known friction point of testing WebGL canvases via automated clicks, not an application defect. Since the color, tooltip, and legend were already confirmed via screenshots, the click-handler code path was verified by (a) reading the exact `onNodeClick` source and (b) invoking `vizShowDetail()` in the page context with the same object shape the real handler constructs from a live inferred node's data (`State.viz3d.graphData()`), confirming the Element Details panel renders `_inferred: true`, `_source_edge`, and `_axiom` exactly as expected.
- Full test suite: 72 passed (unchanged — this turn touched only `ui/index.html` and `ui/js/app.js`, verified live rather than via new unit tests), same 3 pre-existing unrelated `test_mesh.py` failures.

## Live Verification Performed
Seeded an isolated hypergraph `vizinfer` (server on port 8399, database `hgai_viz_infer_verify`) with hypernodes `rel:parent`, `rel:father`, `person:adam`, `person:cain`, `person:abel`, an axiom hyperedge (`skos:narrowerTransitive` over `[rel:parent, rel:father]`), and a fact hyperedge (`rel:father` over `[person:adam, person:cain, person:abel]`, flavor hub). In the browser: selected the graph in Visualize, enabled "Show inferred edges", clicked Render, and confirmed:
- The inferred `rel:parent` henode, its members-node, and the connecting "hyperedge" link all rendered in `#c084fc` (matching `VIZ_INFERRED_COLOR`), distinct from the orange (`flavor:hub`) and blue (`rel:* edge, first member`) colors of the literal edges.
- The legend gained a "⚡ inferred" swatch row.
- Hovering the inferred members-node showed the tooltip note "⚡ inferred — computed live, not persisted".
- The Element Details panel (invoked via the actual `vizShowDetail()` rendering function with the live node's data) showed `_inferred: true`, `_source_edge` pointing at the `rel:father` fact edge's id, and `_axiom` pointing at the `skos:narrowerTransitive` axiom edge's id — confirming full provenance is surfaced.

Test server killed and `hgai_viz_infer_verify` database dropped after verification; the user's real running dev server (port 8357) and its data were never touched.
