# Mutation Summary

## Intent
The user asked for the Visualize tab (built in `mutation_20260824072725_hypergraph_visualization_tab`, then adjusted in `mutation_20260824130927_hyperedge_bag_refactor`) to become a 3D visualization, and to follow the specific hyperedge-representation design already written down in `docs/architecture/hypergraph-3d-viz.md`, which the user had authored/staged separately.

## Context
`docs/architecture/hypergraph-3d-viz.md` specifies an exact graph structure for rendering one hyperedge in 3D: the hyperedge itself is a node; a *virtual* edge labeled `"hyperedge"` connects it to a *virtual* node labeled `"members"`; and from that `"members"` node, one edge per participant fans out to the member's node, each such edge labeled with the hyperedge's relation (`rel:member` in the doc's example). The doc explicitly calls both the `"members"` node and the `rel:member` edges "virtual … for 3D visualization" — i.e. these don't correspond to persisted entities, they exist purely to make the hypergraph's structure legible as a drawable 3D graph. This is a more elaborate variant of the incidence-graph technique used in the prior 2D "bag" mutation: instead of the hyperedge node connecting directly to each member, there's an intermediate "members" hub per hyperedge.

The prior implementation used Cytoscape.js, a 2D graph-drawing library; rendering "in 3D" required a different rendering engine. `3d-force-graph` (vasturiano, built on Three.js + d3-force-3d) was chosen because, like Cytoscape, it ships a single self-contained UMD bundle usable via a plain `<script>` tag with no build step — consistent with how every other library in this project (Bootstrap, CodeMirror, and the just-removed Cytoscape) is loaded from a CDN. Modern three.js itself (0.179+) no longer ships a global/UMD build, only ES modules, so a plan to use custom Three.js geometries for node shapes (e.g. distinct cube/sphere/tetrahedron shapes per node kind) was dropped in favor of differentiating node kinds by color and size only — this avoided introducing `<script type="module">` / import-map machinery into an otherwise plain-script codebase for a cosmetic upgrade.

## What Changed and Why
- **Graph structure now matches the doc exactly.** For each hyperedge `e`, `renderViz()` in `ui/js/app.js` creates: a `henode` (the hyperedge, colored by flavor, sized by member count), a `members` node (small, grey, flagged as virtual — `raw: null`, with a `parentRaw` back-reference to the hyperedge), a `hyperedge`-kind link from the henode to the members node, and one `relation`-kind link per valid member from the members node to that member's hypernode, carrying the hyperedge's `relation` string and the member's `seq`. This replaces the prior mutation's flatter "hub node connects directly to every member" model with the doc's two-hop tree.
- **Every element stays clickable and inspectable**, continuing the principle established in the previous mutation (which fixed a bug where 2-member hyperedges weren't clickable at all): clicking the henode or a `relation` link shows the real hyperedge's JSON; clicking a `relation` link's target hypernode shows that node's JSON; clicking the virtual `members` node or the virtual `hyperedge` link shows a small synthetic JSON object explicitly marked `"virtual": true` with a note explaining it isn't a persisted entity, so a curious user isn't left thinking they found a bug when a click yields no backing record.
- **Camera-focus on click**: clicking any real node smoothly flies the camera to frame it (a standard 3d-force-graph pattern) — a 3D-specific affordance the flat 2D version didn't need, since panning/zooming a 2D canvas to a clicked element isn't as disorienting as navigating 3D space manually.
- **Auto-rotate control**: replaces the old 2D "Layout" dropdown (force/concentric/hierarchical/circle/grid — all Cytoscape-specific 2D layout algorithms with no 3D equivalent) with a slow-orbit toggle, a common 3D-graph-viewer affordance for passively surveying a structure without manual dragging.
- **Search and legend-based type filtering were re-implemented for the new renderer** using a color-substitution + forced-repaint technique (mutate a `_dim` flag on node/link data objects, then re-invoke the existing `nodeColor`/`linkColor` accessor functions to trigger `3d-force-graph` to re-derive and repaint colors) since, unlike Cytoscape, this library doesn't expose a per-element opacity accessor — only per-node/per-link *color* accessors, so "dimming" is simulated by swapping to a muted grey that blends toward the dark background rather than true transparency.
- **Dark canvas background** (`#0f0f1a`) was chosen to match the app's existing dark sidebar/login gradient and because bright colored spheres read far more clearly against a dark 3D scene, which is the convention nearly all 3D graph-visualization tools follow.
- **HTML-escaping added for tooltips** (`vizEsc()`): `3d-force-graph`'s hover-tooltip accessors (`nodeLabel`/`linkLabel`) render their return value as raw HTML, and node/hyperedge labels originate from user-entered hypergraph data — an unescaped label containing something like `<img src=x onerror=...>` would have been a stored-XSS vector via the tooltip. This wasn't a concern in the prior Cytoscape version, whose built-in label rendering doesn't interpret HTML.

## Key Decisions
- **No custom Three.js node geometries** (e.g. distinct shapes per node kind) — deferred because it would require loading three.js separately as an ES module and wiring it into `3d-force-graph` via `window.THREE`, which no longer has an official non-module CDN build at current versions. Color + size differentiation (type-hashed color for hypernodes, flavor color + arity-scaled size for hyperedge nodes, fixed small grey for virtual members nodes) was judged sufficient to distinguish the three node kinds at a glance without that added complexity.
- **Verification**: reused the CDP-over-headless-Chrome harness from the two prior Visualize mutations (still no Claude-in-Chrome browser extension available in this environment). Confirmed against the live seeded `hello-world` graph (11 hypernodes, 4 hyperedges) that: `ForceGraph3D` loads; rendered node/link kind counts exactly match the doc's structure (4 henode + 4 members + 11 hnode nodes; 4 hyperedge-links + 14 relation-links, where 14 is the sum of all hyperedge member counts); clicking a henode, a members node, a relation link, and a hyperedge link each produce the expected (real or synthetic-virtual) JSON in the details panel; search and legend-toggle dimming both correctly flag the expected node counts; Fit and Auto-rotate (on and off) run without error. Zero console errors/exceptions were observed across the full interaction sequence. Test infrastructure (local mongod, the hgai server process, headless Chrome) was torn down afterward.
