# Mutation Summary

## Intent
The user wanted an entirely new capability added to the greenfield rebuild plan: an interactive 3D visualization of the hypergraph in the browser UI, with rotation, auto-rotation, filtering, and double-click-to-focus-on-a-node behavior. They were explicit that this is new functionality with no equivalent in the reference implementation, and that it should be scoped as an optional phase that only starts once the core, required phases (0–12) are already built and working — i.e., the platform must stand on its own without this feature.

## Context
- This followed a run of four consecutive "same pass" requests that added explicit result-shape/attribute-access specs and worked examples to §6.1 (HQL), §6.2 (SHQL), §7 (REST API), and §9 (Inferencing) — each pass established that inferred/matched/hydrated entities behave uniformly and chain together (SHQL bindings addressable at any hop, REST edge hydration, inference results as first-class chainable bindings). The 3D visualization phase was designed to reuse those already-established mechanisms rather than inventing new backend capability: the double-click-focus interaction specifically reuses HQL's `members.node_id` where-filtering (spec'd in the §6.1 pass) and REST's `?hydrate=1` edge endpoint (spec'd in the §7 pass) to fetch a focused node's neighborhood, rather than requiring a new dedicated backend query path.
- `build-plan.md`'s existing structure (§0's "fewer moving parts > more moving parts" principle, §3's pattern of picking exactly one technology per decision with no menus, and the self-hosted-first bias already established for Qdrant in §3) directly shaped the technical choices made in this addition.
- `build-plan.md` §14 already had a precedent for a UI-only, manually-smoke-tested phase (Phase 11 — CLI shell & Web UI), which this new phase's exit criteria explicitly mirrors ("this phase is explicitly UI/UX, verify by actually using it, not just unit tests").

## What Changed and Why
Inserted a new **Phase 13** entry into §14, after Phase 12 (previously the last phase) and before §15 (Explicitly deferred). No other section of the document was touched — the phase was written to be fully additive and require zero backend/API changes, consuming only what §6.1 and §7 already specify.

Key content decisions, each made to keep the new phase self-contained and consistent with the rest of the document without requiring new backend work:
- **Hypergraph → binary scene-graph mapping**: since 3D graph-rendering libraries render binary node-links but hyperedges are N-ary, the phase specifies rendering each Hyperedge as its own scene node (not merely as an edge/line) with one link per member — this is presented as a direct, non-arbitrary application of the document's own §1 tenet that hyperedges are first-class and referenceable like hypernodes, rather than a new design decision invented for this phase.
- **Library choice**: `3d-force-graph` (Three.js-based) was named as a single, specific recommendation — consistent with the document's established pattern of picking one technology per decision rather than presenting options — and justified on the same self-hosted/no-external-service-dependency grounds already used to justify Qdrant in §3.
- **No new REST endpoint for the initial scene load**: the existing `GET /graphs/{id}/nodes` and `GET /graphs/{id}/edges` list endpoints (already paginated/filterable per the §7 pass) are transformed client-side into the visualization's input shape, rather than adding a dedicated `/viz` endpoint — chosen to avoid unnecessary backend surface area for a purely-additive optional phase.
- **Filtering re-queries the server** rather than doing client-side show/hide over an unbounded loaded dataset — chosen for consistency with the list-endpoint filter params already specified in §7, and to avoid requiring the client to hold and search over a potentially large unbounded dataset in memory.
- **Double-click focus reuses existing mechanisms** (HQL member-containment filtering + REST edge hydration) instead of introducing a new "get neighborhood" backend capability — the most direct expression of designing this phase to sit entirely on top of what earlier phases in this session had already specified, rather than growing the API surface for a single UI interaction.
- **A size-bound guardrail** on the initial scene load (warn/require filtering above ~2000 combined nodes+edges) was added as a cheap, explicit safety measure against an unusably large default WebGL scene, without building out a more elaborate level-of-detail or streaming system that wasn't requested and isn't needed for a v1 of this feature.
