# Mutation Summary

## Intent
The user asked a direct clarifying question about the conversion plan: is `VALUES` support meant to eventually become a native SHQL engine feature, or does in-list/membership filtering already exist in SHQL today? The answer required checking `hgai_module_shql/engine.py` directly rather than relying on the plan's own prose, since the plan doesn't currently distinguish "already native" from "transpiler-only" for this specific construct. After the answer was given in chat, the user asked for it to be captured in the plan document itself.

## Context
Verified directly against source rather than assumed: `hgai_module_shql/engine.py`'s FILTER mini-language already implements a real `IN` operator, `attributes:` filters already pass MongoDB operators (including `$in`) straight through to storage, and a grep of the whole `hgai_module_shql/` package confirmed no `"values"` keyword exists anywhere. Separately, `_eval_node_pattern` was checked and shown to build `HypernodeSearchFilters.node_ids_in` — a list-typed filter the storage layer already supports — from a single scalar `id:` value only, since the YAML-level `id:` key never accepts a list itself. This second fact is what the user's follow-up asked to have written down.

## What Changed and Why
Added the note to `docs/architecture/sparql-to-shql-conversion-plan.md`'s Phase 2.5, immediately after its existing bullet list, rather than as a new top-level section — it belongs right where a reader is already learning why `VALUES` needs a `union:`-based transpiler translation at all, since the note's whole point is explaining what's already native (so a future reader isn't tempted to reinvent `IN`/`$in` support) and what a cheaper, narrower alternative to full `union:` unrolling could look like if ever pursued separately. The note explicitly frames the `id:`-list idea as *out of scope* for this plan, consistent with the plan's established discipline of keeping v1 strictly transpiler-side and calling out, rather than quietly folding in, anything that would touch `hgai_module_shql/engine.py`.

The user then asked for the same note in `docs/architecture/sparql-vs-shql-gaps.md`, so it was added there too — immediately after that document's Tier 1 table, where `VALUES`'s frequency/cost/verdict is already scored, rather than duplicated verbatim. The wording was adapted to that document's own voice (tying back to "this tier recommends `union:`" rather than "the plan does X") so it reads as native to each document rather than a copy-pasted aside, while keeping the same three underlying facts consistent across both: the two already-native in-list mechanisms, why neither is sufficient for `VALUES`, and the `id:`-list idea framed the same way — a possible, explicitly out-of-scope follow-on — in both places.

A third request extended the same note into `docs/help/notes/web-ui/rdf-import.md` — a different kind of document from the previous two (end-user Help content read live in the Web UI's Help tab, not developer-facing architecture reference), which called for a different emphasis rather than a third verbatim copy. The two `docs/architecture/` documents are forward-looking design plans for a feature that doesn't exist yet; a Help topic describing RDF import's *current*, shipped behavior shouldn't lead with "here's a future plan." So the new "Coming from SPARQL?" section reorders the same three facts to lead with what a reader can actually use today (the native `IN`/`$in` mechanisms), explain the real gap briefly, and only then point at the architecture docs as further reading for anyone tracking the fuller conversion effort — plain code-formatted repo paths rather than `help:`-style links, since the Help link syntax (`docs/help/notes/web-ui/authoring-help.md`) has no way to address a file outside `docs/help/notes/`.

A fourth request extended the note into `docs/help/notes/shql/shql-filters.md` — the SHQL FILTER-syntax reference itself, which already documented `?var.field IN [a, b, c]` in its operator table before any of this session's work. Rather than re-describing `IN` from scratch, the edit did two narrower things specific to this document: paired `IN` with its pattern-side counterpart `attributes: {field: {$in: [...]}}` inside the existing "Filter or attribute operator?" section (that section's whole purpose is explaining when to reach for one over the other, so the SPARQL-relevant pairing belongs exactly there — one sentence, cross-linking to `shql-patterns.md`'s "MongoDB operators" section rather than duplicating its content), and added the same short "Coming from SPARQL?" pointer as the RDF import topic. This kept the addition to this reference-table-style document terse, consistent with its existing tone, rather than importing the longer prose framing used in `rdf-import.md`.

A fifth request extended the note into `docs/help/notes/shql/shql-patterns.md` — the node/edge pattern-syntax reference, which already documents `id:` (single literal or `?var`) and `attributes:`'s `$in` support, but had never connected the two facts. This document turned out to be the most natural home yet for the `id:`-list observation specifically, since it's the one place readers already learn what `id:` accepts — so the new "`id:` takes one value, not a list" section states that gap plainly and, unlike the more abstract framing used in the two architecture documents, gives the two workarounds a reader can actually use today (a `union:` branch per id, or bind-then-filter with `IN`). The "Coming from SPARQL?" section that follows ties directly back to that `union:`-per-id technique — showing a reader exactly what a translated `VALUES` clause would look like using syntax this same page just taught them — before pointing at the two `docs/architecture/` documents for the fuller conversion effort.

## Key Decisions
- Placed the note as prose after Phase 2.5's bullets rather than as a new table row in §2 or a new tier in `sparql-vs-shql-gaps.md`, since it isn't a SPARQL-to-SHQL translation gap in the same sense as everything else in those documents — it's an observation about SHQL's own surface API being narrower than its storage layer already allows, which is closer to an implementation note than a capability comparison.
- Kept the `id:`-list idea framed as a "possible future enhancement," not a recommendation to build it — the plan's existing `union:`-based translation is already correct and general (it handles multi-variable `VALUES` rows the `id:`-list idea never could), so this is presented as a narrow optimization for one common sub-case, not a required or even clearly-worthwhile follow-on.
