# Mutation Summary

## Intent
The user wanted a rigorous assessment and implementation plan for inferencing/reasoning over the semantic knowledge hypergraph — specifically SKOS-style `broaderTransitive`/`narrowerTransitive` concept reasoning — starting from an explicit "do not make code changes" planning mode. Over a long, iterative design conversation (15 turns), the plan was progressively refined through the user posing concrete worked examples and design corrections, until the user asked to propose a concrete implementation order and then said "yes, go ahead" on its first step — at which point this stopped being a planning conversation and became an implementation task.

## Context
Investigation at the start of the conversation found that inferencing in this codebase is almost entirely aspirational: `hgai/core/inference.py`'s `infer_inverse_edges()`/`check_transitive_relation()` have zero call sites anywhere; `EdgeFlavor.transitive`/`inverse-transitive` are used only as literal equality filters in HQL/SHQL, never as a trigger for real graph traversal — meaning a query like `match: {relation: contains, flavor: transitive, nodes: [A, B]}` silently performs a wrong single-hop literal match rather than erroring or reasoning; `skos_broader`/`narrower`/`related` fields on `HyperedgeBase` are actively stripped from every query result before a caller can see them; and a documented `infer: true` HQL flag (`docs/concepts.md`) was never implemented. A pre-existing "v2 greenfield" design document (`docs/design/epics-to-build-production-hgai/build-plan.md` §9) independently arrives at a similar RelationType/axiom model but assumes a full package-monorepo rewrite that was never executed — its ideas were reused, its rewrite framing was not, since the user is actively extending the current module layout (this session alone had already added hyperkey temporal-dedup, clone/duplicate, and mutation-history features to it in earlier turns).

## What Changed and Why

**The plan** (fully detailed across the conversation transcript in `prompt.md`'s 15 turns; the mechanism itself was never coded, only specified) converged on:
- Relations are data, not code: reasoning behavior (`owl:transitive`, `owl:symmetric`, `owl:inverse-of`, `skos:broaderTransitive`/`narrowerTransitive`) is declared as ordinary hyperedges connecting relation-hypernodes (or concept-hypernodes) — never hardcoded per-relation, and not even stored in a special `attributes.axioms` field (an earlier proposal that was corrected mid-conversation once the user's own worked example showed the pure-hyperedge-assertion pattern was more consistent with the system's "hyperedges are treated as hypernodes" tenet).
- Two reasoning primitives — `expand_edge` (0-hop inverse-of/symmetric/superproperty-projection synthesis, computed via a flavor-aware `atomic_pairs` decomposition and a fixed-point closure over literal-and-already-inferred edges) and `check_transitive`/`walk_closure` (N-hop reachability, PIT-aware, shared between axiom-graph and fact-graph walks) — cover every case worked through by hand, including the user's own `rel:parent`/`rel:father`/`owl:inverse-of` example, verified twice to converge on the same 4-edge result once `expand_edge`'s hub-flavor fan-out bug (naive list-reversal, matching a real bug already present in the dead `infer_inverse_edges` code) was caught and corrected.
- A distinct materialization phase ("Project Inference," Phase 6) was added after the user asked directly whether inference was transient — confirmed yes — and then asked for a UI-accessible process to persist inference results from source hypergraph(s) into a target (existing or new), reusing the existing `create_hyperedge` path so hyperkey dedup and the `mutations` audit trail apply for free, with explicit provenance (`attributes.provenance`) and explicitly-flagged limitations (snapshot, not live-synced; safe to re-run).
- The user's own question ("would it be simpler to only keep `hub`/`symmetric`?") led to eliminating `direct`/`transitive`/`inverse-transitive` from `EdgeFlavor` entirely — justified by a clear test (does a flavor describe one genuine N-ary fact, or several independent binary facts stapled together?) that `hub` and `symmetric` pass and the other three fail, and confirmed to cost zero real functionality since those three flavors never actually triggered any reasoning logic to begin with.
- A 7-step implementation order was proposed with actual dependency reasoning (not just phase-number order) — critically catching that removing `transitive` from `EdgeFlavor` breaks the previously-proposed `match.flavor: transitive` HQL trigger syntax, replaced with a single unified `infer: true` trigger for both `expand_edge` and `check_transitive`.

**The actual code change** (Step 1 of that order, implemented in Turn 15) is exactly the `EdgeFlavor` reduction: `hgai/models/hyperedge.py`'s enum, the MCP tool docstring, the UI's two flavor `<select>`s (list filter and create/edit modal), the Visualize screen's flavor-to-color map, and three live documentation files (`docs/concepts.md`, `docs/hello-world.md`, `docs/dev_notes/skhg-inferencing-notes.md`) were all updated to reflect only `hub`/`symmetric`. No inference engine code was written — that's Steps 2 onward, not yet implemented.

## Key Decisions
- **Verified before touching anything**: grepped the full codebase (models, MCP, UI, tests, live docs) for every reference to the three removed flavor values before editing, confirming zero test coverage depends on them and zero seed/example data uses them — so this is a pure, safe, zero-migration schema simplification, not a breaking change to real data.
- **Left the archived/historical planning docs alone** (`docs/design/epics-to-build-production-hgai/*`, `docs/decks/*`) — these describe a different hypothetical "v2" rewrite or past sales demos and are not living documentation of current behavior; only `docs/concepts.md`, `docs/hello-world.md`, and `docs/dev_notes/skhg-inferencing-notes.md` (all "how the system actually works today" references) were updated.
- **Did not overclaim in the new `EdgeFlavor` docstring**: an early draft referenced `hgai/core/inference.py` as if it already implemented `owl:transitive`-driven reasoning; caught and corrected to say "planned... not yet implemented," since Steps 2–7 of the plan haven't been built.
- **Verified live**, not just via unit tests: spun up an isolated test server + throwaway MongoDB database (never touching the user's real running server or data), confirmed via curl that creating a hyperedge with `flavor: "direct"` now correctly gets a `422` Pydantic enum-validation error while `flavor: "hub"` still succeeds, then confirmed in the browser that both the Hyperedges list's flavor filter and the create-modal's flavor `<select>` now show only `hub`/`symmetric`. Full test suite re-run clean afterward (57 passed; the same 3 pre-existing, unrelated `test_mesh.py` failures confirmed present on `main` before this session's changes).
- **Consolidated the capture**: this conversation began as an explicit "do not make code changes" ask session and was captured as such after Turn 1; once it crossed into real implementation in Turn 15, the prior ask capture was deleted and replaced with this single mutation capture spanning the full 15-turn session, per the project's "don't double-capture" rule.
