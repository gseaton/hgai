# Mutation Summary

## Intent
The 3D visualization's default camera controls only offered orbit (left-click-drag) and, separately, pan via right-click-drag or the built-in A/S/D key modifiers. The user wanted a specific, additional gesture — hold Shift, hold left-click, and drag — to pan the camera, without giving up the existing plain left-click-drag orbit behavior.

## Context
3d-force-graph (the library backing the Visualize screen) uses `THREE.TrackballControls` internally, exposed via `State.viz3d.controls()`. That controls instance has a `mouseButtons` object (`{LEFT, MIDDLE, RIGHT}`) mapping each physical mouse button to an action — by default `LEFT` rotates, `MIDDLE` zooms, and `RIGHT` already pans. There was no existing modifier-key handling anywhere in this codebase's visualization code before this change (confirmed by search — no `.controls(`, `OrbitControls`, `enablePan`, or `mouseButtons` references existed prior to this turn).

## What Changed and Why
- **A capture-phase `mousedown` listener reassigns `mouseButtons.LEFT` right before each drag starts**, rather than tracking Shift state separately via `keydown`/`keyup`. TrackballControls reads `mouseButtons.LEFT` fresh at the moment a drag begins, so mutating it just-in-time, gated on the live `event.shiftKey` flag, is sufficient — and it can't get stuck in the wrong state the way a separate keydown/keyup toggle could if a `keyup` were ever missed (e.g. the window losing focus mid-drag while Shift is still physically held). The listener is registered on the visualization's container element in the *capture* phase specifically so it's guaranteed to run and update the mapping before TrackballControls' own listener (attached deeper in the DOM, on the actual `<canvas>` it renders into) reads that value for the same event.
- **The pan action value is read from the library's own existing `RIGHT` mapping rather than hardcoded** as a raw `THREE.MOUSE` enum number. `THREE` isn't exposed as a global by this bundled build (confirmed at runtime), and reusing whatever action the library already assigns to right-click (which pans by default, a stable, already-relied-upon behavior) avoids hardcoding an enum value that could silently be wrong if a future version of the library changes its internals — the fix stays correct by construction, defined in terms of "whatever this library calls pan" rather than "the number 2."
- **Only `LEFT` is touched; `MIDDLE`/`RIGHT` and all other controls behavior are left exactly as shipped.** The ask was specifically to add a new way to trigger panning via Shift+left-click, not to change what any other input already does.

## Key Decisions
- Investigated switching to `THREE.OrbitControls`-style declarative config (`enablePan`, `mouseButtons: {LEFT: THREE.MOUSE.PAN}` set once) but this library's bundled controls are `TrackballControls`, whose `mouseButtons` field behaves the same way (an action-per-button map) but needs to be mutated dynamically per-drag to get a *modifier-conditional* action, since neither OrbitControls nor TrackballControls has a built-in "hold this key to temporarily override this button's action" concept — only a static mapping. Toggling the mapping just-in-time was the smallest change that achieves the requested conditional behavior without forking or wrapping the controls class.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the already-running dev server (frontend-only change; the server was actually found stopped at the start of this turn from a prior session gap and was restarted to serve the updated file) and a **freshly-created** headless Chrome profile — a stale-cache pitfall was hit and diagnosed along the way: an earlier Chrome instance reused across several debug scripts in this turn had cached the pre-fix `app.js` from its very first page load (before the edit was written to disk), so early test runs were silently exercising old code despite the file on disk being correct — confirmed via `initViz3D.toString().includes('rotateAction')` returning `false` in the stale tab versus `true` after switching to a fresh profile. With a clean profile: confirmed via an instrumented listener log that a native CDP-driven Shift+mousedown (`modifiers: 8`) correctly sets `controls.mouseButtons.LEFT` to the pan value at the exact moment the library's own handler would read it, and that a plain mousedown correctly leaves/restores it to the rotate value. Then, to avoid TrackballControls' momentum/damping bleeding between back-to-back synthetic drags in one script (an artifact that briefly produced a confusing mixed result), tested each action in isolation: forcing `LEFT` to the rotate value and performing a native CDP mouse-drag left `controls.target` unchanged (`target_delta = 0.000`) while the camera position moved (`camera_delta = 47.417`) — a textbook orbit; forcing `LEFT` to the pan value produced comparable movement in both `target` and camera position together (`32.521` / `38.490`) — a textbook pan. Full `pytest` suite: 45 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes. Left the dev server running afterward and killed only the headless Chrome test instances. `git status --short` shows only `ui/js/app.js` as this turn's change.
