# Mutation Summary

## Intent
The user was reviewing `build-plan.md` (the greenfield HypergraphAI v2 rebuild plan written for an AI coding agent) in their IDE and raised a design-review question about §6 (Query Layer): whether the plan needs worked syntax examples at all, or whether the implementing agent should be left to invent HQL/SHQL syntax during Phase 5/6. Embedded in that question was a more concrete observation: §6.2's SHQL spec never actually states the "SPARQL-esque" semantics implied by §1's tenet list, and never describes how to access attributes of anything matched beyond the first pattern in a query — i.e., no documented way to chain a multi-hop query and pull attributes off a later hop's binding. They asked whether the query-layer spec should guarantee at least that much.

## Context
- `build-plan.md` is explicitly designed (§0) to be executed by a fresh AI agent session per phase, with no memory of other phases and no access back to the original reference codebase. Its own stated principle is that schema/interface details in the doc are binding, not left to agent discretion.
- HQL is implemented in Phase 5, SHQL in Phase 6, and both are then referenced *unmodified* by later phases run as separate sessions: MCP tool descriptions (Phase 10), UI query editors with example queries (Phase 11), and generated docs (Phase 12). If the DSL syntax/semantics aren't pinned in the spec those phases implement against, later phases have nothing authoritative to conform to and can silently diverge from whatever Phase 5/6 actually built.
- Verified against this session's own prior research (an Explore-agent audit of the actual reference `hgai` codebase, done for the original `build-plan.md` draft): the reference implementation's SHQL engine already supports exactly this — `select: [?member.label, ?member.attributes.foo]` resolves dot-paths off any bound `?var`, and multi-hop traversal works by reusing an already-bound `?var` as a later pattern's anchor (this anchor-reuse behavior was itself the subject of a documented, previously-fixed bug in the reference implementation). So this wasn't a new feature to design — it was a real capability of the system being rebuilt that the plan had failed to carry forward into its spec text, i.e. a spec gap, not a scope decision.

## What Changed and Why
Assistant recommendation (given before the edit, per this session's working style of proposing before mutating a document mid-review):
1. **Keep a small number of pinned examples in §6**, rather than deferring syntax to agent discretion during implementation — because the multi-phase, multi-session build structure makes DSL syntax a fixed cross-phase contract, not an internal implementation detail; 2–3 canonical examples per language is enough to pin the grammar without bloating the doc.
2. **Add the missing SPARQL-esque semantic statement and attribute-chaining mechanism to §6.2** — confirmed as a real gap, not a design choice to weigh.

The user approved applying the edit ("Yes, apply that edit to §6.2"). The edit added, in place, immediately after the existing SHQL paragraph in §6.2: the binding-table result-shape statement, the any-hop dot-path attribute-access statement, the anchor-reuse chaining statement, and a two-hop worked YAML example (`?person` →`reports-to`→ `?manager` →`member-of`→ `?team`, selecting `?team.attributes.department` in the same `select:` as the hop-1 bindings) to make the mechanism concrete rather than only described in prose.

## Key Decisions
- Scoped the edit to §6.2 only, per the user's explicit turn-2 instruction ("apply that edit to §6.2") — did not also retrofit §6.1 (HQL) with additional examples in this pass, even though the first sub-question (examples in general) technically applies to both; the user's follow-up narrowed scope to the concrete SHQL gap they'd identified, so HQL's example-density was left as a separate, unaddressed question rather than assumed in-scope.
- Chose to state the mechanism as prose rules ("any bound `?var`, any hop, dot-path addressable") backed by one worked example, rather than exhaustively enumerating every combination of pattern type × hop depth — consistent with the document's own stated goal of minimizing token count without sacrificing clarity; one worked example that demonstrates hop-2 attribute access is sufficient to make the rule unambiguous for an implementing agent.
