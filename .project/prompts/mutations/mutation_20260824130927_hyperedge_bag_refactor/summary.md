# Mutation Summary

## Intent
The user asked to fix how the Visualize tab (added in the prior mutation, `mutation_20260824072725_hypergraph_visualization_tab`) represents hyperedges, suggesting either a "bag" representation or standard edges carrying the hyperedge's relation from a hyperedge node to its member nodes.

## Context
The original Visualize implementation special-cased hyperedge arity: exactly-2-member hyperedges were drawn as plain Cytoscape edges directly between the two member hypernodes, while hyperedges with 1 or 3+ members were drawn as a diamond "hub" node with spoke edges to each member. This was inconsistent and, on inspection, buggy: the `tap` handler was only bound to `'node'`, so clicking a 2-member hyperedge's plain-line rendering did nothing — it wasn't clickable/inspectable the way every other hyperedge was, breaking the "every hyperedge is a first-class object" model that the rest of the app follows (hyperedges are queryable/editable entities with their own id, attributes, tags, flavor). The user's phrasing ("bags" / "standard edges ... from the hyperedge node to the member nodes") pointed at the standard bipartite/incidence-graph technique for drawing hypergraphs: always give the hyperedge its own node, and connect it to members via ordinary edges — never conflate a hyperedge with a graph edge.

## What Changed and Why
- **Removed the arity-2 special case in `renderViz()`** (`ui/js/app.js`): every hyperedge now unconditionally creates a `henode` (bag) plus one `hspoke` edge per valid member. This eliminates the click-dead-end for binary hyperedges and makes the visualization arity-agnostic, which is the actual defining property of a hypergraph.
- **Bag sizing by arity**: the bag node's `width`/`height` scale with member count (capped at 40px), so a hyperedge that touches many nodes visually reads as a bigger "bag" than one touching two — a lightweight visual cue for hyperedge size without needing a real convex-hull/compound-node "bag" drawing (which isn't feasible here since a hypernode can belong to multiple hyperedges, and Cytoscape compound nodes require a single parent per child).
- **Bag shape changed from diamond to round-rectangle**: reads more literally as a "bag" holding its members, per the user's suggested metaphor.
- **Spokes now carry the hyperedge's relation and the member's seq** (`relation`, `seq` in edge data) and a back-reference to the full hyperedge (`raw: e`), directly matching the user's second suggested approach ("generate standard edges with the relation hyperedge attribute from the hyperedge node to the member nodes").
- **Generalized click-to-inspect**: the Cytoscape `tap` handler now listens on `'node, edge'` instead of just `'node'`, and checks `d.raw !== undefined` before showing details — so clicking a bag, a hypernode, or a spoke edge all open the same Element Details panel with the underlying JSON. This directly fixes the click-dead-end bug that motivated the request.
- **Stats/legend updates**: the "N nodes · M edges" stat became "N hypernodes · M hyperedges" (now a direct, unambiguous count since every hyperedge is exactly one bag node), and the legend's flavor-swatch CSS/class was renamed from `diamond` to `bag` to stay visually consistent with the new node shape.

## Key Decisions
- **Bag = node, not a drawn boundary/blob**: a literal "bag" (closed curve enclosing member nodes, Euler-diagram style) was considered but rejected — Cytoscape's only native grouping primitive is compound (parent/child) nodes, which require each node to have at most one parent. Since hypernodes routinely participate in multiple hyperedges in this domain (confirmed by the seed data, where e.g. a "Three Stooges" hyperedge-bag is itself a member of a "Rat Pack" hyperedge-bag), a real boundary-drawing approach would require a third-party Cytoscape extension and wouldn't correctly handle shared membership anyway. The bipartite/incidence-graph technique (hyperedge-as-node) has neither limitation and is the standard approach used by hypergraph visualization tools generally.
- **Verification**: Re-used the CDP-over-headless-Chrome test harness from the prior mutation (no Claude-in-Chrome browser extension available in this environment) to confirm: `hbinary` element count is 0 post-refactor, bag node count matches hyperedge count, spoke edge count matches total member arity across all hyperedges, clicking both a bag node and a raw spoke edge correctly populates the Element Details panel with the parent hyperedge's JSON, and no console errors were raised. Test infrastructure (local mongod, the hgai server process, headless Chrome) was torn down afterward.
