# Mutation Summary

## Intent
Continue the phased inferencing implementation plan (see `mutation_20260910201701_edgeflavor_simplification` for the plan's full development history, and `mutation_20260910202713_inference_step2_primitives` for Step 2's shared primitives) with Step 3: build `expand_edge`/`expand_edge_closure` — the inverse-of/symmetric/superproperty-projection reasoning the plan specified — and wire it into HQL behind an explicit `infer: true` flag, closing the "dead code, zero call sites" defect identified at the very start of this multi-session plan.

## Context
Step 2 had already built and verified `atomic_pairs`, `get_axiom_edges`, and `walk_closure`. The plan's Phase 2 spec (developed and corrected across several turns of the original planning conversation, using a running `rel:parent`/`rel:father`/`owl:inverse-of` worked example) called for exactly three synthesis rules operating on `atomic_pairs`-decomposed edges, applied as a fixed-point closure (not a single pass) so a fact projected onto a broader relation becomes itself eligible for further axiom expansion, with per-hop `_inferred`/`_source_edge`/`_axiom` provenance tags and no persistence (computed live, at read time).

## What Changed and Why
`expand_edge` implements the three rules exactly as specified. `expand_edge_closure` implements the fixed-point iteration. Both were wired into `hgai_module_hql/engine.py`'s `execute_hql()` behind a new `infer: true` top-level HQL flag (previously documented in `docs/concepts.md` but never implemented) — a hyperedge match with `infer: true` now runs the closure over whatever fact edges it matched and appends the synthesized results, each independently field-projectable via the existing `return:` mechanism (including the `_inferred`/`_source_edge`/`_axiom` tags, which pass through the existing `_project_fields` fallback for any field not in its special-cased list). A query without the flag never touches the reasoning engine — verified live.

Live end-to-end verification against the exact worked example from the plan (the `rel:parent`/`rel:father`/`owl:inverse-of`/`owl:inverse-of[rel:parent,rel:child]` scenario, reconstructed via the real REST API on an isolated test database) surfaced a real bug the design conversation's hand-tracing hadn't caught: applying `owl:inverse-of` a second time (legitimately — inverse-of is symmetric, and the plan's own design treats already-inferred edges as first-class input to further reasoning) regenerated the original projected `rel:parent` facts, but as three separate 2-member edges rather than the original single 4-member one. The originally-planned dedup (`_edge_content_key`: relation + sorted whole member list) didn't recognize these as already-known, because a 4-member edge and three separately-bundled 2-member edges asserting the same underlying facts have different member-list shapes even though they mean the same thing. Fixed by deduping the closure at the level of individual `(relation, subject, object)` atomic facts (`_atomic_facts`) instead of whole-edge shape — re-traced the same scenario by hand against the fix before re-testing live, confirmed it converges to exactly the expected 4 inferred edges, and added a dedicated unit test (`test_atomic_facts_recognizes_bundling_shape_does_not_matter`) encoding the property that caused the bug, so a future change can't silently reintroduce it.

## Key Decisions
- **Removed `infer_inverse_edges()` rather than leaving it alongside the new code** — it had zero callers, and its naive `list(reversed(members))` logic was independently found to be wrong for any multi-member `hub` edge (confirmed during the original planning conversation's worked examples) — `expand_edge`'s `owl:inverse-of` handling fully supersedes and corrects it.
- **A second unit test (`test_other_member_none_when_relation_not_a_member`) caught a second real bug** before it ever reached live testing: `_other_member` returned an arbitrary member when the queried `relation_id` wasn't actually part of the edge at all, instead of `None`. Fixed to check membership first. Consistent with this session's established pattern (a test written to document expected behavior, not just pad coverage, catching a real defect).
- **Dedup granularity (atomic facts, not whole edges) was decided only after live testing exposed the gap** — the original plan's `_edge_content_key` design was reasonable on paper and only failed once a genuine multi-hop, multi-axiom scenario was run against real data, reinforcing why this session verifies every inference step against a live server/database rather than trusting hand-traced examples alone.
- **A stale-cache false alarm during verification**: re-running the identical HQL query text across a server restart (to pick up the atomic-facts fix) initially appeared to show the bug was still present — traced to HQL's query-result cache correctly serving the previous (pre-fix) response for identical query text, an expected caching behavior unrelated to the actual code; confirmed the fix by re-running with `use_cache: false`, not by changing any caching behavior.
- **Verified regression safety**: a plain HQL query with no `infer` flag was confirmed to still return only the literal matched edge, with `meta.infer: false` — the new code path is fully opt-in as designed.
- Full test suite: 72 passed (69 pre-existing/Step-2 tests minus 2 removed `_edge_content_key` tests plus 5 new ones), same 3 pre-existing unrelated `test_mesh.py` failures.
