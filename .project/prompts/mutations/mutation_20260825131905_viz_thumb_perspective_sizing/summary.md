# Mutation Summary

## Intent
The 3D visualization's default-media thumbnails, added the previous turn, were sized with a fixed CSS `width`/`height` (30x30px) — the same pixel size on screen no matter how far the camera was from the node. That's inconsistent with every other object in the scene: the spheres representing hypernodes/hyperedges genuinely grow and shrink as the camera moves through the 3D space, because they're real WebGL geometry with perspective projection. The user wanted the thumbnails to behave the same way — sized to match the sphere they're standing in for, and responsive to zoom exactly as a real 3D object would be.

## Context
The thumbnails are DOM-overlay `<img>` elements (not true WebGL textures) — a deliberate choice from the previous turn, reusing the exact positioning mechanism already built for the visualization's text labels (`vizProjectPoint()`'s manual camera-matrix math, run every frame in `vizLabelTick()`). That positioning math only ever computed *where* a world point projects to on screen, never *how big* a world-space size should appear there — because the labels it was built for are genuinely flat 2D UI elements (readable text) that intentionally do NOT scale with zoom, the same way a map pin's label stays legible at any zoom level. Thumbnails needed the opposite behavior, which meant extending the projection math rather than reusing it as-is.

## What Changed and Why
- **Perspective size math reuses a value the projection math was already computing and discarding.** `vizProjectPoint()`'s clip-space `w` term (`cw`) was already being computed (it's needed for the perspective divide that produces screen x/y) and then thrown away. For a standard, unskewed perspective projection matrix — which is what 3d-force-graph's camera uses — that term is mathematically equal to the point's camera-space depth (distance along the view axis). Returning it alongside `x`/`y` meant the size calculation needed no new matrix math of its own, just the standard "apparent size" formula: a world-space size at a given distance, under a given vertical field-of-view, maps to a known fraction of the viewport's pixel height.
- **The sphere radius formula is replicated, not read back from the library.** 3d-force-graph (via three-forcegraph) doesn't expose an API to ask "how big did you render this node's sphere," but its sizing convention (`radius = cbrt(val) * nodeRelSize`) is a stable, documented part of that library's contract — and this codebase already supplies both `val` (per-node, already set when building the viz's node list) and `nodeRelSize` (a single `.nodeRelSize(3)` call). Replicating the formula in one small helper, fed by a shared `VIZ_NODE_REL_SIZE` constant that the actual `.nodeRelSize()` call now also reads from, means the thumbnail size can never silently drift out of sync with the real sphere size just because someone changes the `nodeRelSize` tuning value in one place and not the other.
- **The label-avoidance offset became proportional instead of a fixed pixel nudge.** With the thumbnail's own size now varying enormously by zoom level (a few pixels far away, potentially hundreds up close), the old fixed `-24px` margin — chosen when the thumbnail was always exactly 30px — would look absurd at either extreme (a huge gap relative to a tiny distant thumbnail, or barely any separation from a huge nearby one). Offsetting by roughly half the thumbnail's own *current* size keeps the label legible underneath it at any zoom level, using the same "respects zooming" principle applied consistently rather than solving it for size alone and leaving position as an afterthought.
- **Circular instead of rounded-square.** A sphere's silhouette, at any viewing angle, projects to a circle — changing `border-radius` from `6px` to `50%` makes the thumbnail's shape, not just its size, read as "the thing this object actually is" rather than a generic photo-badge sitting near it.

## Key Decisions
- Did not switch to true Three.js sprite/texture rendering to get size-with-distance "for free" from the WebGL pipeline — that tradeoff was already made and explained in the previous turn (async texture upload complexity, coordinating disposal with 3d-force-graph's own node lifecycle) and remains correct: the DOM-overlay approach, now extended with proper perspective-correct sizing, produces the same visual result the user asked for without touching the render pipeline at all.
- Clamped the computed pixel size to a `[6, 400]` range — a defensive bound, not a design feature — so an extreme camera position (very close to a node, or numerical edge cases near the perspective divide) can't produce a thumbnail so large it dominates the whole viewport or so small/negative it breaks layout.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the already-running dev server (frontend-only change, so no restart needed) and a fresh headless Chrome instance (no browser extension connected in this environment). Set the real `group:three-stooges` node's default media to its already-attached image, rendered the 3D visualization with the Media toggle on, and read the computed thumbnail size directly off the live DOM element: 16.6px at the visualization's default camera distance. Then moved the camera's position to 40% of its original distance from the scene origin (simulating a zoom-in) and re-read the size: 45.2px — a 2.72x increase, closely matching the ~2.6x increase independently expected from the actual (not origin-relative) distance change from camera to that specific node, confirming the size genuinely tracks camera distance rather than staying fixed. Full `pytest` suite: 45 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — no backend files touched this turn). `node --check ui/js/app.js` passes. Reverted the test node's `default_media_id` back to unset afterward. Left the dev server running and killed only the headless Chrome test instance. `git status --short` shows `ui/js/app.js` and `ui/css/hgai.css` as this turn's changes (everything else listed is carried-over, still-uncommitted work from the immediately preceding turn).
