# Mutation Summary

## Intent
The immediately preceding turn made ordinary (unfocused) Visualize rendering correctly compose multiple selected hypergraphs — a bare member reference in one graph that doesn't resolve locally now resolves against any other selected graph. The user reported that turning on **Focus** for a hypernode broke this: a hyperedges-only projected graph's edges referencing the focused hypernode (by bare id, exactly as the "only new hyperedges" project-inference mode now correctly leaves them) simply vanished from the focus view, even though they render correctly with Focus off.

## Context
The Focus feature (`vizComputeNeighborhood`/`vizOneHopNeighbors`, from an earlier session turn) predates both of the two immediately preceding cross-graph-composition turns and was never updated for them. Investigation found the bug was actually two independent gaps stacked on top of each other, both needed to reproduce and both needed fixing to resolve the report:

1. `vizComputeNeighborhood` is invoked once per selected graph, using only that graph's own `rawNodes`/`edges`. Its very first line was an existence gate: `if (!nodeIds.has(focusId) && !edgeIds.has(focusId)) return null` — requiring the focus id to be an actual hypernode/hyperedge *document* in that specific graph. For a hyperedges-only projected graph, the focused hypernode (`person:shemp`) is never such a document there — it only ever appears as a bare member id inside that graph's own edges (the entire point of the "only new hyperedges" mode from two turns ago) — so this gate always returned `null` for that graph, and `renderViz()`'s existing "focus not found in this graph → contributes nothing" handling wiped its edges entirely before they ever reached rendering.
2. Even granting that a graph could contribute its edges without the focus being a real document there, the SAME BFS run separately, per graph, has no way to discover a hop that crosses graph boundaries — e.g. `person:shemp` (real node, in the canonical graph) → `rel:sibling` edge (only in the hyperedges-only graph) → `person:moe` (real node, back in the canonical graph again). A per-graph BFS on the canonical graph alone never sees that edge at all (it isn't one of the canonical graph's own edges); a per-graph BFS on the hyperedges-only graph finds the edge but has no `person:moe` hypernode document to report as "in this graph's neighborhood." Fixing only gap 1 without also fixing gap 2 reproduced exactly that: the hyperedges-only graph's edges reappeared, but the *other* members of each edge (`person:moe`, `person:curly`) still vanished, because the canonical graph's own focus-filtering pass had already trimmed its `rawNodes` down to just the focus itself before `vizMemberTargetId`'s cross-graph fallback (from the immediately preceding turn) ever got a chance to look them up.

## What Changed and Why
- **Gap 1's fix generalizes the traversal's own "is this expandable" test**, not just the outer existence check. `nodeToEdges` (built purely from `e.members` across every graph's own edges, independent of whether those members also exist as real documents) already had the information needed — the only thing making it inaccessible was `vizOneHopNeighbors`'s hypernode-expansion branch requiring `nodeIds.has(id)` specifically. Swapping that condition to `nodeToEdges.has(id)` is a strictly looser, not different, test: anything that used to qualify (a real local hypernode) still does (every real hypernode that's a member of some edge is trivially also a key in `nodeToEdges`), while now also admitting a bare-referenced, non-locally-defined id.
- **Gap 2's fix — computing the neighborhood once across ALL selected graphs combined — mirrors the exact design already established for ordinary rendering** (`vizMemberTargetId`'s cross-graph fallback treats the set of currently-selected graphs as one composed pool for member resolution). Doing the same for the BFS itself, rather than inventing a separate cross-graph-stitching mechanism for Focus specifically, keeps the two features' notion of "what counts as connected" consistent — a link that renders in the unfocused view is now guaranteed to also be traversable by Focus, since both now walk the same combined node/edge pool.
- **`focusVizNodeId` (which node gets pinned at the origin) now searches across every graph's own raw data for a genuine document match**, since the combined-neighborhood id-membership check alone can't distinguish "this id is a real node in graph X" from "this id is a real node in graph Y" from "this id is only ever referenced, never defined, anywhere" — the pin must land on an actual node that will actually be rendered. First match in graph-selection order wins, consistent with the "no guessing across multiple candidates" precedent already used by `vizMemberTargetId`'s own cross-graph fallback (from the immediately preceding turn) for the same underlying ambiguity (two selected graphs coincidentally sharing an id).

## Key Decisions
- Did not attempt to disambiguate or special-case the (rare, self-inflicted-in-testing) case where the same bare id exists as a genuinely distinct real entity in two unrelated selected graphs — e.g. two independently-authored graphs that each happen to define their own unrelated `person:moe`. Under the combined-BFS model this turn introduces, a Focus on such an id will correctly-per-the-model (if perhaps surprisingly for that specific coincidence) treat both as one connected entity and pull in both graphs' neighborhoods, exactly matching the same id-based composition philosophy `vizMemberTargetId` already established last turn. This is a known, inherent characteristic of resolving cross-graph references purely by matching id strings, not a defect newly introduced by this fix — flagging it here rather than attempting to solve an ambiguity problem nobody asked to have solved.

## Verification
Live end-to-end verification via a hand-rolled CDP script against the running dev server (no restart needed — frontend-only change) and a freshly-created headless Chrome profile. Built isolated test data reproducing the user's own example: `focus-canon` (real `person:shemp`/`person:moe`/`person:curly` hypernodes) and `focus-inferred` (hyperedges-only, two edges — `rel:sibling`: shemp↔moe, `rel:member-of`: shemp↔curly — both with bare, unqualified members) — deleted afterward.

- **The reported bug, reproduced then fixed**: with both graphs selected and Focus set to `person:shemp` at degree 1, the scene now correctly shows all 7 nodes (both henodes — `rel:sibling` and `rel:member-of` — plus all three hypernodes and both "members" virtual nodes) — matching the unfocused baseline render exactly, and `person:shemp` correctly pinned at the origin. Before the fix, this showed only `person:shemp` itself with zero connected hyperedges.
- **Isolated the two-part nature of the bug during debugging**: an intermediate version with only the `vizOneHopNeighbors`/`vizComputeNeighborhood` gate relaxed (gap 1) correctly surfaced both henodes but still dropped `person:moe`/`person:curly` — confirming gap 2 (per-graph-independent BFS) was a real, separate defect, not something gap 1's fix incidentally also covered.
- **Regression checks**: the single-graph case (`hello-world` alone, focus on `person:moe`, degree 1 — the exact scenario the original Focus feature was verified against several turns ago) still produces the correct connected neighborhood (traced a 7-vs-originally-8 count difference to an actual, unrelated change in the live `hello-world` data — `person:shemp2` is no longer referenced by any edge there at all, confirmed directly via the API — not a regression from this fix). Degree-2 composed search, the "not found" toast/empty-state path, and the Clear button's full-graph restore all still work correctly across composed graphs. A three-graph render (`hello-world` + both test graphs) focused on an id that happens to exist in two of the three graphs behaved consistently with the accepted id-collision-ambiguity characteristic described above, with zero JS errors.
- Installed a global `error`/`unhandledrejection` listener across the whole regression pass — zero errors recorded.

Full `pytest` suite: 84 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected — frontend-only). `node --check ui/js/app.js` passes. Chrome test instance killed; dev server left running (not restarted — no backend files touched this turn). `git status --short` shows `ui/js/app.js` as this turn's only actual change (the other listed files carry the three immediately preceding turns' still-uncommitted work).
