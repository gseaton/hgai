# Mutation Summary

## Intent
`project_inference()` (the engine behind the "Project Inference" screen) materializes computed inference results — expanded axioms and/or transitive closures — into a target hypergraph as ordinary, persisted hyperedges. Before this change, every materialized edge's members that didn't already exist in the target graph were unconditionally duplicated into it (`_ensure_member_exists`), so the target always ended up a fully self-contained copy. The user wanted an option to skip that duplication: when composing an inference-only hypergraph meant to sit *alongside* its source graph(s) for querying, the projected edges should reference the members' original canonical locations rather than absorbing point-in-time copies of them — while keeping the existing self-contained-snapshot behavior available as the default/off state.

## Context
This directly builds on two earlier features from this same session: the **cross-graph member reference** feature (`EdgeMember.node_id` accepting a `<graph_id>.<local_id>` dot-notation prefix, resolved by the 3D visualization) is exactly the mechanism this toggle needed to express "reference the canonical original" without duplicating anything — the user's own reasoning in the request describes precisely that convention. And the **HQL/SHQL dot-notation `from:` syntax** investigation earlier this session established that graph ids can never contain `.`, which is what makes a first-dot split unambiguous for this same convention here.

Investigation of the existing `project_inference()` implementation found the duplication behavior lived entirely in one helper, `_ensure_member_exists(node_id)`: for each member of a to-be-created edge, check the target graph, then fall back to copying a matching hypernode from whichever source graph has it. This was the single, precise point to intercept — the rest of the candidate-generation (`expand_edge_closure`, transitive `walk_closure`), dedup (`find_duplicate_hyperedge`), and provenance-tracking machinery needed no changes.

## What Changed and Why
- **A new resolver (`_resolve_member_ref`), not a modified `_ensure_member_exists`.** The two helpers do fundamentally different things — one creates, the other only decides what string to write — and keeping them separate meant the existing (and already-correct) duplicate-into-target code path for the default `only_new_hyperedges=False` case needed zero changes, eliminating any regression risk to that path entirely.
- **Member resolution happens before the dedup check, and its output feeds both the dedup check and the actual write.** This was the one genuinely tricky part: `find_duplicate_hyperedge` computes a deterministic hyperkey from the exact member-id strings that would be stored. If resolution happened only at write time (after dedup), a graph-qualified id like `hello-world.person:moe` would never match what dedup checked against (`person:moe`), and *every* re-run of an `only_new_hyperedges=True` projection would silently re-create the same edges — breaking the function's own documented "safe to re-run" guarantee. Computing `resolved_members` once, upfront, and using it consistently for both purposes closes that gap; verified explicitly by re-running the same projection twice and confirming the second run correctly reports the edge as already existing (`skip`), not a fresh duplicate.
- **A member already present in the target is referenced bare, never qualified, even in `only_new_hyperedges=True` mode.** There's no reason to add a cross-graph prefix pointing at a source graph when a valid local reference already resolves — this also means running the toggle against a target that's already partially self-contained (e.g. from an earlier `only_new_hyperedges=False` projection, or independently populated) degrades gracefully rather than needlessly qualifying references that don't need it.
- **Both a hypernode and a hyperedge are checked at each resolution step** (target first, then each source graph in order) — a candidate edge's member can itself be a hyperedge (hyperedges are first-class and may be members of other hyperedges, established in this session's very first turn), so restricting resolution to hypernodes only would leave hyperedge-type members permanently dangling under `only_new_hyperedges=True`.
- **The toggle is exposed as its own explained callout row**, not folded into an existing column, and is one of the "any change invalidates the current preview" inputs — matching this screen's existing discipline of never letting a user commit something they haven't freshly previewed (a pattern already applied to every other control on this screen).

## Key Decisions
- Considered qualifying every member with the graph-qualified form unconditionally (always `<source>.<id>`, even when it happens to also exist in the target) for simplicity. Rejected: it would make re-running the SAME projection into a target that had ALSO received some members through other means (e.g. a prior default-mode run, or organic growth) produce unnecessarily verbose/inconsistent output, and the "prefer bare, qualify only when necessary" rule matches the same design decision already made for the cross-graph member reference feature's own backward-compatibility handling.
- Considered making `only_new_hyperedges=True` skip resolution entirely and just always write bare member ids (relying on the dangling-reference degrade-gracefully path already documented for genuinely unresolvable references). Rejected: that would silently produce a *non-functional* target graph — the whole point of the toggle is that the target's edges correctly reference their canonical originals, not that they're merely dangling in a way that happens not to error. The point-of-this-feature is functioning cross-graph references, not just avoided duplication.

## Verification
Live end-to-end verification via direct API calls against the running dev server (restarted partway through — Python backend files were edited, and the first dry-run test against the freshly-edited code showed the OLD unqualified behavior until the restart, a useful confirmation the test methodology itself was working correctly) and a hand-rolled CDP script against a freshly-created headless Chrome profile for the UI half.

Built isolated test data (`pi-test-source`, `pi-test-target`, `pi-test-target2` — all deleted afterward) rather than reusing the shared demo graphs, since this feature performs real writes: a transitive-relation scenario (`pi:a --leads-to--> pi:b --leads-to--> pi:c`, with an `owl:transitive` axiom, so `pi:a --leads-to--> pi:c` is the one inferred candidate) and an inverse-of scenario (`pi:a --parent-of--> pi:d`, with an `owl:inverse-of` axiom, inferring `pi:d --child-of--> pi:a`), with the target graph pre-populated with only `pi:a` — deliberately leaving `pi:c`/`pi:d` unresolvable locally, to exercise the qualification path.

- **`only_new_hyperedges=True`, dry-run**: preview correctly showed `pi:a` bare (already in target) and `pi:c` graph-qualified as `pi-test-source.pi:c` (only in source) — for both the transitive candidate and, separately, the expand/inverse-of candidate (`pi-test-source.pi:d` / `pi:a`).
- **`only_new_hyperedges=True`, committed**: the edge was created with those exact resolved members; confirmed via a direct read of the target graph's hypernode list that it still contained only `pi:a` — no duplicate of `pi:c` was created.
- **Re-run safety**: running the identical `only_new_hyperedges=True` commit a second time correctly reported `skipped: 1, created: 0`, referencing the same `existing_edge_id` from the first run — confirming the dedup-uses-resolved-ids fix works.
- **`only_new_hyperedges=False` (default), on a fresh target**: unchanged from before this turn — `pi:c` was duplicated into the target as an ordinary hypernode (target's node list became `['pi:c', 'pi:a']`), and the created edge's members were bare, unqualified ids.
- **UI**: confirmed the toggle exists in the DOM, that `piBuildRequest()` correctly includes `only_new_hyperedges: true`/`false` in the outgoing request body, that clicking Preview with the toggle on renders the qualified member id (`pi-test-source.pi:d · pi:a`) directly in the preview list (proving the whole request→response→render path works, not just the raw API), and that flipping the toggle after a preview correctly disables the Confirm & Project button again (the existing invalidate-on-any-change safety mechanism correctly covers the new control).

Full `pytest` suite: 84 passed, same 3 pre-existing unrelated `test_mesh.py` failures as before this change (unaffected) — `tests/test_inference.py`'s existing unit-test coverage of the module's other helpers also passed unchanged, confirming no regression to code paths this change didn't touch. Chrome test instance killed; dev server restarted once (required — this turn's core change is backend Python) and left running afterward. `git status --short` shows `hgai/api/routers/inference.py`, `hgai/core/inference.py`, `ui/index.html`, and `ui/js/app.js` as this turn's changes.
