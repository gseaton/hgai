# Mutation Summary

## Intent
Continue the phased inferencing plan with Step 4: rebuild transitive-closure reachability (`check_transitive`) on top of Step 2's shared `walk_closure` primitive, with the three return modes (bool/closure/path) the plan specified, and wire it into HQL behind the same `infer: true` flag Step 3 introduced — replacing the old, never-implemented idea of triggering this off a `match.flavor: transitive` value (which stopped making sense once `transitive` was removed from `EdgeFlavor` entirely in Step 1).

## Context
`walk_closure` (Step 2) already did the cycle-safe, PIT-aware BFS, but only returned `{reached_node: via_edge_id}` — enough for Step 3's superproperty-projection use (which only needs "what relations, via which axiom edge"), but not enough to reconstruct a full explanatory path for `check_transitive`'s `path` mode, which the plan explicitly required. The old `check_transitive_relation` (dead code, zero callers, no PIT support) needed replacing rather than extending, matching how Step 3 replaced rather than patched `infer_inverse_edges`.

## What Changed and Why
`walk_closure` was extended to track each reached node's predecessor alongside its via-edge-id (changing its return type from `Dict[str, str]` to `Dict[str, Tuple[str, str]]`) — a small, contained change whose only existing caller (Step 3's superproperty projection) was updated to unpack the new shape. This keeps one shared BFS implementation serving both Step 3's and Step 4's needs, rather than Step 4 duplicating a second BFS just to get path information. `check_transitive` implements the three modes on top of this, self-gating on an `owl:transitive` axiom exactly the way `expand_edge` self-gates on its own axioms — so calling it on a relation nobody declared transitive safely reports "not reachable" rather than treating an incidental relation-name match as if it were meant to chain.

HQL wiring reuses the existing `match.relation`/`match.nodes` fields (already present for the old literal-match behavor) rather than introducing new query syntax: one node under `infer: true` means "what's reachable from here" (closure), two nodes means "are these connected, and how" (path) — both additive to the existing literal match, never replacing it.

Live end-to-end verification (a `warehouse` → `section-a` → `pallet-1` → `box-1` "contains" chain, `owl:transitive` declared on `rel:contains`, run against a real isolated database and then through the actual HQL REST endpoint) confirmed `bool`/`closure`/`path` modes all correct, the axiom gate correctly refusing to treat an undeclared relation (`rel:friend-of`) as transitive even with a direct edge present, and multi-hop path reconstruction producing the exact 3-hyperedge-id chain in order.

That same live testing surfaced a second real redundancy bug (in the HQL wiring this time, not the core primitives): a node or pair reachable in exactly one hop is, by definition, already a literal stored edge — but the closure/path wiring was unconditionally tagging every result `_inferred: true`, so a direct 1-hop fact appeared twice in query output (once as the plain literal match, once again as a spurious "inferred" duplicate). Fixed by skipping 1-hop results in both modes: closure mode checks whether a reached node's predecessor is the start node itself (using `walk_closure`'s predecessor tracking directly, called inline alongside its own axiom check, rather than through `check_transitive`'s coarser `mode="closure"` return shape which doesn't expose per-node hop distance); path mode simply checks `len(path) > 1`.

## Key Decisions
- **Extended `walk_closure`'s return shape rather than adding a second predecessor-tracking function** — Step 4's `path` mode is a genuine second consumer of the same underlying BFS, and duplicating it would mean two BFS implementations to keep in sync; the one existing call site absorbing a small, mechanical update (unpack a 2-tuple instead of a bare string) was judged the better trade-off, consistent with this session's "fewer moving parts" bias.
- **`check_transitive` self-verifies its own axiom** rather than requiring the HQL layer (or any other caller) to check first — same design discipline as `expand_edge`, so "is this relation actually declared transitive" logic lives in exactly one place regardless of how many query surfaces eventually call into it (HQL now, SHQL/MCP/REST later per the plan's Step 5/6).
- **The 1-hop redundancy fix was applied at the HQL wiring layer, not inside `check_transitive` itself** — `check_transitive`'s own semantics (a full, mathematically correct closure/path including 1-hop reachability) are correct and shouldn't be narrowed just to suit one caller's display preferences; the "don't repeat a fact already shown literally" concern belongs to whatever's assembling a combined literal-plus-inferred result set, which today is only the HQL wiring.
- **Live-verified again rather than trusting the plan's hand-traced design**, per this session's now-established pattern (this is the second real bug live-testing caught in this multi-step plan, after Step 3's atomic-facts dedup issue) — both bugs were subtle enough that neither showed up in the original planning conversation's manual worked-examples, only in actually running the code against a live database and a live query.
- Full test suite: 72 passed (unchanged from Step 3 — no new unit tests added, since `walk_closure`/`check_transitive` are DB-dependent and were verified live), same 3 pre-existing unrelated `test_mesh.py` failures.
