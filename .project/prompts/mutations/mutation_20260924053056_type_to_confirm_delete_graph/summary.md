# Mutation Summary

## Intent
Deleting a hypergraph is uniquely destructive in this system — it cascades to every hypernode and hyperedge it contains, with no undo. The existing protection was a single generic confirmation modal shared across every delete action in the app (nodes, edges, media, notes, accounts, meshes, spaces, and hypergraphs alike), which only requires one click on a "Delete" button after reading a message. The user asked for hypergraph deletion specifically to get a stronger safeguard: require typing the hypergraph's own name/id, matching exactly, before the delete can proceed.

## Context
`ui/js/app.js`'s `confirmDelete(msg, cb)` is a single shared helper backing 14 different delete flows in the app, all routed through one Bootstrap modal (`#modal-confirm` in `ui/index.html`) and one `State.confirmCallback`. Making this change specific to hypergraph deletion — rather than applying "type to confirm" to every delete in the app — meant extending the shared helper with an opt-in parameter rather than either duplicating the modal for hypergraphs alone or making every delete flow (including low-stakes ones like removing a tag or an account) newly annoying to use.

## What Changed and Why
`confirmDelete` gained a third, optional `requireText` parameter. When a caller passes one (only `window.deleteGraph` does), the modal reveals a text input labeled with the exact string required, and the Delete button starts disabled — it only re-enables once the typed text matches that string exactly, checked live on every keystroke. The other 13 existing callers (media, hypernodes, hyperedges, notes, accounts, meshes, spaces, space members, parameterized queries, agent vendors/models, chat sessions) call the same function with their existing two arguments, so they keep behaving exactly as before — this was verified by reading every call site before making the change, not assumed.

The button's own disabled state is the primary guard, but the click handler also re-checks the typed value directly before running the delete callback — a defense-in-depth measure in case the disabled state and the input's live value were ever to disagree (e.g. a future change that manipulates the DOM directly). A new modal-close listener resets all of the new state (the required text, the input's value, the button's enabled state) regardless of how the modal was dismissed, so a cancelled hypergraph deletion can't leave stale state that affects the next, unrelated delete confirmation — a real risk given `State.confirmCallback`/`confirmRequireText` are shared, module-level state across every delete flow in the app.

The hypergraph's `id` (not its `label`) was chosen as the required text, since that's exactly what the existing confirmation message already displays in quotes, and it's the platform's stable, always-present, authoritative identifier — a label can be absent or non-unique in a way an id never is.

## Key Decisions
- Extended the existing shared `confirmDelete` helper rather than building a separate, dedicated modal for hypergraph deletion — keeps one code path for all delete confirmations, and makes "type to confirm" available to any future call site (e.g. if space deletion is ever deemed similarly high-stakes) with a one-line change, not a copy-pasted modal.
- Defaulted the new parameter to `null` specifically so every pre-existing call site needed zero changes — verified this held by grepping every `confirmDelete(` call site in the file before finishing, rather than assuming the signature change was safe.
- Could not complete interactive in-browser verification in this environment (the Claude-in-Chrome extension couldn't reach the disposable test server despite the server's own logs proving it was reachable from other clients) — reported this limitation directly rather than claiming a browser test that didn't actually succeed, and instead verified correctness by confirming the exact served file content and tracing the logic by hand.
