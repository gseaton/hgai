# Mutation Summary

## Intent
Earlier in this session, the user asked for an HQL query to return only hyperedges whose *first* member (`seq: 0`) has a specific node ID. Investigation showed neither query engine actually supported that: HQL's `where.members.*` filters were translated into independent MongoDB dot-path conditions that Mongo evaluates against *any* array element (not necessarily the same one), and SHQL's member-pattern matcher never read `seq` at all despite the README documenting examples that implied it did. The user first asked for a research-only refactor plan (no code changes), then asked to implement it in both engines and bring the README and in-UI example queries in line with the corrected behavior.

## Context
- HQL member filtering lives in `hgai_module_hql/engine.py:_build_edge_search_filters`, which builds a `HyperedgeSearchFilters.extra_filters` dict merged directly into the MongoDB query (`hgai_module_storage_mongodb/stores/hyperedges.py`).
- SHQL member filtering lives in `hgai_module_shql/engine.py`, an in-memory SPARQL-inspired pattern matcher (`_match_members` / `_match_members_expand`) that runs after an initial DB fetch.
- The README already contained several examples (`potus-at`, `alpha-bravo-mesh`) that combined `node_id` and `seq` together as if positional binding worked — these were aspirational/incorrect under the old behavior and needed to either be fixed to match new correct semantics or confirmed as now-working.
- No existing test coverage touched member/seq filtering in either engine before this change.

## What Changed and Why
- **HQL**: member sub-field constraints (from both `where: {members: {...}}` and literal `where: {"members.seq": ..., "members.node_id": ...}` syntaxes) are now merged into one dict before being translated to a MongoDB filter. A single sub-field keeps the original "contains anywhere" dot-path behavior (no change, backward compatible). Two or more sub-fields together (e.g. `seq` + `node_id`) are now translated into a single `$elemMatch`, which is the only way MongoDB guarantees multiple conditions bind to the *same* array element rather than being satisfied independently by different elements.
- **SHQL**: added shared helpers `_resolve_member_pat` (resolves a pattern's `bind`/`id`/`seq` against the current variable bindings) and `_member_satisfies` (checks one edge member against required `id`/`seq`), used by both `_match_members` and `_match_members_expand`. This added real `seq` enforcement where it was previously silently ignored.
- **Adjacent bug fix in `_match_members_expand`**: while implementing `seq` support, found that anchor-vs-wildcard pattern classification only checked for a literal `id` key, not whether a pattern's `bind` variable was *already bound* from an earlier pattern in the same query (a common case — e.g. `members: [{node_id: ?person}]` after `?person` was bound by a prior node pattern). Such patterns were misclassified as unconstrained wildcards, which could overwrite the already-correct binding with an arbitrary remaining member's ID. Unifying classification through `_resolve_member_pat` (which already checks `bind_var in binding`) fixes this as a side effect — necessary for `seq`-anchored patterns referencing bound variables (the exact shape of the README's `alpha-bravo-mesh` example) to work correctly, and incidentally corrects the more common already-bound-`id` case too.
- **README.md**: the `potus-at` HQL example previously combined `members.node_id: {$all: [nation:usa]}` with `members.seq: 0` — under the old "independent conditions" semantics this was roughly a no-op (nearly every edge has *some* seq-0 member), but under the new `$elemMatch` semantics it would require nation:usa itself to be the seq-0 member, which isn't the query's intent (the president is seq-0, not the country). Fixed by dropping the seq condition from the HQL query (HQL can't bind/extract "the other member" anyway — that's what the paired SHQL example does) and added a new "Positional member filters (seq)" subsection demonstrating the working feature with a self-contained example. Added confirmation notes to two existing SHQL examples (`potus-at`, `alpha-bravo-mesh`) that already expressed correct *intent* but previously ran on broken/ignored `seq` handling — their YAML didn't need to change, only the engine did.
- **ui/js/app.js**: added one new example to each of `HQL_EXAMPLES` and `SHQL_EXAMPLES`, both using the same "first member of a rel:member group" scenario from earlier in this session, so users browsing the query editor's examples panel see the new capability demonstrated directly.
- **Tests**: added `tests/test_shql.py` (new file) and extended `tests/test_query.py` with unit tests against the pure filter-building / pattern-matching functions directly — no MongoDB required. Full suite run: 34 passed, 3 pre-existing failures in `tests/test_mesh.py` (network-dependent, confirmed pre-existing via `git stash` before this change) unrelated to this work.

## Key Decisions
- **Backward compatibility for single-field member filters**: deliberately kept the plain dot-path translation when only one member sub-field is given, so existing "contains this node anywhere" queries (the majority of documented examples) keep behaving identically — only queries that combine multiple member sub-fields (the previously-broken/no-op case) change behavior, and only to become correct.
- **Fixed rather than preserved the `potus-at` HQL example's old text**: since its old combined-filter behavior was effectively meaningless (a near-always-true `seq: 0` condition tacked onto a real `node_id` filter) rather than intentionally designed, keeping it unchanged after the engine fix would have silently changed the example's real-world results (likely returning zero rows, since nation:usa is not normally the seq-0 member). Correcting the example to match its documented intent was judged safer than leaving a query that would now behave unexpectedly.
- **Unified `_resolve_member_pat` helper in SHQL** rather than adding `seq`-handling as a parallel, separately-maintained code path in `_match_members_expand`: the anchor-classification bug (already-bound `bind`-only patterns misclassified as wildcards) was directly in the way of correctly supporting `seq` for the exact pattern shape used in the README's `alpha-bravo-mesh` example, so fixing both together in one shared code path was more correct and less risky than duplicating divergent logic.
