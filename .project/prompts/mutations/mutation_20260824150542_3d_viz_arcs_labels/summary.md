# Mutation Summary

## Intent
Following the two prior Visualize mutations (2D "bag" refactor, then the initial 3D refactor per `docs/architecture/hypergraph-3d-viz.md`), the user revised that architecture doc and asked for three things: (1) update the 3D hyperedge rendering to match the revision, (2) make multiple relationships emanating from a single node render as visually distinct arcs rather than overlapping straight lines, and (3) restore the node/edge label on/off toggle that existed in the original 2D (Cytoscape) version but was dropped when the visualization moved to `3d-force-graph` (which only offers hover-triggered tooltips, not a persistent, toggleable label).

## Context
The revised `docs/architecture/hypergraph-3d-viz.md` changed one detail from the version used in the prior 3D mutation: the "3D Graph Elements" list now names the virtual edge connecting a hyperedge-node to its "members" node as `flavor:hub` (an EDGE) rather than a generic `"hyperedge"` virtual edge — i.e. that structural link should be typed by the hyperedge's **flavor**, not by a constant placeholder string. Everything else about the doc's tree structure (hyperedge-node → virtual "hyperedge" edge → virtual "members" node → relation-labeled edges → each member) was unchanged from the version the prior mutation already implemented correctly.

The "distinct arcs" request is a real, visible problem with the existing structure: every hyperedge's "members" node is, by design, the single shared source of one relation-link per participant (a hyperedge with N members produces N links radiating from that one members-node). With `3d-force-graph`'s default straight-line links, these can visually overlap or bunch together near the source, especially in the small, offset-cooled layouts typical of the seed data — the user wants each of those relationships to read as its own distinguishable line.

The "restore labels" request runs into the same constraint noted in the prior 3D mutation: `3d-force-graph` doesn't ship a maintained global/non-module three.js build at the version it depends on (`>=0.179 <1`), which ruled out using its native `nodeThreeObject`/`three-spritetext` custom-geometry path for persistent 3D text (that would have required loading three.js as an ES module behind an import map just to get a `window.THREE` global, a much bigger and riskier change to an otherwise all-classic-script page). Investigated and confirmed `three-spritetext`'s UMD build also hard-requires a pre-existing `window.THREE` (`e(t.THREE)`), so it couldn't be used standalone either.

## What Changed and Why
- **Flavor-typed hyperedge link**: the top-level "hyperedge" virtual link now carries `label: flavor:${flavor}` and is colored by the same flavor palette as the relation-links below it, so a hyperedge's entire subtree (top link + all relation spokes) reads as one visually coherent, flavor-colored unit, and the doc's `flavor:hub`-style naming is reflected literally in the rendered label.
- **Distinct arcs via curvature, not a new library**: rather than reaching for a link-bundling extension, links are grouped by their (already-namespaced, collision-free) source node id and assigned curvature values spread symmetrically around zero (`(i - (n-1)/2) * 0.28`). `3d-force-graph`'s built-in `.linkCurvature()` accessor already renders a curved bezier for any nonzero value, so this required no new dependency — just data preparation before `graphData()` is set. A source with only one outgoing link keeps curvature 0 (a straight line), so single relationships are unaffected.
- **Labels restored via a lightweight DOM overlay instead of 3D text sprites**: a plain absolutely-positioned `<div>` per node/labeled-link is repositioned every animation frame by manually projecting each element's live 3D position through the camera's own `matrixWorldInverse` and `projectionMatrix` matrices (read directly off the camera object `3d-force-graph` already constructed internally). This is pure arithmetic on the matrices' `.elements` arrays — it needed no THREE.js reference of our own, sidestepping the version-mismatch problem entirely while still delivering real, always-visible (not hover-only), toggleable labels for both nodes and links. The overlay is rebuilt on every `renderViz()` call and driven by its own perpetual `requestAnimationFrame` loop (independent of `3d-force-graph`'s internal render/physics loop, since the installed version doesn't expose a public "after render" hook) so labels track the graph correctly even after the physics simulation has cooled down and the user is only orbiting the camera.

## Key Decisions
- **Reused the existing camera object rather than adding three.js**: since `Graph.camera()` already returns a live `THREE.Camera`-shaped object with `.matrixWorldInverse`/`.projectionMatrix` (both plain arrays under `.elements`), the standard column-major matrix×vector formula could be applied directly without ever constructing a THREE class ourselves — avoiding the version-compatibility trap hit while investigating `three-spritetext` for this same feature.
- **Curvature grouped by source only, not by exact (source, target) pair**: a literal "parallel edges between the same two nodes" case barely occurs in this data model (each hyperedge has its own distinct "members" node, so true duplicate-pair edges are rare), but many-links-from-one-source is the normal, expected shape (any hyperedge with more than one member). Grouping by source alone directly targets the visual problem the user described ("multiple edges … come from a single node") without adding unnecessary complexity for a duplicate-pair case that isn't the actual pain point here.
- **Verification**: reused the CDP-over-headless-Chrome harness (still no Claude-in-Chrome extension available in this environment) against the seeded `hello-world` graph. Confirmed: every "hyperedge" link is labeled/colored by its flavor (e.g. `flavor:hub` / `#4f46e5`); a members-node with two outgoing relation-links got distinct curvature values (`-0.14`/`0.14`) rather than `0`/`0`; the label layer contained exactly 37 elements (19 nodes + 18 labeled links, matching the graph's actual element count) with 36/37 successfully positioned on-screen after a render tick; toggling the Labels switch off hid every label element and toggling it back on restored visibility; and a screenshot visually confirms distinct arced spokes and both node and link text labels rendering correctly. Zero console errors/exceptions across the full sequence. Test infrastructure (local mongod, the hgai server process, headless Chrome) was torn down afterward.
