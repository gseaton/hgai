# Mutation Summary

## Intent
The user wanted a way to duplicate an existing hypernode or hyperedge in the UI: clicking a "clone" action should open the normal create editor pre-filled with the source record's content (so the user doesn't have to retype everything), but must not silently save a new record — the user still has to review/adjust and explicitly hit Save.

## Context
The Hypernodes and Hyperedges screens (`ui/js/app.js`) already had a shared modal pattern: `openNodeModal(nodeId)` / `openEdgeModal(edgeId)` toggle between a "create" mode (blank form, editable id, graph picker shown) and an "edit" mode (fetches the record by id, id read-only, graph shown as static text). Table rows already had View/Edit/Delete icon buttons wired via `window.viewNode/editNode/deleteNode` and the edge equivalents. Cloning needed to reuse the create-mode UI/save path (so `btn-save-node`/`btn-save-edge`'s existing POST-based create logic didn't need touching) while sourcing its initial field values from an existing record instead of leaving them blank.

## What Changed and Why
Both `openNodeModal` and `openEdgeModal` gained an optional `cloneFromId` parameter. When present (and no `nodeId`/`edgeId` edit target is given), the modal now runs in a third branch — alongside the pre-existing edit and blank-create branches — that fetches the source record via the same `HGAI_API.getNode`/`getSpaceNode` (or edge equivalent) calls already used for editing, then writes its fields into the form exactly as the edit branch does, with two differences: the id field is left editable (not read-only) and is pre-seeded with `<source-id>-copy` as a starting suggestion rather than the exact source id, since ids must be unique. The `node-form-mode`/`edge-form-mode` hidden field is still set to `'create'`, so the existing save handler naturally does a `createNode`/`createEdge` POST — no save-path code needed to change, satisfying the "do NOT auto-save" requirement structurally: populating the form and saving are the same two separate steps they always were, just with the fields pre-filled.

New `window.duplicateNode(id)` / `window.duplicateEdge(id)` entry points call the modals with `(null, id)`. A "Clone" icon button (Bootstrap Icons' `bi-copy`) was added to each table row next to Edit and Delete.

## Key Decisions
- **Function naming — `duplicateNode`/`duplicateEdge`, not `cloneNode`/`cloneEdge`:** the first implementation attempt named the global handler `window.cloneNode`, wired via `onclick="cloneNode('...')"`. This silently failed in manual browser testing — clicking the button did nothing, no console error. Root cause: inline `onclick` attribute handlers resolve free identifiers through a `with`-scope that includes the clicked element itself, and every DOM element already inherits a native `Node.prototype.cloneNode()` method, which shadowed the intended `window.cloneNode` global. Renamed to `duplicateNode` (and, for naming symmetry/to avoid the same trap recurring, `duplicateEdge` even though no edge-side collision exists) and added a comment explaining why, so the name isn't "helpfully" reverted later.
- **Id suggestion (`<id>-copy`) rather than leaving id blank or copying it verbatim:** copying the id verbatim would let the user hit Save and immediately get a duplicate-key error with no other feedback; leaving it fully blank discards useful context. Suggesting `<source>-copy`, fully editable, matches common "duplicate" UX elsewhere and keeps the id field's existing validation/uniqueness behavior untouched.
- **Verified in a running browser session** (server was already running locally on port 8357) rather than only checking `node --check` syntax: this caught the `cloneNode` shadowing bug, which static syntax checking could not have caught.
