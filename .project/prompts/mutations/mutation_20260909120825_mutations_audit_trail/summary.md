# Mutation Summary

## Intent
The user wanted every hypernode and hyperedge to carry a built-in audit trail — a `mutations` list recording each create/update event (who did it, when, what kind, and exactly which fields changed) — with an explicit anti-noise rule: a candidate mutation that would be identical to the most recently recorded one must not be persisted, so repeated no-op or duplicate saves don't pollute the history. The user also asked for this to be backed by "proper logic and UI," not just a data field.

## Context
This follows two earlier pieces of work in this session: the hyperkey/temporal-dedup change (which already established the pattern of computing something at create/update time and passing it through `HypernodePatch`/`HyperedgePatch` into the Mongo store's typed `$set` whitelist), and the clone/duplicate feature (which uses the same create/edit modals and `showDetail`/View-button plumbing that this change extends). The existing `HypernodeInDB`/`HyperedgeInDB` models already had a precedent for "server-managed, not client-settable" fields (`hyperkey` on hyperedges), which is the same pattern used here for `mutations` — added only to the `*InDB` models, never to `*Create`/`*Update`, so it can only ever be set by the engine, never injected via the API request body.

## What Changed and Why
Two new shared models, `MutationDelta` (`field`/`old`/`new`) and `MutationRecord` (`ts`/`by`/`mutation`/`delta`), were added to `hgai/models/common.py` and attached as `mutations: List[MutationRecord]` on both `HypernodeInDB` and `HyperedgeInDB`. `mutation` was deliberately left as a plain string rather than a strict enum — the user's own request punctuated the type list with a "?", signaling openness to more kinds later (e.g. a future "restore"), and a plain string avoids a schema migration when that happens; only `"create"` and `"mutate"` are produced today.

The core logic lives in `hgai/core/engine.py`: a tracked-fields list per entity type (deliberately excluding system/identity fields like `id`, `hypergraph_id`, `hyperkey`, and `mutations` itself, so the audit trail only reflects meaningful content changes, not bookkeeping), plus three pure helper functions — `_create_delta` (every non-blank tracked field at creation, `old: None`), `_update_delta` (only fields the caller actually supplied AND that differ from the current stored value), and `_append_mutation` (the redundancy gate). `_append_mutation` implements the user's exact rule: an empty delta (nothing really changed) is never persisted, and a non-empty delta that exactly matches the *most recent* existing entry (same mutation kind + same delta content) is also not persisted — but a delta matching an *older*, non-adjacent entry (e.g. a value that was changed, reverted, then changed again) is not considered redundant and does get appended, since it represents a genuine new event even if the net field value has been seen before. The function signals "nothing to persist" to callers via Python list identity (returning the exact same list object when it's a no-op) rather than a deep equality check, which let `create_hypernode`/`update_hypernode`/`create_hyperedge`/`update_hyperedge` cheaply decide whether to include `mutations` in the patch at all (`is not existing_mutations` check) instead of always re-writing an unchanged array.

Storage plumbing (`hgai_module_storage/filters.py`'s two Patch dataclasses, and the two Mongo store `update()` whitelist tuples) was extended the same way `label`/`tags`/etc. already work — no new mechanism, no touching the pre-existing `extra_fields` hack that only `hyperkey` uses.

For the UI, rather than adding a new button/modal (which would duplicate the existing View action), the shared `showDetail()`/`modal-detail` flow already used by both hypernodes' and hyperedges' "eye" (View) buttons was extended: a new collapsible section renders the `mutations` array as a human-readable, newest-first timeline (colored CREATE/MUTATE badge, formatted timestamp, `by`, and each delta as `field: old → new`) above the pre-existing raw-JSON dump, which is left untouched as a fallback for full detail.

## Key Decisions
- **Redundancy check compares only to the single most recent entry, not the whole history** — matching the user's literal wording ("if candidate mutation item is the same as the most current mutation item"). This was verified with a dedicated test (`test_append_mutation_does_not_suppress_non_adjacent_repeat`) proving a value that cycles A→B→A→B produces 3 entries, not 1, since only the immediately-preceding entry is checked.
- **`_update_delta` already excludes unchanged fields per-field, before the whole-entry redundancy check runs** — so a PATCH request that resubmits some fields unchanged and one field genuinely changed only records the one real change, not a partial "the same but also new" hybrid. Verified via `test_update_delta_only_includes_actual_changes` and confirmed live (see below).
- **No new UI modal/button** — reused the existing per-row "eye" (View) icon and its shared detail modal for both entity types, since that's already the natural "inspect this record in depth" entry point and avoids duplicating chrome for a feature that's fundamentally about inspection, not action.
- **`import_hypergraph_data` now strips any `mutations` field from imported documents** before reconstructing `Create` models — while pydantic would silently ignore the extra field anyway (verified: default `extra="ignore"` behavior), stripping it explicitly mirrors the existing `hyperkey` strip immediately above it and keeps the intent obvious to a future reader, rather than relying on an implicit pydantic default.
- **Verified end-to-end against a live, isolated instance** (a second `hgai.main` process on an unused port against a throwaway MongoDB database, never touching the user's real data or already-running dev server) for both hypernodes and hyperedges: confirmed a create records a proper `"create"` entry, a real update appends a `"mutate"` entry, an immediately-repeated identical update does NOT add a third entry (stays at 2), and a subsequent genuinely different update does append a third. Also opened the View modal in the browser via `mcp__claude-in-chrome__*` tools and visually confirmed the new Mutation History section renders correctly (2 entries shown, not 3, for the redundancy-suppressed case) before tearing down the test server and dropping the throwaway database. Full test suite re-run clean afterward (57 passed; the 3 `test_mesh.py` failures are pre-existing and unrelated, per earlier `git stash` verification in this session).
