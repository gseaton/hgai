# Mutation Summary

## Intent
Let users import existing RDF data (Turtle, RDF/XML, JSON-LD, Notation3) directly into a HypergraphAI hypergraph, with triples mapped into the platform's own hypernode/hyperedge model rather than requiring a manual conversion step first. The user refined the request across three turns to pin down the exact mapping: a literal-valued triple object becomes an attribute on the subject hypernode; a resource-valued triple becomes a `hub` hyperedge with the subject as the first (seq 0) member and the object as the second (seq 1) member.

## Context
HypergraphAI already has a native export/import pipeline (`hgai.core.transfer`, `hgai_export: '1.0'` YAML/JSON documents) used by the REST API, the `hgsh` shell, and the Web UI's Import modal — with existing conventions this feature needed to respect: hypergraph/node ids must never contain `.` (reserved for the mesh dot-notation and cross-graph `EdgeMember.node_id` delimiter), MongoDB subdocument keys can't contain `.` either, and edges only support two-member binary relations expressed via the existing `hub`/`symmetric` flavor system (RDF triples, being inherently binary, map naturally onto `hub` edges without needing any model changes).

## What Changed and Why
The core of the work is `hgai/core/rdf_import.py`, which parses RDF with `rdflib` (added as a new dependency — MIT-licensed, pure Python, actively maintained, and the de facto standard RDF library) and produces a document in the *exact same shape* the native export/import pipeline already consumes. This was a deliberate architectural choice: rather than writing a parallel storage-writing code path for RDF, `rdf_to_export_document()` is a pure function (no DB access) that hands its output to the *existing*, already-tested `transfer.import_document()` — so RDF import automatically inherits create/merge semantics, per-item error handling (one bad triple's resulting node/edge doesn't abort the whole import), duplicate-edge detection, and every permission check, with zero duplicated logic.

Mapping decisions, each recorded in the module's docstring:
- **Node ids are minted CURIEs (`prefix:local`), never raw IRIs** — an IRI routinely contains `.` (e.g. `http://xmlns.com/foaf/0.1/name`, or any domain-name-based namespace), which would collide with the cross-graph member-reference convention and be rejected as a Mongo subdocument key if used as an attribute name. The original IRI is preserved in `attributes.rdf_uri` so nothing is lost. Ids are sanitized and, in the rare case two different terms sanitize to the same string, disambiguated with a numeric suffix rather than silently merged.
- **`rdf:type` becomes node metadata (`type` + `attributes.rdf_type`), not an edge** — and the type class IRI is deliberately *not* turned into its own hypernode when it's referenced by nothing but `rdf:type` triples, avoiding disconnected, edge-less "class" nodes cluttering the graph for every distinct type in the file. A class that's also used as an ordinary subject/object elsewhere (e.g. it has its own `rdfs:label`) still gets a node from that use.
- **Literal type conversion is conservative**: only datatypes that convert to a BSON/JSON-safe native Python type (int, float, bool, `datetime.datetime`) are converted; everything else (decimal, date, duration, or an invalid lexical value that `rdflib` fails to convert) falls back to the literal's lexical string rather than risk a Mongo insert failure deep in the storage layer or losing precision silently.
- **Output is fully deterministic** (nodes sorted by id, edges sorted by relation/members, multi-valued attributes sorted) so the same RDF file always produces byte-identical output — useful for testing and for anyone diffing re-imports.

The REST layer adds one endpoint per existing native-import route (`/graphs/import/rdf`, `/spaces/{space_id}/graphs/import/rdf`), reusing `run_import()` so authorization is identical to the native path. Because RDF has no embedded hypergraph id (unlike an `hgai_export` file's `graph.id`), `graph_id` is a required query parameter rather than optional.

The Web UI's existing Import modal was extended in place rather than adding a separate RDF-import modal — same file picker, same Space/Mode controls — with the format detected client-side from the file extension and the Hypergraph ID field becoming required (with an explanatory note) only when an RDF file is selected.

## Key Decisions
- **Reuse the export/import pipeline instead of writing storage code**: this was the single highest-leverage design choice — it means RDF import can never drift out of sync with the native import's permission/merge/error-handling behavior, verified directly by re-running the exact same create/merge/403/409 test matrix against the new endpoint live.
- **`os.path.splitext`-based extension detection, explicit `format` always wins**: both the shell and the UI infer format from the filename when possible, but the REST layer itself requires an explicit `format` query parameter (no server-side filename sniffing) — simpler contract, and the UI already computes the right value client-side before calling it.
- **No shell/API magic for JSON-LD named graphs or RDF reification**: both are explicitly out of scope and documented as such in the module docstring and both help docs, rather than silently mishandling them. A named graph's triples are merged into the one target hypergraph (its graph name dropped); reification triples round-trip as ordinary triples on the reification node, not as edge-level provenance.
- **Verification**: 58 new unit tests (including two mutation-style checks — one caught a real bug where an invalid-lexical-value literal leaked an `rdflib.Literal` object instead of a plain string, now fixed; one intentionally-broken guard confirmed the "no orphan class node" behavior is actually tested, not just implemented). Live end-to-end verification against a disposable second server instance (never the user's running one): all four formats imported and stored correctly via curl (including attribute type round-tripping through Mongo — `datetime`, `int`, `bool` survived intact); create/merge/409/403 behavior matched the native import path exactly; the shell client's `import_rdf_file()` was smoke-tested directly. The Web UI flow (format detection, required-id enforcement, empty-id guard, successful import, Help-link navigation) was verified live in Chrome via a synthetic `DataTransfer`-driven file selection (real OS file pickers aren't scriptable) against the same disposable instance, with no console errors. All test data, accounts and the temporary server instances were cleaned up afterward. Full suite: 498 passed (2 pre-existing, unrelated mesh-ping failures excluded, as in every prior session in this project).
