## Answer / Recommendation
**Recommend consolidating on SHQL and sunsetting HQL** — a reversal from the earlier "wait" recommendation, driven by two changes: (1) `aggregate`/`group_by` was ported onto SHQL earlier this session, closing HQL's one remaining functional capability gap, so HQL now has zero unique capability, only a modestly terser syntax for simple filter queries; (2) the no-legacy-users constraint removes the primary reason to defer, leaving a one-time bounded internal cleanup (remove the engine/API/UI/CLI/mesh/MCP surface; separately migrate 15 `.hql` demo-deck files and one training module) versus an open-ended recurring maintenance tax for as long as both languages exist.

No implementation was proposed or executed this turn — entered plan mode (auto-triggered by the harness), wrote the assessment to the plan file, then used AskUserQuestion to check how much of an eventual sunset to scope into an implementation pass (core removal only / core + full content migration / assessment only). The user chose **assessment only, no execution**, so the plan file and final response were finalized as analysis-and-recommendation with no code changes made.

## Key Points
- Evidence the recurring cost is real, not hypothetical: this very session already paid the "duplicate maintenance" tax twice — designing `aggregate` for both engines despite a permanent result-shape seam between them, and finding a real SHQL inference-gating bug only by reconciling it against HQL's equivalent behavior. Also found and fixed drift that had already accumulated (`main.py` capabilities list, a stale README roadmap bullet, a UI code path silently HQL-only) — direct evidence of what happens by default when every feature/doc/example must be built or kept in sync twice.
- Capability comparison: after the `aggregate` port, the README's own `### HQL vs SHQL` table shows no remaining HQL-exclusive row; HQL's only distinguishing property is syntax (~3 fewer lines for a simple single-type filter query), illustrated with a side-by-side example in the plan.
- Standing surface enumerated as the ongoing cost of keeping both: two engines (~570 vs ~1100+ lines), two API routers, two mesh-federation code paths, two MCP-tool branches, two CLI command families (`hgai_shell.py`), two UI query screens, two test files, two README sections plus a comparison table, and a duplicate training-curriculum module.
- Alternative considered and rejected: keeping both indefinitely for HQL's syntactic simplicity on simple queries — rejected because the MCP surface (the primary agent-facing consumer) is already unified regardless of which language is used, and the verbosity difference on simple queries is marginal (shown by example), not enough to justify a whole second production language, test suite, and training module.
- If/when the user wants to proceed, the follow-up splits into two independently-schedulable pieces: **core removal** (engineering surface — module, API, UI, CLI, mesh, MCP, tests, docs trim) and **content migration** (15 `.hql` demo-deck files → `.shql`, plus reworking the training curriculum's HQL module) — offered as the natural next scoping question rather than assumed.
