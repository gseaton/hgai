# Response Summary

## Question / Intent
The user wanted an engineering assessment of whether HQL (Hypergraph Query Language) should be sunset/discontinued in favor of standardizing solely on SHQL (Semantic Hypergraph Query Language), on the theory that this would reduce user confusion and simplify ongoing development/maintenance. This followed directly from the previous turn's finding that `infer: true` behaves asymmetrically between the two engines (SHQL folds inferred edges into live pattern matching before member-pattern/binding logic; HQL only appends inferred edges to the result set after its one match/where pass, never re-matching them).

## Answer / Recommendation
**Do not do a full sunset/removal now** — the underlying concern is valid, but a rip-out would cost more than it saves on current evidence. Recommended path instead:
1. Port `aggregate`/`group_by` support onto the SHQL engine (`hgai_module_shql/engine.py`) so it becomes a strict superset of HQL — currently `aggregate` (`hgai_module_hql/engine.py:456-465`) is the one real functional gap SHQL doesn't cover.
2. Fix small pre-existing doc/integration drift found along the way, independent of the sunset question: add `"shql"` to the capabilities list in `hgai/main.py:170` (currently lists `"hql"` but not `"shql"`); remove the README Roadmap bullet for "HQL `infer:` clause" (`README.md:1518`) since it already shipped.
3. Migrate `ui/js/app.js`'s `fetchInferredEdges` (used by the 3D viz's "Show inferred edges" checkbox) off of hand-built raw HQL text onto SHQL syntax, since it's currently a silent, UI-level HQL dependency that would need to move regardless of the final sunset decision.
4. Re-open the sunset question later with real usage evidence (e.g. a query-language tag in cache/logs) rather than removing a language currently embedded in demo decks and a training curriculum on the strength of a one-off ask.

Offered, but did not do without further direction: turning this into a concrete deprecation plan (migration guide for `.hql` deck files + training module 6, UI removal, API deprecation timeline) if the user wants to proceed with sunset despite the cost.

## Key Points
- **Evidence the concern is legitimate**: the README's own `### HQL vs SHQL` table (`README.md:1619`) already documents HQL as strictly weaker on every structural axis (no variables, no implicit joins, no multi-hop traversal), and elsewhere the README concedes *"HQL has no variable binding, so it can't single out 'the other member' on its own"* (`README.md:195`), reaching for SHQL to actually do the work.
- **Evidence against removing it now — footprint across 8 separate surfaces**, not just an engine module: REST API (`hgai_module_hql/`, ~570 lines), mesh federation (`hgai_module_mesh/engine.py` `federated_hql`), the MCP tool (`hgai_module_mcp/server.py:hgai_query_execute`, which auto-detects `hql:`/`shql:`), the Web UI's whole "Query (HQL)" screen plus the viz's hidden HQL dependency, the CLI shell (`shell/hgai_shell.py`, `query`/`validate` commands weighted equally with `shql`/`shql-validate`), docs (`README.md`, `docs/concepts.md`, `docs/api-reference.md`), a full dedicated training module (`training/user/hgai-user-fundamentals.md` §6, separate from SHQL's §7), and 15 `.hql` demo-deck query files under `docs/decks/*/queries/` (vs 9 `.shql`).
- **The "confusion" argument is weaker at the AI-agent layer than the human layer**: the MCP surface already exposes a single tool, `hgai_query_execute`, which auto-detects the language from the top-level YAML key — an agent doesn't choose between two tools, so removing HQL wouldn't reduce MCP tool-surface confusion, only human UI/docs confusion.
- **The one genuine, non-syntax capability gap**: `aggregate`/`group_by` exists only in HQL; everything else HQL does (mesh dot-refs, space-scoped `from:`, point-in-time `at:`, `distinct`, `limit`/`skip`, `infer:`) SHQL already covers as a superset.
