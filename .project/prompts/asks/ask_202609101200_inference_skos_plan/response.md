# Response Summary

## Question / Intent
The user wanted an assessment of the current state of inferencing/reasoning capabilities for hypernodes and hyperedges (including SKOS-style broader/narrower concept reasoning), and a plan for how to implement it properly — specifically referencing SKOS's `broaderTransitive`/`narrowerTransitive` semantics. Explicitly no code changes in this turn.

## Answer / Recommendation
Investigated the actual codebase (not just docs) and found four separate, uncoordinated partial mechanisms for relation semantics: (1) `attributes.inverse` on `RelationType` hypernodes, consumed by dead code; (2) the `EdgeFlavor` enum, used only as a literal filter, never a trigger for traversal; (3) `skos_broader`/`narrower`/`related` list fields on every hyperedge, actively stripped from every query result before a caller can see them; (4) a relation-algebra-as-meta-hyperedges design sketched only in dev notes, never implemented. Critically, `hgai/core/inference.py`'s `infer_inverse_edges()` and `check_transitive_relation()` have zero call sites anywhere in the codebase, and `match.flavor: transitive` in both HQL and SHQL silently performs a single-hop literal `$all` member match rather than any real transitive closure — a documented (`docs/concepts.md`) but never-implemented `infer: true` flag reinforces the illusion that this works.

Recommended model: relations are data, not code — a `RelationType` hypernode carries an `axioms` list (`owl:transitive`, `owl:symmetric`, `owl:inverse-of:<relation-id>`), and a small generic engine (fixing/generalizing the two existing dead functions) reads those axioms. Two primitives cover everything: `expand_edge` (0-hop inverse-of/symmetric synthesis, read-time only, tagged `_inferred`/`_source_edge`/`_axiom`) and `check_transitive` (N-hop BFS, needs a point-in-time-filtering fix and closure-set/path return modes, not just boolean reachability).

For SKOS specifically: per the real W3C SKOS spec, `skos:broader`/`narrower` must NOT themselves be marked transitive — `broaderTransitive`/`narrowerTransitive` are separate, derived, query-time-only relations (never asserted directly), computed via `check_transitive` over the non-transitive base relation. This avoids conflating direct vs. transitive semantics and avoids a cycle silently collapsing the whole hierarchy. Recommended removing the dead `skos_broader`/`narrower`/`related` fields entirely in favor of modeling SKOS as ordinary hyperedges between concept hypernodes (consistent with the existing "hyperedges are treated as hypernodes" tenet).

Proposed a 5-phase incremental delivery plan (axiom vocabulary → fix expand_edge behind HQL `infer: true` → fix check_transitive behind `flavor: transitive` → SKOS-specific relation seeding + removal of dead fields → SHQL/MCP/REST/UI surfacing), each phase verified via live query execution (not just unit tests), given a DOM-shadowing bug earlier this session was only caught by a live browser check.

## Key Points
- Found an existing "v2 greenfield" design doc (`docs/design/epics-to-build-production-hgai/build-plan.md` §9) that independently arrives at the same RelationType/axiom model and explicitly audits the current dead-inference-code state as "defect #5" — but that doc assumes a full package-monorepo rewrite that was never executed. Treated its ideas as reusable without adopting its rewrite framing, since the user is actively extending the current module layout.
- Flagged that `match.flavor: transitive` currently produces silently-wrong (not absent) results — a query author trusting the documented behavior gets a plausible single-hop match instead of an error or a real traversal. This is a correctness/trust issue, not just a missing feature.
- Recommended explicit-only triggers (`infer: true`, `flavor: transitive`) — never implicit/automatic expansion — matching the project's own "explicit config over implicit magic" principle.
- Recommended NOT caching inferred results initially (PIT-correctness + cache-invalidation compound in a hard way together); add a materialized closure cache only once real usage justifies it.
- Explicitly scoped federated/mesh-wide transitive reasoning OUT of the first implementation as a materially harder problem.
