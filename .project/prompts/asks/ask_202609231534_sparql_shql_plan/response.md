# Response Summary

## Question / Intent
The user wanted (1) a plan for converting RDF SPARQL queries into SHQL queries against HypergraphAI, without making any code changes, and (2) a conceptual overview of SPARQL vs. SHQL — differences and pros/cons of each.

## Answer / Recommendation
Published as a Claude Docs artifact ("SPARQL to SHQL Conversion Plan", https://claude.ai/artifact/GgW8WUM9GkSyyPVc3faQCs) rather than inline chat text, given its length and table-heavy structure.

Recommendation: build a SPARQL-to-SHQL **transpiler** (not a native SPARQL engine), reusing rdflib's existing SPARQL parser/algebra (already a project dependency via RDF import) as the front end and the existing `hgai_module_shql` engine as the execution backend. Scope v1 to SPARQL 1.1's SELECT-query subset — basic graph patterns, OPTIONAL, UNION, FILTER (SHQL's supported operator subset), ORDER BY/LIMIT/OFFSET, and COUNT/GROUP BY — and explicitly reject (with actionable errors) constructs SHQL has no equivalent for, rather than silently mistranslating them.

The plan is phased (documented in the artifact): schema discovery (probing a target hypergraph's own live axiom edges), a rdflib-based parser stage, BGP-to-pattern translation (including topologically reordering SPARQL's unordered basic graph pattern into SHQL's sequential pattern list — flagged as the trickiest correctness point), OPTIONAL/UNION/FILTER translation, ORDER BY/LIMIT/OFFSET/aggregation translation, a rejection/diagnostics layer, a golden-query validation harness (checked against rdflib's own SPARQL evaluator over the same source triples), and packaging as a new optional `hgai_module_*`-style module with its own REST endpoint.

## Key Points
- **Why a transpiler, not a native SPARQL engine:** the impedance mismatch is at the data-model level (RDF triples vs. HypergraphAI's n-ary hyperedges), not just syntax — a transpiler sitting in front of the already-correct SHQL engine avoids re-implementing point-in-time filtering, axiom-driven inference, and mesh federation a second time against a non-RDF-shaped data model.
- **The RDF-to-hypergraph mapping is the real translation target**, not SPARQL syntax itself: every triple pattern must be classified per the exact rules `hgai/core/rdf_import.py` already encodes (resource-valued triple → `edge:` pattern with subject=seq 0/object=seq 1, except `symmetric`-flavored and `owl:inverse-of` edges; `rdf:type` → a `node:` pattern's `type`/`attributes.rdf_type`, never an edge; literal-valued triple → a `node:` pattern's CURIE-keyed `attributes:` filter, with the digit/quote-led value-typing rule and `strip_attribute_prefixes` both affecting what the filter must match against).
- **Real feature gaps, not just missing sugar:** no property-path operators (only `infer: true` on an existing `owl:transitive` axiom edge, and only for relations that actually carry one); no MINUS, subqueries, VALUES, or BIND; only COUNT + single-field GROUP BY (no SUM/AVG/MIN/MAX/GROUP_CONCAT/SAMPLE); no ASK/CONSTRUCT/DESCRIBE query forms; no SPARQL Update equivalent (SHQL is read-only). A full comparison table of every major SPARQL 1.1 construct and its SHQL equivalent (or lack of one) is in the artifact.
- **SHQL's genuine advantages** the plan calls out: native point-in-time querying (`at:`), axiom-driven inferencing built into query execution with no external reasoner, and the ability to query hand-created (non-RDF-imported) hypergraph data that SPARQL could never address at all.
- Effort is dominated by BGP reordering/mapping correctness and the validation harness, not by parsing (since rdflib's parser is reused rather than hand-rolled) — estimated as a multi-week effort, not a quick script.
