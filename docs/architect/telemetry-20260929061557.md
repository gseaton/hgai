# OpenTelemetry Usage & Error Telemetry — Implementation Plan

2026-09-29

**Goal:** emit OTEL-shaped usage and error telemetry from every surface of HypergraphAI (REST, SHQL, MCP, Web UI, shell) to a **configurable HTTP endpoint** (e.g. `https://telemetry.hypergra.ai/report`) — or, when no endpoint is configured (or local storage is explicitly enabled), **into the platform's own store**, as ordinary hypernodes in a dedicated hypergraph — so it can be analyzed for hot spots (slow routes/patterns), most- and least-used features, usage by account, and error/bug reports. This is a **plan**, not an implementation — no code changes accompany it. It proposes a new optional module (`hgai_module_telemetry`), the event taxonomy, the wire format, the local-storage fallback, configuration, privacy handling, and a phased rollout, grounded in this repository's existing conventions (pluggable modules, pluggable storage backends, the mesh scheduler's background-task pattern, and the aggregation-engine work's habit of exact, testable, documented behavior).

**Default posture:** telemetry is **off by default** and self-hosted operators must opt in. HypergraphAI's stated market includes regulated and air-gapped buyers (defense, financial-crime, healthcare — see `docs/marketing/hypergraphai-markets-20260921170527.md` use cases 13–18); shipping telemetry on by default would contradict the "self-hosted, data stays in the customer's store" positioning that is the product's own differentiator (`docs/marketing/hypergraphai-overview-investor-20260921043558.md`, slide 31). This plan is written so the same code serves HypergraphAI's own hosted offering (telemetry on, pointed at `https://telemetry.hypergra.ai/report`) and a self-hosted customer (telemetry off, or pointed at their own collector) without divergent code paths.

---

## 1. What "OTEL JSON message" means here, and a decision this plan makes explicit

OpenTelemetry defines a wire protocol, **OTLP**, with two encodings (protobuf and JSON) and *fixed* per-signal endpoints when used over HTTP: a collector receives traces at `<endpoint>/v1/traces`, logs at `<endpoint>/v1/logs`, metrics at `<endpoint>/v1/metrics`. The example endpoint in the request, `https://telemetry.hypergra.ai/report`, is a **single** path — not an OTLP collector's base URL. Two designs reconcile this, and the plan adopts **both**, selected by a setting, because they serve different audiences:

| Protocol | `HGAI_TELEMETRY_PROTOCOL` | Endpoint shape | Who it's for |
|---|---|---|---|
| **`hgai-envelope`** (default when enabled) | posts one **self-contained OTEL-shaped JSON envelope** (resource + scope + a batch of records) straight to the **exact** configured URL, e.g. `.../report` | HypergraphAI's own hosted collector at `telemetry.hypergra.ai`, or any bespoke ingestion endpoint a customer stands up | Matches the request literally; simplest server to build (one route, one JSON body) |
| **`otlp-http-json`** | posts standard OTLP/HTTP JSON to `<endpoint>/v1/traces` and `<endpoint>/v1/logs` (metrics later) | A customer's own OpenTelemetry Collector, Grafana Tempo/Loki, Honeycomb, etc. | Standards interoperability for enterprise buyers who already run an OTEL pipeline (a real "Honest gaps" answer if a design partner asks) |

Both protocols carry **the same event model** (§3) — only the envelope framing and target path differ. `hgai-envelope` is the default and the one this plan's Phase 1–4 build first; `otlp-http-json` is Phase 6, additive, and reuses the same event objects. This keeps `HGAI_TELEMETRY_ENDPOINT` meaning exactly what the setting name says — "post to this URL" — in the common case, while not closing the door on real OTLP interoperability later.

**Why not require an OTLP collector from day one:** every self-hosted operator would need to stand up and operate a collector just to try telemetry, which is a real adoption tax for an open-core product whose hosted plan's whole pitch is "we run the operational overhead for you." A single JSON envelope to a single URL is the lower-friction default; `otlp-http-json` is there for buyers who already have OTEL infrastructure and want to point it here instead.

## 2. Architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Emitters (every surface a user or agent touches)                        │
│                                                                            │
│  REST middleware   SHQL engine     MCP tool wrapper   Web UI event SDK   │
│  (every request)   (execute_shql)  (every tool call)  (feature clicks)   │
│                                     hgsh shell (every command)            │
└───────────────────────────────┬────────────────────────────────────────┘
                                 │  telemetry.emit(event)  — never awaited by the caller
                                 ▼
                    ┌─────────────────────────┐
                    │  In-process bounded queue │   ← Web UI events arrive over
                    │  (asyncio.Queue, size N)  │     POST /api/v1/telemetry/ingest
                    └─────────────┬─────────────┘     (server-side relay — see §6)
                                  │
                                  ▼
                    ┌─────────────────────────┐
                    │  Background exporter task │   same pattern as
                    │  batches, retries, backs  │   hgai_module_mesh/scheduler.py
                    │  off, redacts, ships       │
                    └─────────────┬─────────────┘
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                            ▼
     HTTPS POST (batched)          Local write: one hypernode per record
     to HGAI_TELEMETRY_ENDPOINT    in the `__local-telemetry` hypergraph
     e.g. .../report               (§3a) — used when no endpoint is set,
     [only when an endpoint is     or HGAI_TELEMETRY_LOCAL_ENABLED=true;
     configured]                   both run together if both apply
```

- **Emission is fire-and-forget.** No request, query, tool call, or UI action ever waits on telemetry. `emit()` is a synchronous, non-blocking call that pushes onto a bounded in-memory queue and returns immediately; if the queue is full, the oldest event is dropped and a drop counter increments (visible on the admin status endpoint, §6). Telemetry must never be the reason a request is slow or fails.
- **One background task** (mirroring `hgai_module_mesh/scheduler.py`'s `_sync_loop`/`start_scheduler`/`stop_scheduler`) drains the queue, batches events (by count or by a flush interval, whichever comes first), and dispatches each batch to every *active* destination (below). Failures back off exponentially and eventually drop the batch rather than grow the queue unboundedly; a local-storage failure and an HTTP-export failure are independent — one destination being down never blocks the other.
- **A pluggable `Exporter` interface**, mirroring `hgai_module_storage.backend`'s pluggable-backend pattern: `NullExporter` (no-op — used whenever telemetry is disabled outright), `HTTPExporter` (posts to `HGAI_TELEMETRY_ENDPOINT`, implementing both protocols from §1), and `LocalHypergraphExporter` (§3a — writes into `__local-telemetry` via the platform's own storage layer, no network involved at all). A `CompositeExporter` fans a batch out to more than one of these when more than one applies.
  **Destination selection**, evaluated once at startup from settings (§6):
  ```python
  def select_exporter(s: Settings) -> Exporter:
      if not s.telemetry_enabled:
          return NullExporter()
      exporters = []
      if s.telemetry_endpoint:
          exporters.append(HTTPExporter(s))
      if not s.telemetry_endpoint or s.telemetry_local_enabled:
          exporters.append(LocalHypergraphExporter())
      return CompositeExporter(exporters) if len(exporters) > 1 else exporters[0]
  ```
  In words: **local storage is used whenever no external endpoint is configured** (so enabling telemetry always does *something* useful, never silently no-ops for lack of a URL), **and additionally whenever `HGAI_TELEMETRY_LOCAL_ENABLED=true`** even if an endpoint *is* configured (so an operator can keep a local, queryable copy while also shipping off-box). The master switch `HGAI_TELEMETRY_ENABLED` still gates all of this — local storage is a *destination* choice, not a way around the opt-in default in §5.
- **New module `hgai_module_telemetry`**, following `docs/module-development.md`'s module descriptor convention (`name`/`version`/`description`/`get_router()`), mounted conditionally in `hgai/main.py` exactly like the Mesh, SHQL, MCP and AgentChat modules are today (`try/except BaseException`, non-fatal on failure). Its router exposes one admin-only status endpoint (§6); the emit/queue/exporter machinery lives in a plain importable package other modules call into, not behind HTTP.

## 3. Event model

Every event — REST request, SHQL query, MCP tool call, UI action, shell command, or error — is the same shape, so the ingestion endpoint and any downstream analysis handle one schema. Names below use an `hgai.*` attribute namespace layered on top of standard OTEL resource/semantic-convention fields where a standard one exists (`service.name`, `service.version`, `deployment.environment`), so an `otlp-http-json` consumer sees familiar fields and a bespoke `hgai-envelope` consumer gets the same information either way.

```jsonc
{
  "resource": {
    "service.name": "hgai",
    "service.version": "0.1.0",
    "service.instance.id": "hgai-local",          // = HGAI_SERVER_ID
    "deployment.environment": "production",        // configurable; helps a hosted-vs-self-hosted split downstream
    "hgai.deployment.mode": "self-hosted"           // "self-hosted" | "hgai-hosted" — set once at deploy time
  },
  "scope": { "name": "hgai.telemetry", "version": "1" },
  "records": [
    {
      "kind": "usage",                              // "usage" | "error"
      "surface": "rest",                             // "rest" | "shql" | "mcp" | "web-ui" | "shell" | "system"
      "feature": "POST /api/v1/hyperedges",           // route template / tool name / SHQL op / UI action id — the "what got used"
      "timestamp": "2026-09-29T06:15:57.123Z",
      "duration_ms": 42,
      "outcome": "ok",                                // "ok" | "error" | "denied"
      "account": {
        "id_hash": "a3f9...",                          // HMAC-SHA256(username, server-local salt) — never the raw username
        "roles": ["user"],
        "is_agent": false
      },
      "attributes": {
        "http.route": "/api/v1/hyperedges",
        "http.status_code": 201,
        "hgai.graph.id_hash": "9c11...",                // hashed unless HGAI_TELEMETRY_INCLUDE_GRAPH_IDS=true (§5)
        "hgai.space.id_hash": "e04b...",
        "hgai.shql.pattern_kinds": ["node", "edge"],    // no query TEXT, ever — see §5
        "hgai.shql.aggregate": true,
        "hgai.shql.aggregate_pushdown": true,
        "hgai.shql.truncated": false,
        "hgai.shql.infer": false,
        "hgai.mesh.federated": false,
        "hgai.mcp.tool": "hgai_hyperedge_create"
      },
      "error": null                                     // present only when kind == "error"; see below
    }
  ]
}
```

An **error record** carries the same envelope with `"kind": "error"` and:

```jsonc
"error": {
  "fingerprint": "b6e2f0...",          // sha256(exception_type + top_repo_frame + message_template) — see §7
  "type": "SHQLError",                  // exception class name only
  "message_template": "SHQL validation errors: '{n}' error(s)",  // parameterized, no raw values by default
  "surface_context": "shql.execute",    // the chokepoint that caught it
  "http_status": 400,
  "stack_frames": [                     // repo-relative file:line + function only, no source text, no locals
    {"file": "hgai_module_shql/engine.py", "line": 1063, "function": "execute_shql"}
  ]
}
```

**Field design notes**

- **`feature`** is the single field every "most/least used" and "hot spot" query groups on. It is always a *template*, never a raw value with data in it (`/api/v1/hypergraphs/{graph_id}`, not `/api/v1/hypergraphs/eden`; `hgai_hyperedge_create`, not the edge's id). FastAPI already exposes the matched route template (`request.scope["route"].path`) for REST; SHQL's `feature` is a normalized description built from the parsed query (`shql.select`, `shql.aggregate`, …), never the query's own field/attribute names, which can themselves be sensitive (e.g. a customer's product names).
- **`account.id_hash`** — never the username or email. Hashed with a per-server-instance salt (a random value generated once at first boot and stored alongside the admin bootstrap record, see `hgai/core/auth.py::bootstrap_admin`) so events can be grouped *per account within one deployment* without being reversible or comparable across two different customers' deployments (which would otherwise let the telemetry backend correlate two companies' user bases). Role and `is_agent` (derived from `Role.agent` in `hgai/models/account.py`) travel in the clear — they're operationally useful (are agents or humans driving usage?) and not identifying on their own.
- **`hgai.graph.id_hash` / `hgai.space.id_hash`** — hashed by default for the same reason; see §5 for the opt-in to send them in the clear (useful for a design partner's own dashboard, harmful as a default for a multi-tenant hosted product).
- **No query text, no node/edge labels or attribute values, no note content, no chat prompts, ever**, in any field, at any verbosity setting. This is a hard rule, not a configuration knob — see §5.

## 3a. Local storage destination — the `__local-telemetry` hypergraph

When `LocalHypergraphExporter` is active (§2 — no external endpoint configured, or `HGAI_TELEMETRY_LOCAL_ENABLED=true`), each OTEL log message becomes one hypernode, written through the platform's own `create_hypernode` engine call (`hgai/core/engine.py`) — the same code path every other hypernode goes through, so it gets the same audit trail, the same `hypergraphs.increment_counts`, and is queryable with SHQL like any other data the moment it lands. **This is a genuinely nice property of a hypergraph-native platform that a bolt-on telemetry system doesn't get for free**: an operator can `POST /api/v1/shql/query` or use the Query (SHQL) screen against their own usage data — `group_by: n.type` for a quick "usage vs. error" split, `attributes.kind`/`attributes.surface`/`attributes.feature` filters for the same hot-spot/most-used/by-account/error questions §8 lists — using a tool they already have, no separate telemetry dashboard required for a self-hosted operator who's happy to query it directly.

**The hypergraph.** `__local-telemetry` — id chosen deliberately: no dot (hypergraph ids may not contain one — reserved for mesh dot-notation, `hgai/models/hypergraph.py`), a leading double underscore to read unambiguously as platform-internal (the same visual convention this plan's UI work should carry into the Hypergraphs list — see below), unowned (`space_id: None`, since usage spans every space and account on the server, not one tenant). **Created lazily** on the first local telemetry write if it doesn't already exist (`get_hypergraph` miss → `create_hypergraph`), the same lazy-create-on-first-use shape as the admin bootstrap account (`hgai/core/auth.py::bootstrap_admin`) — no separate migration or startup step needed. `type: instantiated`, `label: "Local Telemetry"`, tagged `["system", "telemetry"]`, `created_by: "system"` (the existing convention for non-human writers — see `hgai_module_agentchat/store.py`'s catalog seeding and `hgai/core/inference.py`'s Project Inference materialization, both of which already use `created_by="system"`).

**Each hypernode:**

| Field | Value |
|---|---|
| `id` / `label` | `<generated-3–4-word-slug>-<yyyymmddhhmmss>`, e.g. `slow-query-truncated-20260929061557` — see slug generation below. Used for both, since a hypernode's `label` defaults to its `id` display anywhere a label is expected (Visualize, Notes-style listings) and the two should read the same rather than diverge. |
| `type` | `"OTEL"` — a fixed literal, so `attributes: {type: "OTEL"}`-style filtering (`node: {type: OTEL}` in SHQL) finds every telemetry hypernode regardless of `kind`/`surface`, the same way every other hypernode's `type` (`Person`, `Transaction`, …) names its category. |
| `description` | The OTEL JSON message, `json.dumps(record, indent=2)` — human-readable in the Web UI's hypernode detail view and full-text `search:` filterable (`HypernodeSearchFilters.search` already regexes over `label`; extending that same convenience to `description` for this use is a one-line, low-risk addition noted here for Phase 1's implementer, not a new mechanism). |
| `attributes` | The OTEL record itself, as structured JSON — **not** stringified, since `attributes` is already a free-form document (`HypernodeBase`/`hgai_module_storage`'s `attributes.<key>` addressing) and this is what makes `attributes.kind`, `attributes.surface`, `attributes.feature`, `attributes.account.id_hash`, `attributes.duration_ms`, `attributes.error.fingerprint`, etc. each independently queryable and — from Phase 2 on — **aggregatable** via SHQL's own `aggregate:` block (`count`/`group_by`/`sum`/`avg`/`min`/`max`, storage-pushed-down and exact at any scale — the same engine work this session built). "Most-used feature this week," fully local, is `aggregate: {count: true, group_by: n.attributes.feature}` over a `valid_from >= ...` window. |
| `tags` | `["telemetry", kind]` (`kind` = `usage` or `error`), so tag-filtered browsing (the same UI affordance every other hypergraph's node list already has) works without SHQL. |
| `status` | `"active"` always — see retention, below. |
| `valid_from` | The event's own `timestamp`, so point-in-time (`at:`) queries and the Visualize time slider work on telemetry exactly like they do on any other temporal data — "what had happened by 06:00" is already a first-class question this platform answers. |

**Slug generation.** A short, readable identifier (not a random string, not the raw `feature` value verbatim — some `feature`s are long route templates) built deterministically from the event: take up to 4 lowercase, hyphen-joined tokens drawn from `surface`, the meaningful segment(s) of `feature` (path template braces and slashes stripped: `/api/v1/hyperedges` → `hyperedges`), `outcome` (only if not `"ok"`, so success events don't all end in `-ok`), and — for error records — `error.type`; deduplicate adjacent repeats, truncate to 4 tokens, then append `-<yyyymmddhhmmss>` (UTC, second precision) for unique, sortable ids. Example: a failed `POST /api/v1/hyperedges` becomes `rest-hyperedges-error-permissiondenied-20260929061557`; a slow SHQL aggregate becomes `shql-query-aggregate-20260929061557`. If token extraction yields nothing usable (rare — e.g. a UI action with an opaque id), fall back to `kind-surface-<yyyymmddhhmmss>` so the id is still well-formed. This is deterministic and collision-free by construction (the timestamp suffix), so it needs no uniqueness check against existing hypernodes before insert.

**Isolation and access control — required, not optional:**

- **Never enumerated for mesh federation.** `hgai_module_mesh/engine.py::_local_graph_ids()` (used when a mesh server entry has no explicit `graphs` list, to fetch "every active graph on this server" for fan-out) **must exclude `__local-telemetry`** by id. Left unaddressed, a peer server or mesh-admin querying `mesh.*.` graphs on this server would pull cross-tenant, cross-account usage data into a federated SHQL result — a real data-leak path this plan is flagging explicitly so it isn't discovered later. Phase 3a's implementation task is one filter line in `_local_graph_ids()`, not a design question.
- **Admin-only by construction, using the existing permission model, not a new one.** An unowned graph is visible to an account only if `'*' in account.permissions.graphs` or the graph's id is explicitly listed (`hgai/core/auth.py::filter_accessible_graphs`) — admins already satisfy this for every graph. `__local-telemetry` is simply never added to any non-admin account's `permissions.graphs`, so it is invisible to ordinary users through the *existing* REST/SHQL/MCP authorization path with zero new access-control code. This is worth stating plainly: it composes with the security model already audited for every other graph, rather than adding a special case to reason about separately.
- **Excluded from ordinary Hypergraphs browsing.** The Web UI's Hypergraphs list (and `GET /api/v1/graphs`) already permission-filters (§ above), so non-admins never see it; for the admins who *can* see it, Phase 3a should still exclude ids matching `__*` from the default list view (mirroring how dotfiles are conventionally hidden), with an explicit "show system graphs" toggle — it's operational data, not a graph an admin is likely trying to browse alongside their real ones, and a busy telemetry stream would otherwise dominate the list.
- **Excluded from RDF/graph export-import's "all graphs" conveniences** and from any future "duplicate this server" tooling, for the same reason as the mesh exclusion — flagged here so it's checked at implementation time rather than assumed.

**Retention — required because volume is unbounded otherwise.** Every request becomes a hypernode; at any real traffic volume `__local-telemetry` will grow without bound if nothing prunes it, unlike the external-endpoint path where retention is the receiving service's problem. A new setting, `HGAI_TELEMETRY_LOCAL_RETENTION_DAYS` (default `30`), and a background sweep task — the same shape as `hgai/core/media.py::sweep_orphaned_media`'s grace-period GC, invoked from the same lifespan-managed scheduler this plan already reuses from `hgai_module_mesh/scheduler.py` — deletes hypernodes in `__local-telemetry` older than the retention window. `0` disables pruning (keep forever; an operator's explicit choice, not the default). This needs a small storage-layer addition beyond what exists today: `HypernodeStore` currently has `delete_by_graph` (whole-graph delete, used on hypergraph deletion) but no delete-by-filter; Phase 3a adds a narrowly-scoped `delete_before(hypergraph_id, cutoff)` (or reuses `search()` + individual deletes for a first cut, given telemetry hypernodes are cheap to iterate and this isn't a hot path) rather than widening `HyperedgeSearchFilters`-style filters for a one-off need.

**Composability with the external endpoint.** Nothing above is exclusive to standalone/no-endpoint operation: with `HGAI_TELEMETRY_LOCAL_ENABLED=true` *and* an endpoint configured, both destinations receive every batch (`CompositeExporter`, §2) — e.g. HypergraphAI's own hosted deployments could run with local storage on (self-serve, in-product usage insight for the customer) *and* export to `telemetry.hypergra.ai` (cross-customer aggregate product analytics), from the same events, no double instrumentation.

**A note on the privacy posture (§5) in light of this option.** Local-only telemetry (no endpoint configured) is, by construction, **more** private than any external destination: the data never leaves the deployment's own MongoDB, the same database that already holds the customer's actual knowledge graphs — no new trust boundary is crossed. That's worth surfacing to the product owner as a real option: `HGAI_TELEMETRY_ENABLED=true` with no endpoint configured could reasonably be a **friendlier default** than the current plan's "off entirely," since it gives every operator (including regulated/self-hosted ones) their own usage and error visibility with zero data ever leaving their server. This plan does not change the agreed §5 default unilaterally — it's flagged here as a candidate revision worth a decision (see the amended §11 open questions, below), not adopted.

## 4. Instrumentation points

| Surface | Where it hooks in | What becomes `feature` | Notes |
|---|---|---|---|
| **REST** | New ASGI middleware in `hgai/main.py`, added via `app.add_middleware(...)` alongside the existing `CORSMiddleware` | `"{method} {route_template}"`, e.g. `POST /api/v1/hyperedges` | One middleware covers every router (`hypergraphs`, `hypernodes`, `hyperedges`, `accounts`, `spaces`, `media`, `inference`, `notes`, `parameterized_queries`, `help_topics`, plus the conditionally-mounted Mesh/SHQL/MCP/AgentChat routers) without touching each one. Reads the authenticated account off the request state the same way `get_current_account` (`hgai/core/auth.py`) already does, so no route handler changes. |
| **SHQL** | `hgai_module_shql/engine.py::execute_shql` — the single chokepoint every SHQL caller (REST, MCP, mesh federation, HgNexus) already goes through | `"shql.query"` with rich `attributes` (see §3): `aggregate`, `aggregate_pushdown`, `paging_pushdown`, `truncated`, `infer`, federation, pattern kinds/count | This is the highest-value hook for "hot spots": it already reports `meta.truncated`, `meta.aggregate_pushdown`, `meta.paging_pushdown` (built in the storage-aggregation work earlier this session) — those become telemetry attributes for free, so "which queries are hitting the candidate cap in production" becomes an answerable question without new engine code. |
| **MCP tools** | A single wrapping decorator applied where each `@mcp.tool()` function is defined in `hgai_module_mcp/server.py` (30 tools) — implemented as a small helper, e.g. `@telemetry.track_tool` stacked with `@mcp.tool()`, so each tool definition changes by one line, not thirty call sites | `f"mcp.{tool_name}"`, e.g. `mcp.hgai_query_execute` | Captures the same success/denied/error `outcome` the existing `_denied()`/`_guard_graph()` helpers in `server.py` already compute — the wrapper reads their return value, it doesn't reimplement authorization logic. |
| **Web UI** | A small client-side event helper in `ui/js/app.js` (`vizTrackFeature`-style, one call per already-existing user action: Render clicked, Focus double-click — see the double-click focus feature just shipped — Export, Import, Notes save, etc.) posting **to this server's own** `POST /api/v1/telemetry/ingest`, never directly to the external endpoint | `"ui.<screen>.<action>"`, e.g. `ui.visualize.focus_dblclick`, `ui.query.run` | The browser never talks to the external telemetry endpoint directly: no CORS configuration to maintain on a third-party domain, no telemetry API key exposed to the browser, and the server can attach the *verified* JWT-derived account rather than trusting whatever the client claims. `/api/v1/telemetry/ingest` is authenticated the same as any other route and simply enqueues; the browser gets a 202 immediately. |
| **hgsh shell** | The shell's central command-dispatch point (`shell/hgsh_shell.py`) | `"shell.<command>"`, e.g. `shell.import-rdf` | Lower priority (Phase 4) — the shell is typically an admin/scripting surface, less relevant to "which product feature gets used," but cheap to add once the emit() helper exists. |
| **System / startup** | `hgai/main.py` lifespan — module mount failures already logged (`logger.warning(f"... module not available ...")`), mesh sync failures already logged in `scheduler.py` | `"system.module_mount"`, `"system.mesh_sync"` | Turns existing `logger.warning` calls at known trouble spots into structured error events for free, in addition to their existing log lines — logging is not replaced, telemetry is additive. |

**What is explicitly *not* instrumented in Phase 1–4:** request/response bodies, SHQL query text, hypernode/hyperedge/note content, chat (HgNexus) prompts or completions, media file contents or filenames, vendor API keys (already Fernet-encrypted at rest per `hgai_module_agentchat/crypto.py` — never touch telemetry regardless). If a future phase wants opt-in content sampling for debugging, it needs its own explicit, separately-reviewed plan — it is out of scope here.

## 5. Privacy, data minimization, and operator control

This section is as load-bearing as the wire format — telemetry that a regulated buyer can't audit and disable is a sales *blocker* for several of the product's own named markets (defense/public sector, financial-crime, healthcare, GRC — `docs/marketing/hypergraphai-markets-20260921170527.md` #13, #16–18), so the defaults below are deliberately conservative.

1. **Off by default.** `HGAI_TELEMETRY_ENABLED=false` out of the box, in `.env.example`, and in the Docker Compose default. Turning it on is an explicit operator decision, documented in the admin Help topic this plan's Phase 5 adds.
2. **No content, ever, in any mode.** Query text, entity/attribute values, note bodies, chat prompts/completions, media — never leave the process via telemetry, independent of any setting. This is enforced at the event-construction call sites (the emitters only ever build the fixed attribute set in §3), not by a redaction filter downstream that could be misconfigured.
3. **Hashed identifiers by default.** Account, graph and space ids are HMAC-hashed with a per-deployment salt (§3). An operator can opt into sending them in the clear with `HGAI_TELEMETRY_INCLUDE_GRAPH_IDS=true` / `HGAI_TELEMETRY_INCLUDE_ACCOUNT_IDS=true` — useful for HypergraphAI's own hosted deployments where per-customer dashboards want real ids, wrong for a shared or externally-audited default.
4. **A visible kill switch and status.** The admin-only `GET /api/v1/telemetry/status` (Phase 1) reports whether telemetry is enabled, the configured endpoint (host only, not the full URL with any embedded token), queue depth, drop count, and the last export's outcome — so "is this thing sending data, and to where" is answerable without reading source or config files.
5. **Endpoint authentication is separate from data.** If `HGAI_TELEMETRY_API_KEY` is set, it travels as a bearer header to the telemetry endpoint, never as a query parameter (which would land in access logs on the receiving side) and never logged locally.
6. **HTTPS required.** The exporter refuses to start (falls back to `NullExporter` with a startup warning, not a crash — consistent with every other optional module's `try/except BaseException` non-fatal pattern) if `HGAI_TELEMETRY_ENDPOINT` is not `https://`, unless `HGAI_TELEMETRY_ALLOW_INSECURE=true` is explicitly set (local dev only).
7. **Document it like a data-processing disclosure, not a footnote.** Phase 5 adds a Help topic (`docs/help/notes/admin/telemetry.md`, alongside `configuration.md`) stating exactly what is and is not collected, matching this section — the kind of thing a customer's security review will ask for, and the kind of honesty this project's own investor materials already lead with ("Honest Gaps and How the Plan Addresses Them").

## 7. Error/bug reporting specifics

- **Fingerprinting** groups the same underlying bug across many occurrences: `sha256(exception_type + first_repo_frame + message_template)`. The *message template* — not the raw message — is used so `"Hypergraph not found: 'my-secret-project'"` and `"Hypergraph not found: 'other-graph'"` fingerprint identically instead of flooding distinct "unique" errors per customer's graph name. Producing the template from a raised exception is a small helper (regex-strip quoted/formatted segments, or — cleaner — have the handful of call sites that raise user-data-bearing errors, e.g. `SHQLError(f"Hypergraph not found: {ref!r}")` in `hgai_module_shql/engine.py`, pass a template + args pair the telemetry layer formats for the *local* error but only sends the template).
- **Where errors are caught:** a FastAPI exception handler (`app.exception_handler(Exception)` and one for `HTTPException`, added in `hgai/main.py`) covers REST; the MCP tool wrapper (§4) covers MCP; `execute_shql`'s existing `try`/`except SHQLError` boundary covers SHQL parse/validation errors specifically, distinct from a generic REST 500. None of these change existing error *behavior* (status codes, error message bodies returned to the caller) — telemetry observes, it doesn't intercept.
- **Every error is reported**, independent of `HGAI_TELEMETRY_SAMPLE_RATE` (which only thins out high-volume "ok" usage events) — a rare but severe bug shouldn't get sampled away.
- **Downstream analysis** (fingerprint → count, first/last seen, affected `account.id_hash` set, affected route/tool) happens at the receiving service (`telemetry.hypergra.ai` or wherever `HGAI_TELEMETRY_ENDPOINT` points) — **out of scope for this repository**, which is responsible only for emitting complete, well-formed, privacy-safe error records.

## 8. Answering the four analysis questions

| Question | How the event model answers it |
|---|---|
| **Hot spots** | `duration_ms` grouped by `feature`, percentiled downstream. The SHQL hook additionally exposes `hgai.shql.truncated` / `aggregate_pushdown` / `paging_pushdown`, so "slow AND truncated" queries — the ones this session's engine work was built to eliminate — are directly queryable. |
| **Most-/least-used features** | `count(*) group by feature` over a time window, downstream. `surface` lets "most-used REST route" vs. "most-used MCP tool" vs. "most-used UI action" be sliced independently, since they answer different product questions (API integrators vs. agents vs. the Web UI's own audience). |
| **By account** | `group by account.id_hash` (or the real id, if `HGAI_TELEMETRY_INCLUDE_ACCOUNT_IDS=true`), joined against `account.roles`/`is_agent` to separate human usage from agent usage — itself a metric the investor materials care about (how much traffic is agent-driven vs. human-driven is direct evidence for the "AI-native by default" positioning). |
| **Error / bug reporting** | `kind: "error"` records, grouped by `fingerprint`, with the affected `feature`/`surface`/`account.id_hash` set and `stack_frames` — enough to triage and reproduce without ever having shipped the customer's data off their server. |

**All four are answerable "downstream" — but with `LocalHypergraphExporter` active, downstream can be *this server, right now*.** Every row above is a `group_by` / `count` / `avg(duration_ms)` SHQL `aggregate:` query over `__local-telemetry` (§3a): e.g. hot spots is `select: [n.attributes.feature, n.attributes.duration_ms] where: [node: {type: OTEL}] aggregate: {avg: n.attributes.duration_ms, group_by: n.attributes.feature}`, storage-pushed-down and exact regardless of volume. This doesn't replace an off-box analytics service for cross-deployment aggregation (Question §11.2), but it means the four questions this plan exists to answer have a working, self-hosted answer from Phase 3a onward, independent of whether an external endpoint is ever configured.

## 9. Testing plan

Following this repository's existing conformance-test habit (the storage-aggregation and paging-pushdown work built parallel suites against a reference implementation and real MongoDB; this needs the analogous pair):

- **Exporter unit tests** against a fake HTTP client (the same mocking pattern `tests/test_mesh.py` already uses for `get_http_client`): batching triggers on size and on interval, retry/backoff on failure, queue-full drop behavior, fingerprint stability for errors with different data but the same template.
- **A "never blocks" test**: assert that `emit()` returns in well under a millisecond even when the queue is full or the exporter is mid-backoff — the property that matters most, since a regression here turns an optional feature into a production incident.
- **A "disabled means silent" test**: with `HGAI_TELEMETRY_ENABLED=false`, assert zero HTTP calls are made across a full request/SHQL/MCP-tool exercise — the privacy default must be verifiably true, not just documented.
- **Redaction/schema tests**: every emitted event, across every surface's emitter, validates against the fixed schema in §3 (no unexpected keys — an emitter accidentally interpolating a raw value into `feature` or `attributes` should fail a test, not ship to production).
- **A round-trip fixture** for each protocol (`hgai-envelope`, `otlp-http-json`) against a tiny local HTTP server fixture, so a future protocol change is caught by a test rather than discovered against the real endpoint.
- **`LocalHypergraphExporter` tests**: destination-selection logic (§2's `select_exporter`) covers all four combinations of (endpoint set/unset) × (`LOCAL_ENABLED` true/false); a written batch produces exactly the hypernode shape in §3a (id/label slug format, `type: "OTEL"`, `attributes` round-trips the full record, `valid_from` matches the event timestamp); the mesh-exclusion and permission-isolation properties (§3a) are asserted directly — not just described — e.g. `_local_graph_ids()` never contains `__local-telemetry`, and `filter_accessible_graphs` for a non-admin account never includes it; the retention sweep deletes exactly the hypernodes older than the cutoff and nothing else, mirroring `sweep_orphaned_media`'s own existing test coverage as a template.

## 11. Open questions for the product owner

1. **Default enabled for HypergraphAI's own hosted plan?** This plan assumes `HGAI_TELEMETRY_ENABLED=false` in the shipped default (Compose file, `.env.example`) regardless of deployment target, with the *hosted* deployment's own environment configuration turning it on — never a code-level "hosted vs. self-hosted" branch. Confirm that's the intended split.
2. **Is `telemetry.hypergra.ai` a service that exists yet?** This plan builds the emitting side only; a receiving service (ingestion endpoint, storage, the actual hot-spot/usage/error dashboards) is out of scope and presumably a separate project/plan.
3. **Per-account opt-out**, not just per-server? Some buyers may want individual users (not just the whole deployment) able to disable telemetry for their own actions. Not designed above; would add an `AccountPermissions`-level flag (`hgai/models/account.py`) checked at emit time.
4. **Retention and subject-access requests** for hashed account ids — even hashed, a hash is reversible if the telemetry backend also stores the salt or a username→hash mapping; confirm the receiving service's own data-handling plan doesn't undermine the hashing done here.
5. **Metrics (not just usage/error events)** — OTEL also defines a metrics signal (counters, histograms) which would let `duration_ms` percentiles be computed at the SDK level instead of downstream from raw events, at the cost of a heavier SDK dependency. This plan's event-based approach (§3) is simpler and sufficient for the stated goals; revisit only if downstream aggregation volume becomes a problem.
6. **Should local-only telemetry (no endpoint configured) be a friendlier default than fully off?** Flagged at the end of §3a: unlike the external-endpoint path, local storage never leaves the deployment's own database, so it doesn't carry the same privacy argument that justified `HGAI_TELEMETRY_ENABLED=false` in §5/§7's shipped default. This plan does **not** change that default on its own — confirm whether `HGAI_TELEMETRY_ENABLED=true` + local-only should become the out-of-the-box posture, or whether "off means off, no exceptions" is the intended default regardless of where the data would go.
7. **Retention default for `__local-telemetry` (`HGAI_TELEMETRY_LOCAL_RETENTION_DAYS=30`, §3a/§6)** — is 30 days the right default given typical Mongo deployment sizing for this product, or should it scale with `HGAI_CACHE_MAX_SIZE`/expected graph sizes some other way? A DBA-facing decision this plan doesn't have enough deployment data to make confidently.
