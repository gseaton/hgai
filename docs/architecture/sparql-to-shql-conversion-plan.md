# SPARQL to SHQL Conversion Plan

2026-09-23

**Recommendation:** build a SPARQL-to-SHQL *transpiler* (not a native SPARQL engine) that reuses rdflib's existing SPARQL parser/algebra and the existing SHQL execution engine as its backend, scoped to SPARQL 1.1's SELECT and ASK query forms over basic graph patterns, OPTIONAL, UNION, FILTER, VALUES, output-only BIND, ORDER BY/LIMIT/OFFSET/DISTINCT, and COUNT/SUM/AVG/MIN/MAX aggregation — plus two targeted property-path special cases (inverse `^p`, fixed-length `p1/p2` chains) and documented, caveated approximations of `FILTER EXISTS`/`NOT EXISTS` and `MINUS`. Full SPARQL parity is not reachable — SHQL has no general property-path algebra, no subqueries, no `GROUP_CONCAT`/`SAMPLE`, and no `CONSTRUCT`/`DESCRIBE`/Update — so the plan below also names what stays untranslatable and why, rather than chasing 1:1 coverage. This v1 scope follows the tiered prioritization in `docs/architecture/sparql-vs-shql-gaps.md`: everything named above is either purely transpiler-side or an explicitly documented approximation, with one exception: `COUNT`/`SUM`/`AVG`/`MIN`/`MAX` aggregation now maps onto SHQL's own `aggregate:` block, which was extended (and pushed down to the storage layer) specifically so aggregates stay exact on large graphs — see §5, Phase 4.

## 1. SPARQL vs. SHQL — conceptual differences

**Data model.** SPARQL queries an RDF triple store directly (subject–predicate–object, resources and literals, optionally quads/named graphs). SHQL queries HypergraphAI's native hypergraph model: typed hypernodes with an `attributes` document, and n-ary hyperedges with a `relation`, a `flavor` (`hub`/`symmetric`), and an ordered `members` list. RDF import (`hgai/core/rdf_import.py`) maps triples onto this model with specific, lossy rules — a resource-valued triple becomes a 2-member `hub` hyperedge, a literal-valued triple becomes a node attribute (CURIE-keyed), `owl:TransitiveProperty`/`owl:inverseOf`/`owl:SymmetricProperty` become axiom hyperedges. A SPARQL query therefore cannot be transliterated syntactically — it has to be translated *through* this same mapping, or it will silently address a shape of data that doesn't exist (see §4).

**Query syntax.** SPARQL is a W3C-standard declarative text grammar with four query forms (SELECT/ASK/CONSTRUCT/DESCRIBE) plus a separate update language (SPARQL Update). SHQL is a proprietary, read-only YAML/JSON pattern list (`hgai_module_shql/`) — there is no SHQL equivalent of SPARQL Update; all HGAI mutation happens through the REST/CRUD/shell/MCP API instead.

**Pattern matching.** A SPARQL basic graph pattern (BGP) is an *unordered* set of triple patterns joined by shared variables; property paths (`p+`, `p*`, `p1/p2`, `^p`, …) generalize chains and repetition inline in the pattern text. SHQL's `where:` is a *sequential* list of `node:`/`edge:`/`filter:`/`optional:`/`union:` pattern objects, joined by shared `?var` bindings; a hyperedge's `members` sub-patterns match on `node_id`/`seq`/`bind` only — constraining a member's own type or attributes needs a separate join to a `node:` pattern. There is no general path-operator syntax; the nearest built-in equivalent is `infer: true` axiom-driven expansion (`owl:transitive`/`owl:symmetric`/`owl:inverse-of`/`skos:broaderTransitive`/`narrowerTransitive`) plus the dedicated `/infer/transitive` reachability endpoint — and only for a relation that already carries an axiom hyperedge, never an ad hoc path expression. Two narrower path shapes (`^p`, fixed-length `p1/p2` chains) are still translatable without any of that — see §5, Phase 2.5.

**Inferencing.** Plain SPARQL has no built-in entailment (OWL/RDFS reasoning is a separate layer bolted onto a triple store). SHQL bakes a fixed entailment set — inverse-of, symmetric, superproperty projection, transitive closure — directly into query execution via `infer: true`, computed live and never persisted unless explicitly projected. For a hypergraph that was RDF-imported from an OWL-annotated source, this is a genuine SHQL advantage: the importer already turns those OWL declarations into axiom edges with no extra reasoner needed.

**Temporal queries.** SHQL has first-class point-in-time querying (`at:`, matched against `valid_from`/`valid_to`). Plain RDF/SPARQL has no native equivalent without RDF-star or a bespoke reification convention — a capability gap in the other direction, with nothing to translate *from* SPARQL.

**Federation.** SPARQL federates via `SERVICE <endpoint>` inside a query (per-pattern remote binding). SHQL federates via dot-notation mesh refs (`mesh.server.graph`) or a bare mesh id in `from:` — a whole-query graph-set selection, not a per-triple-pattern remote call. These models don't map onto each other cleanly.

## 2. Feature-by-feature comparison

| SPARQL 1.1 construct | SHQL equivalent | Notes |
|---|---|---|
| `SELECT … WHERE { triples }` | `where:` list of `node`/`edge` patterns joined on shared `?var` | Direct translation for the common case (§5) |
| Basic Graph Pattern (unordered) | Sequential `node:`/`edge:` pattern list | Must be reordered so every pattern's variables are bound by an earlier one — SHQL evaluates in list order, SPARQL doesn't |
| `OPTIONAL { }` | `optional: [...]` | Same left-outer-join semantics |
| `UNION` | `union: [{patterns:[...]}, ...]` | Same set-union semantics |
| `FILTER(expr)` | `filter: "expr"` (bespoke mini-language) | Covers `=,!=,<,>,<=,>=,IN,CONTAINS,STARTS_WITH,ENDS_WITH,MATCHES,BOUND,IS_TYPE,AND,OR,NOT`; no arithmetic, no `lang()`/`datatype()`/`str()` |
| `FILTER EXISTS` / `NOT EXISTS` | `OPTIONAL` + `BOUND()`, for simple cases (§5, Phase 3) | Approximated, not equivalent in general — a single existence check translates cleanly; anything nested or combined with further variable use is rejected, not silently mistranslated |
| `MINUS { }` | Two-query subtraction by shared-variable key, client-side in the transpiler (§5, Phase 3) | Approximated — `MINUS` is variable-compatibility-aware in real SPARQL semantics, which this doesn't fully replicate; documented as a known divergence, not claimed as parity |
| Property paths (`p+`,`p*`,`p?`,`p1/p2`,`p1\|p2`,`^p`) | `infer: true` on an `owl:transitive` axiom edge (unbounded `+`); `^p` and fixed-length `p1/p2` chains translated directly (§5, Phase 2.5) | No general path algebra beyond these targeted cases — no alternation (`\|`), no `*`/`?`, no bounded-length repetition, no mixing several path operators in one expression |
| `BIND(expr AS ?x)` | Evaluated client-side over already-fetched rows, for the output-only case (§5, Phase 4) | Supported when `?x` is used only in `SELECT`, never as a join key for a later pattern or inside an upstream `FILTER` — SHQL has no way to make a computed value available *during* pattern matching, so that case is rejected |
| `VALUES` (inline data) | Unrolled into a `union:` of literal-bound branches by the transpiler (§5, Phase 2.5) | Supported — pure transpiler-side translation, no SHQL engine change |
| Subquery (nested `SELECT`) | None | No query nesting — would need staged, two-pass execution at the orchestration layer; out of scope (§5, Phase 5) |
| `GROUP BY` + `COUNT`/`SUM`/`AVG`/`MIN`/`MAX`/`GROUP_CONCAT`/`SAMPLE` | `aggregate: {count, sum, avg, min, max, group_by}` (§5, Phase 4) | All five reducers plus a single-field `GROUP BY` map onto SHQL's own `aggregate:` block. For a single `node:`/`edge:` pattern the storage layer computes them exactly, regardless of graph size (`meta.aggregate_pushdown: true`); more complex patterns are aggregated in memory over the fetched candidates and are flagged `meta.truncated` if the candidate cap cut the data short. Semantics differ slightly from SPARQL: `SUM`/`AVG` ignore non-numeric values instead of raising a type error, and an empty `AVG` is `null`, not `0`. `GROUP_CONCAT`/`SAMPLE`, multi-key `GROUP BY` and aggregates over expressions remain unsupported. Over a mesh (`FROM` several servers), each server aggregates its own graphs and the partials are merged exactly (`avg` as merged sum ÷ merged numeric count), so federated aggregates need no client-side computation either |
| `ORDER BY` / `LIMIT` / `OFFSET` | `order_by` / `limit` / `offset` | Direct translation, including multi-key sort with asc/desc |
| `DISTINCT` / `REDUCED` | `distinct: true` / none | `REDUCED` is a soft hint anyway; `DISTINCT` is a safe over-approximation |
| `ASK` query form | Translated to `SELECT` + `limit: 1`, non-empty check (§5, Phase 4) | Supported — nearly free once BGP/OPTIONAL/UNION/FILTER translation exists; subject to the same candidate-cap caveat as the other Phase 4 items |
| `CONSTRUCT` query form | None | No subgraph-synthesis primitive — HGAI's own hyperedge listing / hypergraph export already serve the usual reason to reach for `CONSTRUCT`; out of scope by design, not just cost (§5, Phase 5) |
| `DESCRIBE` query form | None | No bounded-description primitive — a targeted node query already serves this; out of scope by design (§5, Phase 5) |
| `GRAPH <uri>` (per-pattern named graph) | `from:` graph-id list / mesh refs | Whole-query scoping only, not selectable per triple pattern; the common multi-graph case is already covered by `from:` |
| `SERVICE <endpoint>` | Mesh dot-notation / bare mesh id in `from:` | Different federation model (§1) — HGAI already has a better-fitted, native federation mechanism for its own server topology |
| RDFS/OWL entailment (external reasoner) | `infer: true` | Narrower but built-in and zero-config once axiom edges exist |
| `FROM` / `FROM NAMED` | `from:` | No default-graph-vs-named-graph distinction in HGAI |
| Blank nodes (`_:b`) | `bnode:<label>` hypernode ids | Representable and matchable like any other node once imported |
| Literal datatype/language (`^^xsd:int`, `@en`) | Collapsed at import time | `lang()`/`datatype()` filters have nothing to translate to — this is an RDF-import data-preservation gap, not a query-translation one (see §4's closing note) |
| SPARQL Update (`INSERT`/`DELETE`) | None | Out of scope by design — SHQL is read-only; use the REST/CRUD/MCP API, which carries the permissions/audit/dedup this would otherwise have to reimplement or bypass |

## 3. Pros and cons

**SPARQL — pros:** W3C standard, portable across any RDF store; broad tooling (Jena, GraphDB, Stardog, rdflib) and developer familiarity; full expressive power over the RDF model (property paths, four query forms, federation, an update language, formal entailment regimes); matches the *original* ontology's semantics exactly, with no lossy mapping step.

**SPARQL — cons (in this context):** knows nothing about HGAI-native constructs — n-ary hyperedges, `flavor`, point-in-time validity, spaces, mesh — so a hand-written SPARQL query can only ever address what RDF import preserved, never data created directly through the CRUD API; no temporal query capability without RDF-star or reification; adds a full SPARQL engine (or this transpiler) as new surface area to build and maintain.

**SHQL — pros:** native to the platform — every construct maps 1:1 onto engine internals, so it can query anything in a hypergraph, RDF-imported or hand-created; first-class point-in-time, OPTIONAL/UNION, and axiom-driven inferencing wired in with no external reasoner; a small, simple engine (~1,200 lines) that's easy to extend for HGAI-specific needs.

**SHQL — cons:** no standard, no external tooling, no portability to another RDF store; materially less expressive than SPARQL — no general property-path algebra, no subqueries, no `GROUP_CONCAT`/`SAMPLE`, no `CONSTRUCT`/`DESCRIBE`/Update; `FILTER EXISTS`/`NOT EXISTS` and `MINUS` are only approximated, not fully equivalent; the `FILTER` grammar itself is a bespoke hand-rolled parser, not a real grammar/AST, so it's harder to extend safely than a standard expression language would be. (`VALUES`, output-only `BIND`, `SUM`/`AVG`/`MIN`/`MAX`, `ASK`, and the `^p`/fixed-length property-path special cases are covered — see §5.)

## 4. The RDF-to-hypergraph mapping bridge

A converter cannot transliterate SPARQL triple-pattern syntax onto SHQL edge-pattern syntax directly — it must route every triple pattern through the same mapping `hgai/core/rdf_import.py` already encodes, or its output will query the wrong shape of data:

- `?s <p> ?o` where `<p>` is a resource-valued (object) property → an `edge:` pattern: `relation: <p's full IRI>`, `members: [{node_id: …, seq: 0}, {node_id: …, seq: 1}]` — subject is seq 0, object is seq 1, **except** a data edge on an `owl:SymmetricProperty`, whose flavor is `symmetric` (direction/seq not semantically significant), and the synthetic `owl:inverse-of` axiom shape.
- `?s a <Class>` → **not** an edge pattern at all. `rdf:type` was folded into the subject's `type` (short local name only) and `attributes.rdf_type` (full-IRI list) at import time — the converter must special-case `a`/`rdf:type` into a `node:` pattern's `type:` field or an `attributes: {rdf_type: {$in: [...]}}` match.
- `?s <p> "literal"` → a `node:` pattern's `attributes:` filter — requires computing the same CURIE compaction `_qname()` used (or accounting for `strip_attribute_prefixes`, which changes the key entirely) and the same digit/quote-led value-typing rule (a numeric-looking literal became a native int/float, not a string — a filter written against the string form will not match).
- A property path over a transitive property → `infer: true` + an `edge:` pattern, legal **only if** an `owl:transitive` axiom edge actually exists for that relation right now — otherwise the query must be rejected, not silently run non-transitively.
- A variable bound to a literal's language tag or datatype has nothing to bind to post-import — queries relying on `lang()`/`datatype()`/`str()` must be detected and rejected.

Because axiom edges can be hand-edited after import, the transpiler should query the **target hypergraph's own current axiom edges live** (via SHQL itself) before finalizing any translation that depends on them, rather than re-parsing the original RDF source file — that keeps translations correct even after the hypergraph has since been edited by hand.

The literal datatype/language gap above is a different *kind* of gap from everything else in this plan: it isn't something the transpiler can ever close, because the information doesn't survive RDF import into the hypergraph at all. Closing it would mean changing what `hgai/core/rdf_import.py` *stores* (e.g. a sidecar `attributes["<key>#lang"]`), an import-pipeline design decision independent of this whole conversion effort — see `docs/architecture/sparql-vs-shql-gaps.md`'s Tier 5.

## 5. Conversion plan (phased)

**Phase 0 — Scoping & schema discovery.** Fix the supported SPARQL subset up front (§2) and publish it as a contract. Build a schema-probe step that queries a target hypergraph's own axiom edges via SHQL, so the transpiler knows per-relation whether a path/symmetric/inverse translation is legal for *this* graph.

**Phase 1 — Parser.** SELECT and ASK query forms for v1; CONSTRUCT/DESCRIBE/Update are out of scope by design, not deferred (§2, §5 Phase 5). Reuse `rdflib.plugins.sparql.parser` — already a project dependency via RDF import — to get a validated SPARQL algebra tree rather than hand-rolling a second grammar. Walk the algebra (BGP, LeftJoin, Union, Filter, Extend, Slice, OrderBy, Group/Aggregate, Project), the standard approach for any SPARQL-to-X compiler.

**Phase 2 — Core BGP → SHQL pattern translation.** One pass per BGP, using the Phase 0 schema probe plus the fixed mapping rules (§4) to classify each triple as a `node:` pattern, an `edge:` pattern, or an attribute filter. Then topologically reorder the emitted SHQL pattern list so every pattern's variables are bound by an earlier one — SHQL is sequential, SPARQL's BGP isn't. This ordering step is the single trickiest correctness point in the whole transpiler and needs its own dedicated test suite.

**Phase 2.5 — `VALUES` unrolling and targeted property-path special cases.** Three independent, purely transpiler-side translations — none requires an SHQL engine change:

- `VALUES` — mechanically expand into a `union:` of branches, one per row of inline data, each binding the corresponding variable(s) to a literal before the rest of that branch's patterns run.
- Inverse property path (`^p`) — swap `seq: 0`/`seq: 1` in the translated `edge:` pattern. No dependency on the Phase 0 schema probe.
- Fixed-length path chains (`p1/p2`, …) — expand into N sequential, joined `edge:` patterns. Stretch goal, not blocking v1 — mechanical, but adds translation-stage complexity for a construct most hand-written queries don't actually need (people usually write the joins out anyway).

General property-path algebra (`*`, `?`, alternation `|`, arbitrary mixed sequencing) is explicitly out of scope — see Phase 5.

**A note on why `VALUES` needs unrolling at all.** Single-field "match against a list of literals" is already native to SHQL today, two different ways: `filter: "?var.field IN [a, b, c]"` (SHQL's own FILTER mini-language) and `attributes: {field: {$in: [a, b, c]}}` inside a `node:`/`edge:` pattern (raw MongoDB operators pass straight through). Neither is what `VALUES` unrolling needs, though — SPARQL `VALUES` can bind several variables at once per row, and, more fundamentally, it can inject a binding for a variable with no corresponding pattern at all, which no SHQL construct does: every `node:`/`edge:` pattern derives its binding from an actual document search (`_eval_node_pattern`/`_eval_edge_pattern`), never from a bare literal. Hence the `union:` unrolling above, which works for the general case regardless.

There's a narrower, cheaper alternative worth flagging as a *possible future SHQL engine enhancement*, out of scope for this transpiler plan: SHQL's node-pattern `id:` key currently accepts only a single literal or `?var` (`hgai_module_shql/engine.py`, `_eval_node_pattern`'s `node_id = pattern.get("id")`), even though the storage filter it builds, `HypernodeSearchFilters.node_ids_in`, already accepts a list — the search layer can already do a real multi-id match, `id:` on the YAML surface just never exposes it. If `id:` accepted a list (`id: [a, b, c]`) or a `$in` form, the transpiler could translate the common "`VALUES` enumerates candidate ids for one node pattern" case (e.g. `VALUES ?person { ex:alice ex:bob ex:carol }`) directly into a single node pattern instead of a 3-branch `union:` — a real, self-contained, transpiler-independent SHQL improvement. It's deliberately not part of this plan (it's a genuine `hgai_module_shql/engine.py` change, and the `union:` unrolling above is already correct and general without it), but it would make the common case of `VALUES` translation cheaper if ever taken up separately.

**Phase 3 — OPTIONAL / UNION / FILTER / approximated EXISTS / MINUS.** `LeftJoin` → `optional:`, `Union` → `union:`, `Filter` → best-effort translation to SHQL's FILTER subset. A simple `FILTER EXISTS`/`NOT EXISTS` (a single existence check, not nested inside further variable use or aggregation) translates to `OPTIONAL` + `BOUND()`; anything more complex is rejected, not silently mistranslated. `MINUS { }` translates to two separate SHQL queries — the main pattern and the excluded pattern — subtracted client-side by shared-variable key; this is a documented approximation of SPARQL's variable-compatibility-aware `MINUS` semantics, not a claim of full equivalence. Reject (with a specific, actionable error) anything needing arithmetic or SPARQL builtins with no SHQL analogue.

**Phase 4 — ORDER BY / LIMIT / OFFSET / DISTINCT / aggregation / ASK / output-only BIND.** `ORDER BY`/`LIMIT`/`OFFSET`/`DISTINCT` translate directly per §2. `COUNT`/`SUM`/`AVG`/`MIN`/`MAX` + single-field `GROUP BY` all map onto SHQL's own `aggregate:` block (`count: true`, `sum: <row key>`, `avg`, `min`, `max`, `group_by: <row key>`; each `?var` used must also appear in `select:` so it has a projected row key). The transpiler adds `limit: 0` when the SPARQL query returns only aggregates, so no rows are fetched, and reads the results from `meta` (`count`, `sum`/`avg`/`min`/`max` as `{row key: value}`, `groups` and `group_measures` per group). A single-pattern translation is aggregated by the storage layer and is exact at any scale; a multi-pattern translation (joins, `OPTIONAL`, `UNION`, `FILTER`) is aggregated in memory over the fetched candidates, so the transpiler must check `meta.aggregate_pushdown` and, when it is `false` and `meta.truncated` is `true`, surface the result as incomplete rather than authoritative. `ASK` runs the translated `SELECT` with `limit: 1` and returns whether it came back non-empty: run the translated `SELECT` with `limit: 1` and return whether it came back non-empty. Output-only `BIND(expr AS ?x)` — where `?x` is used only in `SELECT`, never as a join key for a later pattern or inside an upstream `FILTER` — is evaluated the same way, as a post-processing step over the already-fetched rows; a `BIND` used earlier in the query is rejected, since SHQL has no way to make a computed value available *during* pattern matching.

`ASK` and output-only `BIND` still read rows from a plain SHQL `SELECT`, so they inherit the per-pattern candidate cap (2,000 by default, configurable via `HGAI_SHQL_MAX_NODE_CANDIDATES` / `HGAI_SHQL_MAX_EDGE_CANDIDATES`). Unlike before, exceeding it is no longer silent: the result carries `meta.truncated` and `meta.truncated_by`, and the transpiler must pass that through wherever these results are surfaced. Aggregates over multi-pattern queries share the same caveat; single-pattern aggregates do not. `GROUP_CONCAT` and `SAMPLE` remain out of scope for v1 (see `docs/architecture/sparql-vs-shql-gaps.md`).

**Phase 5 — Rejection & diagnostics.** Every unsupported construct must fail translation with a specific, actionable error — never run silently as a subtly-wrong SHQL query. This matters more than raw coverage: a transpiler that quietly ran a `CONSTRUCT` query as an ordinary `SELECT` and returned the wrong shape of result is worse than one that refuses the query outright. Rejections carry the specific reasoning from `docs/architecture/sparql-vs-shql-gaps.md`'s Tier 4/5, not a generic "unsupported" message: `SERVICE` and per-pattern `GRAPH <uri>` point the user at mesh dot-notation and `from:` scoping respectively; `CONSTRUCT`/`DESCRIBE` point at the equivalent native HGAI query or export mechanism; SPARQL Update points at the REST/CRUD/MCP API; `lang()`/`datatype()`/`str()` explain that the underlying information doesn't survive RDF import, not that the transpiler merely hasn't gotten to it yet.

**Phase 6 — Validation harness.** A golden-query suite: hand-picked SPARQL queries (simple BGP, OPTIONAL, UNION, FILTER combinations, one transitive-property query, one symmetric-property query, one `VALUES` query, one `SUM`/`AVG`/`MIN`/`MAX` query (both a single-pattern, storage-pushed-down case and a multi-pattern in-memory case), one `ASK` query, one output-only `BIND` query, one `^p` inverse-path query, one `FILTER EXISTS` approximation case, and one `MINUS` approximation case) run against a known RDF-imported hypergraph (e.g. the `eden` seed's own source TTL), asserting the transpiled SHQL's results match a reference SPARQL evaluator (rdflib's own in-memory engine) over the *same* source triples — except for the `MINUS`/`FILTER EXISTS` cases, which instead assert the *documented* divergence from true SPARQL semantics, not an exact match. Also include a case that deliberately exercises the candidate cap (with a lowered `HGAI_SHQL_MAX_*_CANDIDATES`), asserting `meta.truncated` is set for the in-memory path and that a pushed-down aggregate stays exact, so behavior at the boundary is verified, not just assumed.

**Phase 7 — Packaging.** Ship as a new optional module (e.g. `hgai_module_sparql_shql`), following this project's existing `hgai_module_*` pattern, with a REST endpoint (e.g. `POST /api/v1/graphs/{id}/query/sparql`) that parses → translates → calls the existing SHQL engine. Not a new execution engine — a front-end only, consistent with how `hgai_module_mesh`/`hgai_module_shql` are already separated as pluggable modules.

**A note on scope: this plan covers the backend only.** Every phase above delivers a `hgai_module_sparql_shql` REST endpoint calling the existing SHQL engine — nothing here proposes a Web UI surface (the Query (SHQL) screen has no SPARQL input mode or toggle in this plan), a shell command (`hgsh` has `shql`/`shql -f`; no SPARQL equivalent is named), or an MCP tool (every other query surface — `hgai_query_execute` — is exposed to AI agents via MCP; this endpoint isn't). This isn't a deliberate "backend first" phasing decision recorded anywhere — the client-facing surfaces were simply never scoped. Given who's most likely to actually hand-write SPARQL against this platform (a developer evaluating it against existing RDF tooling, or an AI agent), an MCP tool and/or a Web UI input mode are plausibly more natural entry points than a bare REST endpoint, and deserve their own deliberate scoping — a phase (or phases) with their own effort estimate — rather than an assumption that they'll get "wired up later" once the backend exists.

## 6. Recommendation & next steps

Build the transpiler, not a native SPARQL engine: the impedance mismatch between SPARQL and this platform is at the **data-model** level (triples vs. n-ary hyperedges), and a transpiler sitting in front of the existing, already-correct SHQL engine sidesteps that mismatch far more cleanly than a from-scratch SPARQL-native query engine would — the latter would have to reimplement point-in-time filtering, axiom-driven inference, and mesh federation a second time, against a data model that isn't RDF-shaped to begin with.

Scope v1 to the SELECT/ASK construct list in §2 rather than chasing full SPARQL 1.1 parity — that list is exactly `docs/architecture/sparql-vs-shql-gaps.md`'s Tier 1 (`VALUES`, output-only `BIND`, `SUM`/`AVG`/`MIN`/`MAX`) and Tier 2 (`ASK`, `^p`, fixed-length path chains) items, all achievable inside the transpiler (aggregates via SHQL's now-extended `aggregate:` block, everything else without touching the shared SHQL engine), plus Tier 3's `FILTER EXISTS`/`NOT EXISTS` and `MINUS` shipped as documented, caveated approximations rather than full implementations. Tier 4 (subqueries, `CONSTRUCT`/`DESCRIBE`, per-pattern `GRAPH`, `SERVICE`, SPARQL Update, general property-path algebra) and Tier 5 (literal datatype/language) are explicitly out of scope, not deferred-by-default — several of them are non-goals on their own merits, since HGAI already has a better-fitted native mechanism for the same underlying need, not merely expensive to build. See that document for the full per-gap reasoning behind every one of these calls.

Effort is dominated by Phase 2 (BGP reordering + mapping correctness) and Phase 6 (the validation harness) — not by parsing, since rdflib's SPARQL parser is reused rather than built from scratch. Treat this as a medium-to-large effort (multiple weeks), and expect the golden-query validation harness to surface mapping edge cases (symmetric-property direction, `strip_attribute_prefixes` key collisions, digit-led literal typing, the Phase 4 candidate-cap boundary, and where the `MINUS`/`FILTER EXISTS` approximations diverge from true SPARQL semantics) that aren't obvious from reading the mapping rules alone.
